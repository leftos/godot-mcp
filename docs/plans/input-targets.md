# Input targets: world nodes, visible text, list items

Design draft for the plan item "Input aimed at 2D/3D world nodes through the camera, UI targets by visible text, and Tree/ItemList/TabBar/PopupMenu/OptionButton item targets" ([MAIN.md](./MAIN.md), Wave 1), from ideas 7 and 8 of the [survey](../research/2026-09-29-godot-mcp-survey.md). Section 6's questions are ruled, and the rulings are [DECISIONS.md](../DECISIONS.md) decision 25, which wins where this file differs; steps 1 to 5 of section 7 have landed, and step 6 is open.

## 1. Problem

Today an input target is `{element}` (a Control by path or unique bare name, aimed at its rect's centre) or `{x, y}` in viewport coordinates (`src/GodotMcp.Server/Tools/InputTarget.cs`; the bridge's `resolve_target` in `bridge/godot_mcp_targets.gd`). An `{element}` naming anything but a Control is refused ("is a Node2D, not a Control, so it has no rect to aim at", `_resolve_element`). So the game repos drive what has no Control path by setting state and emitting signals, which skips the input path the player uses, or by computing coordinates by hand:

- **Tabs and options set by hand.** delve `docs/DEVELOPMENT.md` L67: the fight dock's `Tabs` `TabBar` "switches seats (`current_tab`, then emit `tab_changed`)"; a second seat comes "through the host's `Assign` `OptionButton` on a bot's card (`select` the index whose text is the player's name, then emit `item_selected` with it)". A tab and an option item are drawn inside one Control and have no node path, so no `{element}` reaches them. `OptionButton.select` does not emit `item_selected` (4.7 source, `option_button.cpp`: `select()` calls `_select(idx, false)`), which is why the drive emits it by hand.
- **Text differs from name.** delve L67: "The main menu's Host button is the node named `Host` and reads `New Game`, so match the node name, not the text." An agent reading a screenshot sees "New Game" and has no way to aim at it by what it sees.
- **Cards picked by title.** delve L77: the fanned hand and the rewards board reorder their children, so "press by node name (`Card0`) or match the card's `Body/Layout/Title` text"; L67: cards are "pressed through `call("Press")` on the card (the `MarginContainer` above the button; `pressed` emitted on the button leaves the toggle untouched)", and "a card's lower part hangs below the window, so a click lands on its head". The title is a mouse-ignoring `Label` (delve `Scenes/Components/ActionCard.tscn`: the card's `Name` Label under `Body/Layout`, every container on the way `mouse_filter = 2`), a sibling of the `Press` Button that takes the click.
- **Text-less map buttons.** delve L67: "The map's room buttons are the `Pick` buttons under `ZoneMap`, with no text of their own, so a vote is the first visible enabled one of them by name". A text target does not reach them; they stay `{element}` targets (see question 4 on picking one of several).
- **3D projected by hand.** delve L99: a debugging drive projects a die's mesh points "through the tray's `Camera3D.unproject_position`" inside a `run_script`, then reasons about the pixels. Any click or hover on a 3D node today needs the same hand projection, then a guess at how the viewport maps to the window.
- **A Node2D grid.** opening-hand's overworld (`src/Duel.Client/Scratch/OverworldScratch.tscn`) is a `TileMapLayer` and `Things` under `WorldRoot` (Node2D) with a `Camera2D`, inside a `SubViewport` (640x360) that is shown through a `TextureRect` named `Screen` (`OverworldScratch.cs` L262: `screen.Texture = GetNode<SubViewport>("%World").GetTexture()`), not a `SubViewportContainer`. It is driven by keys (`_UnhandledKeyInput`, `Input.IsActionPressed`), so mouse input there is hover and screen readout (where a thing is drawn), not clicks; and no mouse event reaches that SubViewport, since only a `SubViewportContainer` forwards input.

The repo's own docs already point agents at the gap: TOOLS.md "Drive input" says `hover` reads an embedded `PopupMenu` item's tooltip "with a point target (a `PopupMenu`'s items are drawn by its internal `PopupMenuItems` Control, which an element target cannot name …)", and the InputTests compute a popup item's centre in a `run_script` (`tests/GodotMcp.IntegrationTests/InputTests.cs` L96-107).

## 2. Proposed target grammar

One `InputTarget` object, as today, everywhere a tool takes a target: `click.target`, `drag.from` and `drag.to`, `mouse_button.target`, `hover.target`, `scroll.target`. The tools' parameter lists do not change (the five-parameter limit is untouched); `InputTarget` gains keys. Exactly one of three **anchors**, plus optional refiners:

| Key | Meaning |
|---|---|
| `element` | A node by path or unique bare name, as today. Widened (question 1) from Controls to any `CanvasItem` (Node2D, Sprite2D, Area2D, a Control) or `Node3D` |
| `x`, `y` | A point in viewport coordinates, as today |
| `text` | A visible Control whose shown text is exactly this (question 3) |
| `under` | With `text`: search only under this node (path or unique bare name), e.g. `{text: "Strike", under: "Actions/Layout/Row/Hand"}` |
| `item` | With `element` or `text`: an item drawn inside that Control, `{text}` or `{index}` (exactly one; a Tree also takes `path`, the texts from the first shown level down, and `column`, default 0). The Control is an `ItemList`, `Tree`, `TabBar`, `TabContainer` (its tab bar), `PopupMenu`, `OptionButton` or `MenuButton` (their popup) |
| `offset` | With `element` on a world node: `{x, y, z?}`, a point in the node's local space (2D pixels, 3D units) added before projection, default the origin (question 2); a `z` on a 2D node is refused ("is a Node2D; offset takes x and y"), and `z` defaults to 0 on a 3D node |

Examples: `{element: "Tray/Dice/D20"}` (3D), `{element: "WorldRoot/Things/Senior"}` (2D), `{text: "New Game"}`, `{element: "Tabs", item: {text: "Alex"}}`, `{element: "Assign", item: {text: "Alex"}}`, `{element: "Inventory", item: {path: ["Weapons", "Sword"]}}`.

The server (`InputTarget.ToBridge`) checks the shape before anything is sent: one anchor; `under` only with `text`; `item` only with `element` or `text`; `offset` only with `element`; an `item` with exactly one of `text`, `index`, `path`. A refusal names the keys given, as today.

### Resolution to viewport coordinates

Every target resolves in the bridge to one point in the **root viewport's coordinates**, and the existing path takes it from there: `to_window` maps it through the root's screen transform to the window point the injected events carry, so the non-negotiable (input tools take viewport coordinates and map them to the window) holds, and no new code touches window pixels.

- **A Control** (as today): the centre of its rect through `viewport_transform` (`get_global_transform_with_canvas()`, then an embedded window's position and final transform).
- **A 2D world node** (`CanvasItem`, not a Control): `get_global_transform_with_canvas() * offset` in its own viewport's coordinates, which include a `Camera2D` (it sets the viewport's `canvas_transform`) and a `CanvasLayer`.
- **A 3D node**: its viewport's `get_camera_3d()`, then `camera.unproject_position(node.global_transform * offset)` in that viewport's coordinates.
- **Out of a SubViewport**: when the node's viewport is not the root, the point is carried out one viewport at a time until it is in the root's coordinates: through a `SubViewportContainer` parent, `point * stretch_shrink` when `stretch` is on (the container scales events by `1/shrink` on the way in), then the container's own `viewport_transform`; through an embedded `Window`, as `viewport_transform` already does. A SubViewport with no `SubViewportContainer` parent is refused (question 7). This helper also fixes a Control inside a SubViewportContainer, which `viewport_transform` today places in the SubViewport's coordinates.
- **Text**: the matched Control's centre, as an `{element}`.
- **An item**: the item's rect in the Control's local space, centre taken, then through the Control's `viewport_transform`: `ItemList.get_item_rect(idx)` less the scroll bars' values (the 4.7 source does not subtract them, section 3), `Tree.get_item_area_rect(item, column)` (includes the scroll), `TabBar.get_tab_rect(idx)`. Each is checked back before any event, with the Control's own inverse where one exists (`ItemList.get_item_at_position(local, true)`, `TabBar.get_tab_idx_at_point(local)`, `Tree.get_item_at_position(local)`): a point the Control does not map back to the item is refused, so a scroll or cache quirk misses loudly, never on a neighbour. A `PopupMenu` item has no public rect (question 6).

### The hit check

Kept as today for Controls, text and items: after the aim motion, `gui_get_hovered_control()` at the point must be the target (for an item, the list Control), a descendant, or its click-taking ancestor; otherwise nothing is pressed and the call fails naming what covers it. For a text match on a mouse-ignoring Control, see question 5.

A world node is not a Control, so its check is the inverse: the GUI must not take the event. A GUI-handled mouse event never reaches `_unhandled_input` or physics picking (4.7 source, `Viewport::_push_unhandled_input_internal`). `_gui_call_input` (4.7.2 `viewport.cpp` L1740-1783) walks from the hovered Control up its parents and stops at a top-level item; the first Control whose effective filter is Stop marks a pointer event handled (L1764-1767), Ignore Controls are skipped and the walk goes on (`gui_find_control` never returns one, L1871). So, after the aim motion:

- **In the root viewport**: when the hovered chain, up to its top-level item, holds a Control whose effective filter is Stop, the call is refused, nothing pressed: "`<path>` projects to (x, y), where `<control path>` (`<class>`, mouse_filter Stop, rect x,y,w,h) takes the click before physics picking; aim elsewhere with offset, or at that Control."
- **Inside a SubViewport**: the root's hovered Control must be the node's `SubViewportContainer` (whose own filter is Stop, and which forwards the event), as `lands_on` checks for a Control; then the same no-Stop rule applies inside, to the SubViewport's `gui_get_hovered_control()`.
- A handler that calls `accept_event()` cannot be predicted before the press; TOOLS.md says so rather than refusing.

### What the result reports

Every call with a non-point target adds `aimedAt` (for `drag`, `aimedAt: {from, to}`):

```
aimedAt: {x, y, kind: "control" | "node2d" | "node3d" | "item", path, class,
          matched?: {by: "text", text},          // a text target: the shown text it matched
          item?: {index, text, path?},           // an item target: the item it resolved to
          viewport?: "/root/…/World"}            // a world node inside a SubViewport
```

`x, y` is the point aimed at, in viewport coordinates (the same point `pointer` reports once the gesture ends, unless the gesture moved on). `matched.by` says a text target matched shown text; the node's `name` is always in `path`, so "Host" reading "New Game" is visible in one result. The existing hit fields (`pressedOn`, `releasedOn`, `hoveredOn`, `scrolledOn`) stay as they are; for a world node they read null when no Control is under the point, which is the expected outcome.

### Ambiguity

A bare name several nodes share is refused as today (`AMBIGUOUS_TARGET`, up to 10 paths). Several visible Controls showing the same text, or several items with the same text in one Control, are handled per question 4; the recommended rule refuses and lists each match's path (or item index) with its rect, pointing at `under` or `path`/`index`.

## 4. Edges

- **Off-screen.** A resolved point outside the root viewport's visible rect (or outside a SubViewport's rect, or outside its container's visible rect) is refused with the point and the rect: "…/D20 projects to (812, -40), outside the 640x360 viewport". delve's cards that hang below the window are the common case: the refusal lets the agent pass `offset` (a world node) or aim at the text on the card's head (question 5). No clamping: a clamped click lands on something else.
- **Behind the camera.** `is_position_behind` true is refused ("behind the camera …/TrayCamera"), since `unproject_position` would mirror it onto the screen. In front but outside the frustum ends as off-screen.
- **No camera.** A 3D node whose viewport has no current `Camera3D` is refused naming the viewport. A 2D node needs none: without a `Camera2D` the canvas transform is the identity.
- **Hidden or zero-size.** `is_visible_in_tree()` false is refused (as `HIDDEN_TARGET` today). A Control, item or tab rect with no area is refused. A hidden item (`TreeItem.visible` false or an ancestor's, `TabBar.is_tab_hidden`, a hidden PopupMenu item) is refused; a disabled item or tab is aimed at and reported, since clicking a disabled one is a legitimate test, and `aimedAt.item.disabled` says so. Visibility says nothing about occlusion; the hit check covers occlusion by GUI, and occlusion by other world geometry is not checked (the result reports the point, and `take_screenshot` with a crop shows it).
- **Several matches.** See question 4.
- **Unreachable items.** A collapsed Tree ancestor, an item scrolled out of its list or tree, a TabBar tab outside the drawn range, a closed OptionButton popup: question 6.
- **SubViewports.** Through a `SubViewportContainer`: mapped as section 2, and the container's own mouse filter and overlaps decide whether the event reaches it, which the hit check tests (the hovered Control must be the container or inside it). Without one (opening-hand's `TextureRect` showing a `ViewportTexture`): question 7. A SubViewport with `disable_input` on is refused for a press and allowed for a `hover` readout.
- **Not under any camera / canvas.** A `Node3D` in a `World3D` no viewport's camera shows, and a `CanvasItem` outside the tree, are refused ("not drawn by any viewport"). A plain `Node` (no transform) is refused as today.
- **Physics picking in a quiet run** works with no help (section 8): the bridge never calls `notify_mouse_entered()`, which logs a warning on every call once the pointer is inside (4.7.2 `viewport.cpp` L3651-3657). A `SubViewport`'s `physics_object_picking` defaults to off (only the root takes the project setting, `scene_tree.cpp` L2215), so a world node in a SubViewport without it gets no `input_event`; TOOLS.md says so. With `display/window/subwindows/embed_subwindows` off, picking depends on the window manager having seen the pointer over the window (`viewport.cpp` L3264-3268); TOOLS.md names it, no code.
- **Translated text.** The shown (translated) text is matched; a raw key that is not shown does not match. The result's `matched.text` is the shown text.
- **The moving target.** A world node that moves between resolution and press (a walking sprite) is aimed where it was at the aim frame; `drag` resolves `to` once, before the press, as today.

## 6. Open questions for the user

1. **How a world node is named.** (a, recommended) Widen `element` to any CanvasItem or Node3D: the refusal "is a Node2D, not a Control" becomes a world aim, and `aimedAt.kind` says which it was. Worst case: an agent that meant a Control but typed a path to a Node2D gets a world click (with no GUI hit) instead of a refusal, and reads `kind: "node2d"` after the fact. (b) A separate `node` key beside `element`: `element` stays Controls only. Worst case: an agent passes a Sprite2D as `element`, is refused, and needs a second call; two keys to learn for "a node". **Ruled (user, 2026-09-29): (a), widen element.**
2. **Which point of a world node.** (a, recommended) Its origin (`global_position`), with `offset` in local units to aim elsewhere; the point is reported. Worst case: a sprite whose origin is its top-left or feet (`centered = false`, a character pivot) gets clicked at a corner or below the visible body until the agent adds an offset. (b) The visual centre when the node has one (a `Sprite2D`/`AnimatedSprite2D`'s `get_rect()`, a `VisualInstance3D`'s AABB centre, the merged AABB of its visual children), else the origin. Worst case: an `Area3D` whose collision shape is off-centre from its mesh is aimed at the mesh centre and misses the shape the game picks with; the rule is harder to predict from the scene file. (c) Origin only, no `offset`. Worst case: delve's half-off-screen cards and any pivot-at-feet sprite need `{x, y}` again. **Ruled (user, 2026-09-29): (a), the origin plus offset.**
3. **How text matches.** (a, recommended) Exact shown text, whitespace trimmed, case-sensitive; a miss lists up to five near misses (case-insensitive or contained) and any node whose name equals the text with what it shows ("no Control shows 'Host'; …/Host reads 'New Game'"). Worst case: text with a counter or a trailing colon ("Gold: 12") needs its full current form, one extra call after the refusal. (b) Exact, then a unique case-insensitive substring when nothing is exact, `matched.text` saying what it took. Worst case: "Play" silently takes "Play Again" on a screen that has no "Play" yet, and the click happens on the wrong screen state. (c) Also match the node name when no text matches, `matched.by: "name"`. Worst case: a hidden-text Button named like another Control's visible text is clicked; the report says so, after the press. **Ruled (user, 2026-09-29): (a), exact shown text with near misses on a miss.**
4. **Several matches.** (a, recommended) Refuse, listing up to 10 matches with their paths (items: index) and rects, and narrow with `under` or `path`/`index`. Worst case: delve's map, where many text-less `Pick` buttons share one name, still needs a full path per button (as today), and a hand of identical card titles needs `under`. (b) An `nth` key (0-based, in tree order, visible matches only) beside the refusal. Worst case: tree order is not screen order (delve's hand reorders its children when a card lifts, L77), so `nth: 0` presses a different card than the leftmost one. (c) The first visible match in tree order, reported in `aimedAt`. Worst case: the same reorder presses the wrong card with no refusal at all. **Ruled (user, 2026-09-29): (a), refuse listing the matches, narrowed with under or a path or index.**
5. **Text on a Control that takes no clicks** (delve's card title `Label` beside the card's `Press` Button). (a, recommended) Aim at the matched Control's centre and accept, as the hit, a Control of the same scene instance (the hit's `owner` is the match's `owner`, or is that owner) that takes the press there; `pressedOn` names it. Worst case: a scene whose own overlay (a sibling glass panel with mouse filter Stop) covers the label is accepted and swallows the click, and the agent learns it from `pressedOn`. (b) Skip the hit check for a mouse-ignoring match. Worst case: a modal dialog covering the card takes the click and the call reports success. (c) Match only Controls that take clicks (BaseButton, LineEdit, TabBar…); a Label is refused naming its nearest click-taking ancestor. Worst case: delve's cards, whose Button has no text, are unreachable by title, the L77 workaround stays. **Ruled (user, 2026-09-29): (a), aim at the match and accept a hit in the same scene instance, named in pressedOn.**
6. **Items not reachable now, and PopupMenu geometry.** Part one, the reach: (a, recommended) Refuse with the fix and the numbers (a scrolled-out item: its rect and the visible rect, "scroll the list"; a collapsed tree ancestor: its path; a closed `OptionButton`/`MenuButton` popup: "click the button first"), except a closed `OptionButton`/`MenuButton` popup, which the gesture opens with a real click on the button first, reported as `aimedAt.opened: true`. Worst case: an item in a long list needs a `scroll` call and a retry, and a click that opens the popup and presses within 400 ms could be swallowed by PopupMenu's grabbed-click guard (to measure). (b) Refuse all, the OptionButton included. Worst case: delve's `Assign` flow is two calls every time. (c) Make items reachable by setting state (`scroll_to_item`, `uncollapse_tree`, `ensure_tab_visible`, `show_popup`) before the real click. Worst case: the drive skips the scroll and fold input a player makes, the same class of shortcut the item exists to remove, and a game reacting to its own scroll signals behaves differently. Part two, a `PopupMenu` item's point, which Godot does not expose: (a, recommended) Probe with real motions: move the pointer into the popup's items area and read `get_focused_item()` after each motion, bisecting on y until the pointer rests on the item (about log2(n) motions); the final motion leaves the item highlighted as a player's would. Worst case: sweeping across a submenu item can start its open timer, and a very short item list with icons of mixed heights costs a few more motions; `get_focused_item` following the mouse is to be verified first. (b) Recompute the layout from the theme constants as `_get_mouse_over` does. Worst case: a theme or engine change breaks the formula silently and the click lands on the neighbour (caught only by the check-back, which PopupMenu has no public inverse for). (c) Keyboard: `set_focused_item(i)` then `ui_accept`. Worst case: the mouse path the player takes (hover, release rules, the 400 ms guard) is never exercised, and a game listening to mouse input on its menu sees none. **Ruled (user, 2026-09-29): part one (a), refuse with the fix and open a closed OptionButton or MenuButton popup with a real click; part two (a), probe with real motions.**
7. **A SubViewport shown without a SubViewportContainer** (opening-hand's overworld through a `TextureRect`). (a, recommended) Refuse naming the SubViewport and how it is shown; a press there would not reach the SubViewport anyway, since only a container forwards input. Worst case: an agent cannot `hover`-read where the Senior is drawn on screen and keeps using `run_script` for that readout. (b) Map through a `TextureRect` whose texture is that viewport's `ViewportTexture` for its stretch modes (scale, keep, keep centred, tile refused), for `hover` and readout only, refusing presses. Worst case: more mapping code for one scratch scene, and a game that draws the texture another way (a Sprite2D, a shader) still falls to the refusal. **Ruled (user, 2026-09-29): (a), refuse naming the SubViewport.**

Rulings (user, 2026-09-30): a disabled popup item is refused, since `get_focused_item()` reads -1 over it and the probe cannot confirm the aim; an item inside a submenu takes two calls, the first aiming at the submenu item until its submenu opens (`aimedAt.item.submenu` names it), the second targeting that submenu `PopupMenu` as `element`; `hover` on an item of a closed `OptionButton`/`MenuButton` popup is refused ("click the button first") and never presses. Rulings as built:
   - The opening click's press sets the mouse button mask (measured), so the popup shows with the button held and arms its grabbed-click guard; that click's own release reaches the popup's `gui_input`, which clears the guard first (popup_menu.cpp L708-712), so the item's press follows with no wait.

# State digest: a game's own compact state in place of a screenshot

Design draft for the plan item "State digest: game nodes opt in for a compact state read in place of a screenshot" ([MAIN.md](./MAIN.md) L29, the Track), from idea 4 of the [survey](../research/2026-09-29-godot-mcp-survey.md) (L115-118). Nothing here is decided until the open questions in section 6 are answered.

## 1. Problem

An agent that wants to know what a game is doing (whose turn it is, how many hit points a card shows, which cell the player stands on) has three routes today, and none of them is the game saying it: a screenshot, read by eye; the engine's view of nodes (`inspect_node`, `snapshot_subtree`, `get_ui_elements`), which sees exported properties and drawn Controls, not the game's model; or a hand-written script (`run_script`, `run_csharp`, the `cs_*` tools) that knows where the model lives. The two C# games driven through the server lean on the third.

**delve-the-dungeon.** Its drive notes forbid the screenshot as a source of numbers and put a script in its place:

- **Numbers come from scripts.** `docs/DEVELOPMENT.md` L73: "the numbers (the ghosts' centres, the hit points on ghost and card, a card's alpha) are read from a sampling script, never from the shot". In that file alone `run_script` is named 25 times, `run_csharp` 3, `cs_set` and `cs_members` once each (counted with `rg -o` over the file), and `snapshot_subtree` never.
- **The model is not where the engine looks.** The fight's state is `Combat.ShownView`, an `internal GameState?` (`src/Delve.Client/Scripts/Screens/Combat.cs` L323), and `GameState` is an immutable record of the whole run, the floor, the party and the phase (`src/Delve.Rules/State/GameState.cs` L24-34). Godot's `get` and GDScript cannot read a record (TOOLS.md L28), so `inspect_node` and `snapshot_subtree` see none of it; `cs_get {node: "Combat", member: "ShownView"}` does, but writes the whole run to 8 levels (TOOLS.md L276), and the agent has to know the member's name first. `Combat.StartedBeatCount` (L345) is a public `int` added so a drive can wait on it (DEVELOPMENT.md L75): the game already shapes state for agents, one member at a time.
- **Scripts must know the tree.** L72: `has_method` "does not see a C# method that is `internal`, so a `run_script` tells a node apart by where it stands … never by a method it carries"; look nodes up "by name and class …, never by bare name: `find_child("Ready")` on the lobby returns a seat card's label first". L77: the hand and the rewards board reorder their children, and "a script that then reads the board's nodes gets `null`: find the screen again under `Main/Safe/Screens` after every press". L69: the dice are "no `RigidBody3D` …, so a script that counts bodies counts none". Each is a lesson a script paid for, and every new drive re-learns where the numbers live.
- **What a state read would carry.** L67 reads the question label by the start of its text (`begins_with`, since it "can carry a second line"), and L74 reads "every card's `size` against its `get_combined_minimum_size()`": both are the game's own facts, reached through drawn Controls.

**opening-hand.** It drives scratch scenes one step at a time and reads the tree between steps: `docs/DEVELOPMENT.md` L61 plays `PlayStep` "with `wait_for` … between steps, which also leaves room to read the tree or `snapshot_subtree` before a step". The scratch base class exposes its state as a status line (`ScratchScene.GetStatus()`, `src/Duel.Client/Scripts/Diagnostics/ScratchScene.cs` L192, public because "`has_method` and `call` see a C# method only while it is public", L17-20). The overworld's logical position is a private field, `private Vector2I playerCell` (`src/Duel.Client/Scratch/OverworldScratch.cs` L117): `inspect_node` leaves it out (it lists only `[Export]` members of a C# script, TOOLS.md L252), and `snapshot_subtree` sees the sprite's pixel position, not the cell.

The survey's source servers solve this with a convention the game opts into: satelliteoflove's `digest` reads nodes in an `mcp_watch` group or with `func _mcp_state() -> Dictionary` (its `docs/tools/runtime-state.md` L19, L23; `max_nodes` 40 by default, L28), and Gua reads nodes in a group with metadata (survey L117). Neither reaches C#. Both our games are C# (MAIN.md L26), so the opt-in must work from C#, where a method's return type decides whether Godot can call it at all (section 3).

## 2. Proposed design

A game marks the nodes whose state matters and gives each a method that returns that state; one runtime tool reads every marked node in one frame and returns the values, bounded in size, and can keep the read for `diff_snapshots`. Each part below states the recommended option; section 6 holds the alternatives.

### How a node opts in (questions 1, 2)

A node is in the group `mcp_state` and defines the state method:

```gdscript
func _ready() -> void:
    add_to_group("mcp_state")

func _mcp_state() -> Dictionary:
    return {"hp": hp, "maxHp": max_hp, "cell": cell, "status": status_names()}
```

```csharp
public override void _Ready() => AddToGroup("mcp_state");

// Any accessibility, no parameters, any return type the C# tools can write: a record, an anonymous type,
// a Dictionary<string, object?>, a Godot.Collections.Dictionary.
private object _McpState() => new { Turn = view.Turn, Question = question.Text, Seats = view.Party.Select(p => new { p.Name, p.Hp }) };
```

The GDScript name follows GDScript's convention for a callback the engine never calls, the C# name C#'s (MAIN.md L29 names `_McpState`). A C# method is found by reflection in the C# helper (question 1), so the method need not be public and its return need not be a Variant type: Godot's own call cannot see a method that returns a record (section 3), which is the state delve would return. The group is the index (question 2): `get_nodes_in_group` returns the marked nodes in tree order without walking the tree, autoloads included, so delve's `Net` (an autoload, not under the current scene) can opt in. The group is added in code or saved in the scene (`persistent`); either works.

### The tool (question 4)

`get_game_state(node, options {keys, maxNodes, maxDepth, keep}, session)`, a `RuntimeTools` partial, so `batch_drive` offers it with no change (it reflects `RuntimeTools`' tools, ARCHITECTURE.md L123):

- `node`: read only the marked nodes under this one (a path, bare name or `%UniqueName`, as `inspect_node` takes); the whole tree when left out.
- `options.keys`: only these keys of each node's state, a key or a dotted path into it (`seats[0].hp`); every key when left out.
- `options.maxNodes`: 1 to 500, default 50; `options.maxDepth`: levels of nested values written, 1 to 8, default 4.
- `options.keep`: also hold the read in the session's snapshot store and return its `stateId` (question 5).

Result:

```
{frame, nodes: [{path, class, state} | {path, class, error}], total,
 omitted?: {count, paths},     // marked nodes past maxNodes or the size budget, the first 20 paths
 stateId?, hint?, errors?}
```

`frame` is `Engine.get_process_frames()` at the read, so two reads are ordered and a read inside a `frame_control` step is tied to its frame. `nodes` is in tree order. `hint`, when no node is marked, names the group and both method names and points to `snapshot_subtree` and `get_ui_elements` (question 3). A node's `error` says why it has no state: in the group with no state method, the method raised (a GDScript error from the error feed; a C# exception's type and message), or it returned a coroutine or a `Task`, which is not awaited, since a digest is one frame's read.

### Reading in one frame (question 7)

The bridge answers a new command `state` in a new module, `bridge/godot_mcp_state.gd` (the `State` child). In one handler, with no `await`: it takes `get_nodes_in_group("mcp_state")`, keeps those under `node` and outside the bridge, and for each one calls `_mcp_state()` when `has_method` finds it and converts the value with the JSON module's `to_json`, cutting at `maxDepth` itself (the JSON module's own depth counts built-in resources only, `bridge/godot_mcp_json.gd` L70-71). The nodes whose script is a C# script and whose GDScript-visible methods have no `_mcp_state` are collected by instance id, and, when the server's request carries the helper's `extension` path (it does for a project with a C# assembly, as every `dotnet` request does), the handler calls the helper's `state` op once, in the same frame, through the `Dotnet` module's loaded callable, and puts the helper's reply string into its own reply untouched: GDScript's JSON parser would turn every number into a float (`bridge/godot_mcp_dotnet.gd` L4-6). The server parses both halves, merges them by path into tree order, applies `keys`, and enforces the size budget.

The helper's `state` op (`{op: "state", ids, maxDepth}`) resolves each id with `GodotObject.InstanceFromId`, finds `_McpState` on the object's type (cached per type: an instance method with no parameters, any accessibility, declared on the game's type or a base up to the first GodotSharp type, as `cs_members` walks them), invokes it and writes the value with Core's `ValueWriter` through `GodotFormatter`, so a Godot object reads as `{"$node": path}` and a nested level past `maxDepth` as `"<depth limit: Type>"`, as `cs_get` writes them.

### Size bounds

- Each node's `state` is at most 4000 characters of JSON; a longer one comes back as `{valuePreview, valueLength}`, the shape every tool uses (TOOLS.md L47).
- The whole `nodes` list is at most 40000 characters: the nodes after the one that crosses it move to `omitted` with their paths, and `total` counts every marked node read.
- `maxNodes` counts marked nodes in tree order before anything is read, so a scene with 300 marked cards reads 50 and lists the rest in `omitted`: read fewer with `node` or `keys`, or raise `maxNodes`.
- `maxDepth` (default 4) keeps a returned record from writing its whole graph: delve's `GameState` holds the floor's rooms beside the party (GameState.cs L24-34), and the default cuts it where a game should have picked fields anyway. The skill tells games to return the few values an agent checks, plus the context needed to judge them (the satelliteoflove doc's advice, runtime-state.md L19), not a model object whole.

### Diffing between reads (question 5)

`options.keep` stores the read in the session's `SnapshotStore` beside `snapshot_subtree`'s captures, sharing its 16-entry limit and its id sequence, so `diff_snapshots` compares two reads, or a read with the live game when `afterId` is left out, with no new diff tool. A kept read is flattened first: each node's state becomes one property per leaf, keyed by its dotted path (`seats[1].hp`, `question`), so a changed hit point is one `changed` entry rather than the whole state; lists are keyed by index. The store's `Snapshot` record gains a kind, so a live re-read for `diff_snapshots` repeats a state read with the kept options instead of a subtree capture. Diffing a state read against a subtree snapshot is refused, naming both kinds.

### Tool class and annotations (question 6)

The state methods are game code, so `get_game_state` declares `Destructive = true` as `cs_get` does (a getter runs game code), and `ToolClasses.Overrides` gives it the `read` class as it gives `cs_get` (`src/GodotMcp.Server/Agents/ToolClasses.cs` L32), so the read-only agents that most need to stop reading screenshots (a playtester, an explorer) are swept the tool at install.

### Relation to project tools

[project-tools.md](./project-tools.md) marks methods an agent calls, with an attribute the game declares and the helper matches by name through `CustomAttributeData`. A digest is a different contract (one read, many nodes, keyed by node path, one frame, diffable), so it keeps its own convention. Question 1 (b) is the attribute form, which would share project-tools' name matching and the game's attribute file; a read-only game tool (`[GodotMcpTool(…, ReadOnly = true)]` returning a status) stays the way to expose a single computed answer that belongs to no node, such as opening-hand's `GetStatus`.

Over time is the timeline watch's job (MAIN.md L31: several properties and signals sampled over a window), not this tool's: delve's per-frame sampling script (DEVELOPMENT.md L70) is that item's evidence. The watch could later sample digest keys; nothing here depends on it.

## 4. Edges

- **Nothing opted in.** `{frame, nodes: [], total: 0, hint}`; the hint names the group, `_mcp_state` and `_McpState`, and points to `snapshot_subtree` and `get_ui_elements`. Not an error: a game that opts nothing in is the common case until its repo adopts the convention.
- **In the group, no method.** The node's entry carries `error` (question 3). A C# node whose method is misspelled or takes parameters reads the same, and the error names the method it looked for and the type it looked on.
- **Both names on one node.** A C# node with a Godot-visible `_mcp_state` and an `_McpState`: `_McpState` is read and the entry adds `warning`. A GDScript node with `_McpState` is not read by that name (the GDScript name is `_mcp_state`), and its error says so.
- **A C# game whose helper cannot load** (no helper build, a load failure the `Dotnet` module remembers): the GDScript nodes still read; each C# node's entry carries the load error, as `cs_members` would answer it. A C# node whose public `_mcp_state` returns a Godot Dictionary still reads through Godot's call.
- **The first read in a C# game** pays the helper's cold load when a C# node is marked; a C# project whose marked nodes are all GDScript never loads it, since the bridge calls the helper only for collected C# nodes.
- **A stale build.** The helper reads what the game loaded; the result says nothing about the disk's build (`run_csharp`'s MVID check is for compiling against the game, which this does not do).
- **A method that raises, awaits or runs long.** A GDScript error in `_mcp_state` gives the node an `error` from the error feed (`first_error_since` across the call, as `call_method` does) and the read goes on; a C# exception likewise, with its type and message; a coroutine or `Task` is an error, not awaited. A method that blocks the main thread blocks the read, and the hang watchdog reports it as it would a `cs_call`.
- **Side effects.** The convention says the method only reads; the server cannot check it. A method that changes state changes it at every read, including a `diff_snapshots` re-read.
- **Freed and moving nodes.** The read is one handler in one frame, so no node is freed partway; a node freed between a kept read and a live re-read is a `removed` path in the diff. Many instances of one scene (delve's cards) each read as their own path; a reordered hand (delve L77) shows as path changes only if the paths change, since nodes are keyed by path, not index.
- **Lists in a kept read.** Flattened by index, a list that gains an element at its head shows every later element as changed. A game that wants stable diffs keys such state by id (`{"seats": {"alex": {...}}}`); the skill says so.
- **Value shapes differ by language.** A GDScript Node value reads as its path string (the JSON module's rule), a C# one as `{"$node": path}` (the helper's), as `inspect_node` and `cs_get` differ today.
- **Paused games.** Answered while paused, so a read between `frame_control` steps sees the stepped frame. Holding delve's tree paused across calls drops its socket (DEVELOPMENT.md L78); that is the game's rule, not the tool's.
- **Attached and joined games.** Read as a run session is; a dormant game answers nothing until joined.
- **The bridge's own nodes** are never read, even when a game adds them to the group.
- **Big states.** Past 4000 characters a node's state is `{valuePreview, valueLength}`; past the 40000-character list budget later nodes move to `omitted`. A kept read stores the values as returned, the previews included, so a diff of a cut state compares previews: narrow it with `keys`.

## 6. Open questions for the user

1. **How a C# node opts in.** (a, recommended) A method named `_McpState`, any accessibility, no parameters, any return type, found by reflection in the helper and written by `ValueWriter`. How: one method per marked class; a record or anonymous type returns as it is. Worst case: a misspelled name reads as "in the group, no state method", caught only by the node's `error`. (b) An attribute the game declares itself, `[GodotMcpState]`, matched by name as project-tools' `GodotMcpToolAttribute` is, on fields, properties or a method, each marked member one key. How: `[GodotMcpState] private Vector2I playerCell;` with no method written. Worst case: marks scattered over many members of many classes, a second attribute file in each game, and the key set is whatever members happen to be marked. (c) Godot-visible only: a public `_McpState()` returning `Godot.Collections.Dictionary`, called by the bridge through Godot's own call, with no helper. How: the game builds the Dictionary by hand. Worst case: delve cannot return its `GameState` record or an anonymous type and converts every value to Variants itself, and whether an `internal` one is seen is the unverified row of section 3. **Ruled (user, 2026-09-30): (a), `_McpState` found by reflection.**
2. **Which nodes are read.** (a, recommended) The `mcp_state` group is the index; a member's state comes from its method. How: `get_nodes_in_group`, no tree walk, autoloads included. Worst case: a node with the method but not in the group is silently not read, until the agent learns the group is required. (b) The method alone, found by walking the tree (`has_method` on every node; for each C# node, the helper's per-type check). How: no group to add. Worst case: every read walks every node (delve's fight tree size is unmeasured) and every C# node's type goes to the helper, so the first read of a C# game loads it even when nothing is marked. (c) Either: group members, plus nodes found with the method by a walk. Worst case: the walk's cost of (b) on every read, for the convenience of skipping one `AddToGroup`. **Ruled (user, 2026-09-30): (a), the `mcp_state` group.**
3. **A group member with no state method, and no opt-in at all.** (a, recommended) No fallback: such a member's entry is an `error`, and a game with no marked node gets an empty list and a `hint` pointing to `snapshot_subtree` and `get_ui_elements`. Worst case: a game must write a method for each class it marks, and an unadopted game gets nothing from the tool. (b) Fall back to the node's script variables (GDScript's) and `[Export]` members (C#'s, what `inspect_node` lists by default). Worst case: a C# node's exports are layout knobs, not state, and they fill the budget. (c) satelliteoflove's visibility tier: with nothing marked, every visible CanvasItem and Node3D up to `maxNodes` with a fixed field set per class (position, rotation, velocity, animation, a Control's rect and text). Worst case: it duplicates `get_ui_elements` and `snapshot_subtree`, and a big scene's background nodes fill `maxNodes` before the ones that matter. **Ruled (user, 2026-09-30): (a), no fallback.**
4. **A new tool or an option on an existing one.** (a, recommended) A new tool, `get_game_state`, returning the data. How: one call, the values in its result. Worst case: one more tool in the list, beside `inspect_node` and `snapshot_subtree`, that an agent must learn to prefer. (b) An option on `snapshot_subtree` (`options.state: true`), read through `diff_snapshots`. Worst case: `snapshot_subtree` returns no data, so seeing the state at all takes a snapshot and a diff against an empty one, and its `properties`/`ignore` options mean nothing there. (c) An option on `inspect_node` (`options.state: true`). Worst case: one node a call, no one-frame read of several nodes, and `inspect_node` (`ReadOnly`, the `read` class) starts running game code behind an option. **Ruled (user, 2026-09-30): (a), a new `get_game_state` tool.**
5. **Diffing between reads.** (a, recommended) `options.keep` stores the read, flattened to dotted leaf keys, in the session's snapshot store, and `diff_snapshots` compares it with another read or re-reads the live game. How: `get_game_state {options: {keep: true}}`, act, `diff_snapshots {beforeId}`. Worst case: a list that gains a head element diffs as every element changed, and state reads share the 16-entry store with subtree snapshots. (b) (a) without flattening: each top-level key compared whole. Worst case: one hit point changing inside `seats` reports the whole seats list as the change. (c) No diffing: the agent compares two results itself. Worst case: every before-and-after check costs two full results in context, the thing the digest exists to avoid. **Ruled (user, 2026-09-30): (a), `keep` flattened into the snapshot store.**
6. **Annotation and tool class.** (a, recommended) `Destructive = true`, since state methods are game code, and a `ToolClasses` override to `read`, as `cs_get` has. How: the read-only agents are swept the tool; the hint tells clients it runs code. Worst case: a client that asks before every destructive tool asks before each read. (b) `ReadOnly = true` (the `read` class by attribute). Worst case: a client that auto-approves read-only tools runs game code unasked, and a state method with a side effect runs on every read. (c) `Destructive = true` with no override (the `edit-live` class). Worst case: playtesters and explorers, the agents that most need to stop reading screenshots, never get the tool. **Ruled (user, 2026-09-30): (a), destructive with a `read` override.**
7. **How the C# half is read.** (a, recommended) In the bridge's one `state` handler: the bridge reads the GDScript nodes and calls the helper's `state` op inline for the C# ones, in the same frame, passing its reply string through for the server to merge. How: one request, one frame. Worst case: the bridge's handler now depends on the `Dotnet` child's load path, so a helper load failure shows in a read that looked GDScript-only to the agent (as each C# node's `error`). (b) Two requests, the bridge's `state` for GDScript nodes and a `dotnet` helper op for C# ones, merged by the server. Worst case: the halves are read frames apart, so during an animation a digest mixes two moments, and a kept read diffs noise. (c) In a C# project the helper reads every marked node, calling a GDScript `_mcp_state` through Godot's `Call`; in a GDScript project the bridge does. Worst case: two walks and two value writers kept alike, and a GDScript Node value reads as `{"$node": path}` in one project and as a path string in another. **Ruled (user, 2026-09-30): (a), the helper called inline, one frame.**
8. **Waiting on a state key.** (a, recommended) Not in the first version: `get_game_state` runs as a `batch_drive` step, `diff_snapshots` checks a change, and `wait_for {expression}` (`node._mcp_state().hp == 0`) covers GDScript nodes. Worst case: a C# game that waits for a state value polls with repeated `get_game_state` calls, or keeps a Godot-visible member for `wait_for {property}`, as delve's `StartedBeatCount` is (DEVELOPMENT.md L75). (b) A `wait_for {node, state: "<key path>", equals}` condition and the matching `batch_drive` assertion, the state read every frame until met. Worst case: a C# node's wait calls the helper every frame (cost unmeasured), and a state method with a side effect runs once a frame. **Ruled (user, 2026-09-30): (b), a `wait_for {node, state, equals}` condition and its `batch_drive` assertion, in the first version.**

## 8. Spike results (step 1, 2026-09-30)

Godot `4.7.2.stable.mono.official`, a CsProbe copy driven by `run.ps1 drive` with a throwaway `state` helper op, a bridge command and a server tool; the machine was 74-100% busy with two other implementers, so the medians hold better than the maxima.

| C# method on a node | `has_method("_McpState")` / `call` | `has_method("_mcp_state")` |
|---|---|---|
| `public`, `internal` or `private` `_McpState()` returning `Godot.Collections.Dictionary` | true / the Dictionary | false |
| `public _mcp_state()` returning a Dictionary | false | true, `callv` works |
| `public` or `private` `_McpState()` returning a record | false / "Method not found" | false |

- **Names are verbatim**: a C# `_McpState` is never seen as `_mcp_state`, and a C# method literally named `_mcp_state` returning a Variant type is visible to Godot, so section 4's "both names on one node" can happen as written. Section 4's "public `_mcp_state`" needs no `public`.
- **The inline call works**: the bridge handler called the helper's Callable 25 times synchronously with `Engine.get_process_frames()` unchanged across every command, the state method calling Godot (`GetTree()`, `GetParent()`) and `GodotFormatter` resolving node paths from inside the handler, with no re-entrancy failure, deferred call or `pending` reply. One warm call costs 49-109 µs median on the GDScript side (max about 0.5 ms); the first `state` call after the helper loaded costs about 10 ms of JIT. A server round trip is frame-bound, about 16 ms at 60 Hz.
- **The reflection read works**: a `private` `_McpState` returning a record with a nested record, a `Node` and `List`s wrote through `ValueWriter` at depth 4 with `cs_get`'s depth cut (`<depth limit: SpikeSeat>`) and `{"$node": path}` (a node at the cut still writes as `$node`, the formatter running first). One node reads in about 49-78 µs warm; 50 nodes in about 2.4 ms helper-side (47 µs a node) plus 0.5 ms to hand the 26,737-character reply to GDScript. A side effect in the method repeats on every read, as section 4 says.
- Rulings 1 (a), 2 (a) and 7 (a) stand as written; step 2 can be briefed.

Step 2 details settled from the design and the existing tools (orchestrator, 2026-09-30):

- The hint reads `No node is in the mcp_state group. A GDScript node joins it and defines _mcp_state() returning a Dictionary; a C# node defines _McpState(). Until a game opts in, snapshot_subtree and get_ui_elements read the tree.`
- Per-node errors: `in the mcp_state group but has no _mcp_state method`; `_mcp_state raised: <the error feed's text>`; `_mcp_state returned a coroutine, which is not awaited`; a GDScript node with only `_McpState`: `defines _McpState, the C# name; a GDScript node defines _mcp_state`; a C# node before step 3: `a C# node's _McpState is read by the C# helper, which get_game_state does not call yet`.
- The GDScript depth cut writes `"<depth limit: Dictionary>"` or `"<depth limit: Array>"`, as the C# cut names its type; any Variant a method returns goes through the same walker, leaves through the bridge's `to_json`.
- The bridge slices by `maxNodes` in tree order and returns `total` and the first 20 paths it left out; the server adds the nodes the 40000-character budget moves, into one `omitted {count, paths}`.
- Validation texts copy the existing tools' (`maxDepth must be 1 to 8; got n.`, `maxNodes` as `snapshot_subtree`'s, an empty key as `CheckNames`'); the bridge call's timeout is `inspect_node`'s.
- `godot_mcp_inspect.gd`'s `_is_coroutine` becomes public `is_coroutine`, and State calls it; State reuses `call_now`'s error window per node.
- `RuntimeTools.State*.cs` gets its own `run.ps1` rule mapping it to `reads` (the general `RuntimeTools*.cs` rule selects every runtime group), and `StateTests` joins `reads`.

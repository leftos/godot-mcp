# Warm headless Godot and a scratch-step runner

Design draft for two plan items the user ruled share one design ([MAIN.md](./MAIN.md)): Wave 1's "a warm headless Godot serving many headless requests instead of one process per call", and the Track's "a headless runner for the projects' own scratch-scene steps (`AddStep`/`PlayStep`) with parsed results". Both keep one headless Godot serving several requests over the server's wire. Nothing here is decided until the open questions in section 7 are answered.

## 1. Problem

**One process per headless call.** Every headless tool (`validate`, `get_scene_file_tree`, `describe_class` without a session, every scene edit and `batch_scene_operations`) is one `godot --headless --path <p> --script headless/operations.gd -- <request file>` run (`HeadlessRunner.RunGodotAsync`), under the folder's prep lock, with its request and result as JSON files. The process does one op and quits (`headless/operations.gd` `_initialize`, L84-100). Measured on a busy machine for Wave 1 (MAIN.md, Wave 1): a headless op's process takes **0.72 s median around a 21 ms body**, so about 97% of an op is engine start and exit. Over the itest suite's **264 headless ops on 210 project folders** (one process per `--path`), keeping one process per folder would save **about 40 s** (the 264 - 210 = 54 ops that follow another op on the same folder, at about 0.72 s each). For agents in the game repos it is **about 0.7 s per consecutive op** on one project; the figure is InputProbe's (GDScript). A C# project's start also brings up the .NET runtime and loads the game assembly, so delve's and opening-hand's per-op start is likely longer: unmeasured (step 0 measures it).

**Scratch scenes run by hand-written scripts.** Both active games keep scratch scenes (delve-the-dungeon: 43 under `src/Delve.Client/Scratch/`; opening-hand: 10 under `src/Duel.Client/Scratch/`) whose root derives from a `ScratchScene` base (delve `Scripts/Diagnostics/ScratchScene.cs`, opening-hand the same file with small differences). A scene adds named steps with `AddStep(name, play)`; `PlayStep(index)`, `GetStepCount()`, `GetStepName(index)` and `GetStatus()` are public (delve L104-147; opening-hand L149-192). `--scratch-auto=<seconds>` plays every step on a `Timer` that many seconds apart, prints `[scratch] played <n> step(s)` and quits 0; a step that throws prints `[scratch] step <i>/<n> '<name>' threw: …` and quits 1 (delve L410-491; opening-hand L223-303). Each game has a `tools/scratch/Run-Scratches.ps1` that launches every scene headless through `tools/gate.ps1`, one Godot per scene, and reads a verdict off the log:

- **The verdict is a text search.** Green is gate exit 0, a `played` line, and no line matching `ERROR|SCRIPT ERROR|Exception|WARNING: ObjectDB`; "no steps" is exit 0 with neither. The two scripts already disagree: opening-hand matches case-sensitively and skips the project's own `WARNING: [` lines (its L125-127), delve matches case-insensitively with `Select-String`'s default (its L272-273), so a delve `[scratch]` note containing "error" turns a scene red.
- **Tables of seconds.** delve's `$pace` gives 28 scenes their step seconds with a comment each (L71-145) and `$ceilings` gives 4 a longer ceiling than 180 s (L158-167); opening-hand has one ceiling row (L78-82). A ceiling is the scene's steps times its pace plus slack, worked out by hand from a step count the script cannot see.
- **Per-scene state the runner reimplements.** delve refuses to start when the client assembly is older than a source (`Assert-ClientBuilt`, L176-204), which the server's prep already does; delve runs 4 at once on `--temp-profile` so logs do not collide (L245-250), and replays a scene red beside others once alone (L347-377).
- **Nothing per step.** The log carries the `played` total and the thrower's line; a step that fails later, from a timer it started, prints with `GD.PrintErr` (delve `TrayScratch.cs` L1070, L1172) and is found only by the text search. Which step printed what is not recorded.

## 2. Proposed design: the warm host

A **warm host** is one long-lived `godot --headless --path <p> --script headless/host.gd` process per project folder, which dials the server's listener as a bridge does and answers `headless` requests, each the same `{op, params}` a request file carries today, until it is stopped. `HeadlessRunner` keeps its contract (the prep lock, `ClearFolder`, prep, the ceiling, the result and failure texts); only `RunGodotAsync` changes, from starting a process to sending a request to the folder's host.

### Process lifetime and keying

- **One host per project folder**, keyed by `ProjectPaths.Normalise(projectDir)`, held in a `HeadlessHosts` pool on the `SessionRegistry` beside its prep locks. A process cannot serve another folder: `--path` is read once in `Main::setup` and the project's settings are loaded then (section 4).
- **Started by the first request** on a folder, under that folder's prep lock (after `ClearFolder` and prep, as today): `godot --headless --path <p> --script <abs host.gd>` with `GODOT_MCP_OFF=1` (as every headless run, so a live session's bridge autoload frees itself), and the host's own `GODOT_MCP_HOST_PORT` and `GODOT_MCP_HOST_TOKEN`, names the bridge never reads. It joins `OwnWork` and is started through `ChildProcesses.Start` with stdin closed (DEVELOPMENT.md footgun on inherited stdin). `--path` makes the project the process's working directory whatever folder it starts from (section 9), so a live host holds its folder against a rename or delete: `stop_project` stops a folder's host (section 9), and `SessionRegistry.Shutdown` stops every host and waits for its handle.
- **C# projects stay cold** (section 9): a project whose `PrepScan.FindCsproj(projectDir).Kind` is not `CsprojKind.None` runs one process per call as today, and only GDScript-only projects get a host.
- **Handshake** as a run's: the host's `_initialize` frees the autoloads (as `operations.gd` does, L85-86), then dials and sends `{type: "hello", token, projectPath, pid, host: "headless"}`; `BridgeListener.AcceptBridgeAsync` routes it by token to the pool's waiter with a `HandshakeExpectation`, 15 s of load-adjusted time as a launch's (`GodotSession.HandshakeTimeout`). A host that does not say hello in time is killed and the request fails as a start failure (question 3).
- **Its log** is `.godot/godot-mcp/headless.log` for its whole life (today's per-run log, now appended), and the host prints `[godot-mcp] request <id> <op>` before each request, so a failure quotes the log from its own request's marker, never an earlier request's lines.
- **Listed.** `list_sessions` gains `headlessHosts: [{projectPath, pid, startedAt, requests, idleSeconds}]`, so an agent sees what holds a folder (question 6 on ending one).

### Request framing over the existing wire

The host speaks the wire the bridge speaks (DECISIONS.md, Wire): 4-byte big-endian length plus UTF-8 JSON, every request with an id, served by one `BridgeConnection` per host. Commands:

| Command | Params | Reply |
|---|---|---|
| `headless` | `{op, params}` exactly as `RunGodotAsync` builds them today (`build`, `buildConfiguration`, `buildErrors` added) | `{id, ok: true, result: {ok, result?, error?, engineErrors}}`: `result` is the object today's result file holds (`BridgeConnection` hands back `reply["result"]`, `Wire/BridgeConnection.cs`), so `ReadResult` and `FailureMessage` read it unchanged |
| `ping` | — | `{id, ok: true}` (the hang watchdog's probe) |
| `shutdown` | — | `{id, ok: true}`, then the host quits |

- **The request and result files go.** `.godot/godot-mcp/headless/<guid>.request.json` and `.result.json` are no longer written; the ids replace the guids. A reply for a timed-out id is dropped (Non-negotiables).
- **Numbers.** GDScript's JSON parser reads every number as a float (DEVELOPMENT.md footgun), so the host echoes `int(id)` as the bridge does.
- **engineErrors per request.** The host's `ErrorLog` (today's `operations.gd` class) keeps its entries; each request answers the entries logged from its own start on, plus the **start slice**, the entries logged while the host started (an autoload's `_init` error, a project setting), so each reply holds what a cold run's `_log.since(0)` holds today (L98). `validate` groups the start slice as it does today (`_validate`, L182-191). The start slice is sent on every request, as a cold run reports it on every run.
- **One request at a time.** The host reads a frame, runs the op to its end on the main thread, writes the reply, reads the next. Requests reach it one at a time anyway (the prep lock, below).
- **Between requests** the host's `_process` returns false and polls the socket; the headless display server never draws, so the main loop sleeps about 6.9 ms an iteration (section 4) and an idle host costs little CPU (to measure in step 0).

### Idle shutdown

A host idle for the **idle limit** (question 2: 5 minutes recommended) is sent `shutdown`, given 3 s, then killed with its tree; the pool also keeps at most **4 hosts**, and a fifth folder's first request stops the least recently used idle one first (a busy host is never stopped for it). Idle is wall time, like the other waits that are not ceilings (ARCHITECTURE.md, Load-adjusted time: Wall time), counted from the host's last reply. `SessionRegistry.Shutdown`, which is synchronous, stops every host and waits on each process handle with `Process.WaitForExit` until Windows signals it (DEVELOPMENT.md footgun "A killed process reports exited before it lets go of its files"), so the itests' `SessionHarness.DisposeAsync` frees each fixture folder before its `TempDirectory` deletes it.

### Crash, stall and restart

- **A request passes its ceiling** (60 s, 120 s for a batch, load-adjusted, with the backstop): the host is killed with its tree and dropped from the pool; the error keeps today's text, `The headless <op> run on <project> did not finish (<detail>)`, with the log path. A GDScript op cannot be interrupted mid-call, so there is no `cancel`.
- **A stall** (no CPU in the host's tree for 120 s during a request; its socket carries no output between replies, so `StallWatch` counts CPU and log growth as `ToolProcess` does) ends the same way.
- **The host exits mid-request** (a crash, a script calling `quit()`): the request fails with `The headless <op> run on <project> ended (Godot exited <code>) before it answered`, and the log from the request's marker, as today's "wrote no result"; the host is dropped.
- **A connection that closes while idle**, or a host process that exits while idle, is dropped quietly (logged at Debug).
- **The next request on the folder starts a fresh host.** No request is retried (question 3).

### What invalidates a warm host

A host is stopped, and the request that found it stale starts a fresh one, when anything it read at start or keeps in memory may differ from the disk:

- **A rebuild** does not arise: a C# project stays cold (section 9), so no host ever loads an assembly.
- **An import.** The UID cache and the global class list are read once at start (section 4), and an import rewrites both and `.godot/imported/`. Prep stops the folder's host before its `--import` runs (the host is idle then: prep holds the lock), and the fingerprint below catches an editor's import.
- **A file change under the project.** Before each request the server compares the folder's **fingerprint** (each file's path, size and write time, under the project minus `.git/` and folders holding `.gdignore`, plus `.godot/uid_cache.bin`, `.godot/global_script_class_cache.cfg` and `.godot/imported/`) with the one taken after the host's last reply; any difference stops the host. Taking it after each reply absorbs the host's own writes (a saved `.tscn`, a `.uid` file, its uid-cache append), so consecutive tool edits stay warm and an edit by anything else (the agent's Write tool, the editor, another server's host) costs one cold start. This is question 1's recommended option; the finer rule (keep the host across `.tscn` and `.tres` edits, relying on the resource cache being weak) is its option (b).
- **The prep lock.** Every request holds the folder's prep lock from before prep until its reply, as `HeadlessRunner.RunAsync` holds it through the run today, so a request never overlaps a launch's prep, an import, an arm's or attach's override write, or another request on the folder. The host itself lives outside the lock.
- **Concurrent requests.** Two tool calls on one folder at once queue on the prep lock, as today; calls on different folders run on their own hosts at once. Two servers on one folder each keep their own host; each sees the other's writes through the fingerprint and restarts, so neither reads a scene the other has changed. A `batch_scene_operations` is one request.
- **Not invalidators**: a live session starting or stopping on the folder, or its `override.cfg` coming and going (the host read the file at start and freed the bridge autoload it named; `ClearFolder` runs before each host start, not before each request); a request's own `prepare: never`.

## 3. Scratch steps on the same design

### Why the scratch runner is a headless game, not the edit host

A scratch scene needs the game running as the game: its autoloads (delve's `Launch` reads the command line and picks a temporary profile for a scene under `Scratch/`, `Launch.cs` L49, L79, L113-124), the scene as the main scene, the game's C# assembly, and the user arguments after `--`. The edit host frees the autoloads before they enter the tree and has no main scene (`operations.gd` L84-86), so it cannot play a scratch. What the two share is the rest of this design: a headless Godot per project folder that dials the server and serves many id'd requests over the wire, started under the prep lock after prep, stopped at the end, killed at a ceiling or stall, its log sliced per request, its crash reported with that slice.

So a scratch scene plays in a **headless game session**: `run_project`'s launch path (`GodotSession.LaunchAsync`: prep, the marked override, the bridge, the hello) with `--headless` in its engine arguments, the scene as `scene`, and the profile's user arguments; its session is named `<folder>.scratch-<scene>` (cut to the name rule as `preview_scene`'s is) and takes the folder's live override settings as `preview_scene` does. The bridge already runs headless: it never goes dormant there (`godot_mcp_dormant.gd` L133-143) and leaves the window alone (`godot_mcp_window.gd` L53, L80). The requests it serves are `call_method` and `wait_for`, already on the wire.

### Who walks the steps

Recommended (question 4): **the server walks them**, the scene's own clock left off (no `--scratch-auto`):

1. Launch; read `GetStepCount()` and each `GetStepName(i)` with `call_method` on the scene root (`/root/<Scene>`), refusing a root without the four methods (the **scratch protocol**: `PlayStep(int)`, `GetStepCount()`, `GetStepName(int)`, `GetStatus()`).
2. For each step: mark the session's error feed and its stdout and stderr line counts, `call_method PlayStep [i]`, then `wait_for {gameMs: pace x 1000}` (game time from the bridge's `process_frame`, as the scene's `Timer` counts it); then read `GetStatus()`.
3. The step failed when the `call_method` reported an error or the error feed holds an error logged since the mark; a C# exception thrown by a step reaches the feed, since Godot's C# call bridge catches it and pushes it as an error (section 4). The run stops at the first failed step, as `--scratch-auto` stops.
4. After the last step and one more pace, `stop_project` (a graceful `shutdown`, so the process runs its exit and prints any `ObjectDB … leaked at exit` warning to stderr, section 4), then read the stderr lines since the last step.

The scene's ceiling is computed, not tabled: the launch's own handshake, then `steps x (pace + 10 s)` of load-adjusted time as `wait_for`'s allowances are; a run past it is stopped and reported `killed`. delve's `$ceilings` table goes.

### What "parsed results" means

From the games' own output, per scene:

```
{scene, verdict: "green" | "red" | "no-steps" | "known" | "known-now-green" | "killed",
 steps: {played, total}, pace, seconds, session,
 failedAt?: {index, name, error, status},          // the first failed step
 steps?: [{index, name, ok, gameMs, status,          // with options.details, or for a red scene
           errors: [{message, file, line}],          // the error feed since the step's mark
           lines: [...]}],                           // stdout and stderr lines in the step's window that match the project's patterns
 exit: {code, leaked?: "<n> ObjectDB instances"},    // after the stop
 known?: "<reason>"}
```

- **status** is the second line of `GetStatus()`, what the scene noted with `SetNote` (the label's first line is the step).
- **errors** come from the error feed: engine errors, `push_error`, C# exceptions, each with file and line; never a text search.
- **lines** are the stdout and stderr lines of the step's window that match the project's patterns (question 7): delve's `GD.PrintErr` failures from timers a step started, which reach stderr only (section 4), land under the step that was up when they printed. `[scratch] …` notes are kept for a red scene, so the reader sees what the scene said before it failed.
- **verdict**: `green` when every step played with no error and no matching line and the process exited 0 with no leak; `no-steps` when `GetStepCount()` is 0; `red` otherwise, with `failedAt` naming the first step that failed and why; `known` and `known-now-green` as the scripts' `$Known` tables work (a known scene that plays green is red until its row goes); `killed` at the ceiling or a stall.
- **The tool's result** is `{passed, green, red, known, noSteps, killed, scenes: [...]}`, one short object a scene, the step list only for a red scene or with `options.details` (compact output).

### The tool and its settings

A new tool, `run_scratches(projectPath, scenes, options {pace, parallel, userArgs, prepare, details})`: `scenes` a list of scene names or `res://` paths, left out for every scene in the profile's scratch folder. The per-scene settings live in the project's `godot-mcp.json` (question 5): `scratch: {folder, userArgs, pace: {<Scene>: seconds}, known: {<Scene>: reason}, parallel, patterns}`, parsed strictly as the rest of the profile. Scenes run `parallel` at a time (default 1); with more than one, a scene red beside others is played once more alone and reported `alone` when it then passes, as delve's script does. Prep runs once for the run, so a stale client assembly is built, not refused. The runner is agent-native by construction: every step it takes is a tool call an agent can make itself (`run_project`, `call_method`, `wait_for`, `stop_project`), and its result says which session each scene ran in.

## 5. Edges

- **The start slice repeats.** An autoload `_init` error is reported on every request of a host, as it is on every cold run today; `validate` groups it under its file each time.
- **A scene the host saved, then edited outside.** The fingerprint after the host's reply includes the saved file; the outside edit changes its write time or size, so the next request starts cold. A write landing during the request, between the host's save and the fingerprint, is absorbed and missed: the host could then read a stale `.gd` (the GDScript cache is strong). Rare (an agent's edit racing its own tool call on the same folder); the self-check below narrows it to scripts.
- **A held resource.** After each reply the host checks `ResourceLoader.has_cached` for every `res://` path the request named (scene, script, texture, new path); a path still cached means something held it, and the host answers with `stale: true`, which the server treats as an invalidation. It keeps a leak in `headless/` from turning into a stale read.
- **The folder is renamed or deleted** while a host is idle: refused, since the host holds it as its working directory (section 9). `stop_project` with the folder stops its host first; the idle limit and the server's exit stop it too.
- **Two servers.** Each server has its own pool; hosts on one folder from two servers are two processes. Their prep locks are per server (in memory), as today.
- **A host crashing at start** (a broken autoload, a Godot that cannot start): no hello within 15 s, killed, and the request fails naming the log (question 3).
- **The server exits uncleanly.** A host whose connection closes quits itself (its `_process` sees the socket gone), so a killed server leaves no host running; the job object ends it too.
- **Scratch: a scene that reads its own command line.** A scene that looks for `--scratch-auto` to change what it does (opening-hand's `IsScriptedRun`, `ScratchScene.cs` L81) sees none when the server walks the steps; `options.userArgs` or the profile's can pass one, and the scene's own clock then plays too, so the runner refuses `--scratch-auto` in user arguments.
- **Scratch: a step that measures wall time.** The server's `gameMs` wait counts game time, as the scene's `Timer` does; a step reading `Time.GetTicksMsec()` sees the same pacing under an idle machine and a longer one under load (the frames stretch); delve's "red beside others, green alone" rule stays.
- **Scratch: a step whose failure prints only.** A `GD.PrintErr` without a throw is found through the project's patterns on the step's lines; with no pattern it is kept in `lines` but does not fail the step.
- **Scratch: a scene with no scratch protocol.** Refused before any step, naming the missing methods and the root it looked at.
- **Scratch: sessions on one folder.** Parallel scenes are several headless sessions on one folder, allowed today; an import is refused while they run (prep's rule), which is why prep runs once before the first scene.

## 6. Where the code goes and the tests

- **GDScript.** `headless/operations.gd` is split so its request handling is a library: a static `run_request(op, params, log, start) -> Dictionary` (dispatch, the reply, `engineErrors` from `start` plus the start slice), which the cold entry point (`_initialize`, kept for step 1's proof) and the new `headless/host.gd` both call. `host.gd` is a `SceneTree` script: `_init` registers the logger as today, `_initialize` frees the autoloads, notes the start slice and dials; `_process` connects, sends the hello, reads frames and runs `headless`, `ping` and `shutdown`, returns false while the socket lives and true once it is gone. Frame reading and writing are small enough to copy from the bridge's `_read_frames` and `_send`; if gdlint's size or duplicate rules object, they move to a shared `bridge/godot_mcp_frames.gd` both load.
- **Server.** `src/GodotMcp.Server/Session/HeadlessHost.cs` (one host: process, connection, log marker, the request with its ceiling and stall watch, stop), `HeadlessHosts.cs` (the pool on `SessionRegistry`: keying, the idle timer on the registry's `TimeProvider`, the cap, invalidation reasons, `Shutdown`), `ProjectFingerprint.cs` (the snapshot and compare). `HeadlessRunner.RunGodotAsync` sends through the pool; `ProjectPrep` tells the pool when it built or before it imports. `ProjectTools.ListSessions` adds `headlessHosts`. `run_scratches` goes in a new `Tools/ScratchTools.cs` (its own class, as `PreviewTools`, so `batch_drive` never offers it) over a `Session/ScratchRun.cs` that walks one scene and `ScratchVerdict.cs` that turns a scene's steps, feed entries and lines into its verdict; `ProjectProfile` gains the `scratch` section.
- **Unit tests** (`tests/GodotMcp.Tests`): `ProjectFingerprintTests` (a changed file, an added and a deleted one, the host's own write absorbed, `.gdignore` and `.git/` left out, `.godot/imported` counted); `HeadlessHostsTests` on `FakeTimeProvider` and a fake host dialling over real loopback as `FakeBridge` does (the idle limit, the cap stopping the least recently used idle host and never a busy one, a build or import invalidating, a crash mid-request quoting the log from its marker, a stale self-check, `Shutdown` waiting on the process); `ScratchVerdictTests` (each verdict, the first failed step, a pattern line under the step it printed in, known and known-now-green, the leak line); `ProjectProfileTests` for the `scratch` section's strict parse; `ScratchValidationTests` for the tool's refusals.
- **GDScript tests** (`tests/bridge/test_operations.gd`, a new `test_host.gd`): `run_request` answering as the cold run did; the start slice and per-request slices; frame parsing; `stale` from the self-check.
- **Integration tests.** Every existing headless class (`HeadlessTests`, `HeadlessSceneTests`, `HeadlessPropertyTests`, `HeadlessSignalTests`, `HeadlessMeshTests`, `HeadlessBatchTests`) runs through hosts unchanged, which is the proof of no behaviour change. A new `WarmHeadlessTests`: two ops on one folder answered by one pid; a scene edited outside between them answered by a new pid and read fresh; a C# rebuild between them restarting the host and the new method seen; an import restarting it; a host killed mid-request and the next request served; the folder deleted after the harness disposes. A new `ScratchRunnerTests` on a scratch fixture: a GDScript scene in InputProbe implementing the scratch protocol (green, a step that pushes an error, a step whose timer prints a matching line a step later, no steps) and a C# one in CsProbe (a step that throws, reported with its exception), in the `timing` lane since it paces by game time (DEVELOPMENT.md footgun on lanes), heavy for its C# build. Each new class goes into a `$itestGroups` group and `$itestRules` maps `headless/host.gd` and the new server files.
- **Docs, in each landing's commit**: ARCHITECTURE.md (the Headless row, a Session lifecycle entry for hosts, the `run_scratches` row, the Load-adjusted time lists), TOOLS.md and `skills/godot-mcp/SKILL.md` (`run_scratches`, `headlessHosts`, a warm host's restart rules), README.md (the new tool), the glossary (**Warm host**, **Fingerprint**, **Start slice**, **Scratch scene**, **Scratch protocol**, **Pace**; the "Headless tool" and "Headless run" entries rewritten for hosts), DEVELOPMENT.md (the test classes; a footgun if step 0 finds a held handle), CHANGELOG.md bullets under `## Unreleased`.

## 7. Open questions for the user

1. **What restarts a warm host after a file changes.** (a, recommended) Any change under the project the host did not make: the fingerprint (every file's path, size and write time, minus `.git/` and `.gdignore`d folders, plus the `.godot` caches) is compared before each request and retaken after each reply, and any difference restarts the host; plus the has-cached self-check. How it works: correctness never rests on how Godot's caches behave, only on stat calls. Worst case: an agent that alternates its own Write edits with headless calls gets a cold start on each, today's cost, and a project with many files pays a stat walk per request (unmeasured; step 0 measures delve's). (b) Restart only for what the process cannot reload: a `.gd`, `project.godot`, the C# assembly or the `.godot` caches; a `.tscn`, `.tres` or asset edited outside keeps the host, trusting the weak resource cache and the self-check. Worst case: a resource something in `headless/` still holds is read stale, and an edit saves over the agent's outside change, data lost with no error. (c) A `FileSystemWatcher` on the folder. Worst case: its directory handle blocks a delete or rename of the folder (a worktree removal, a test's temp folder), and a buffer overflow drops events silently. **Ruled (user, 2026-09-30): (a), any change the host did not make.**
2. **How long an idle host lives.** (a, recommended) 5 minutes of wall time since its last reply, at most 4 hosts, the least recently used idle one stopped for a fifth. How it works: a working agent's consecutive edits stay warm, and a folder is let go within minutes. Worst case: an agent that pauses 6 minutes between two edits pays one cold start, and five folders worked in turn keep restarting one. (b) Until the server exits, no cap. Worst case: the itest suite's 210 folders would leave hosts running (each test's registry stops its own, but a long agent session across many worktrees keeps a host each, holding memory, unmeasured). (c) 30 seconds. Worst case: most agent pauses between tool calls are longer than that (unmeasured), so the game repos gain little beyond `batch_scene_operations`. **Ruled (user, 2026-09-30): (a), 5 minutes idle, at most 4 hosts.**
3. **When a host fails.** (a, recommended) The call that met the failure fails with the log from its request's marker, the host is dropped, and the next call starts a fresh one; nothing is retried, and a host that cannot start fails its request as a cold run that wrote no result does today. Worst case: a crash that a fresh start would not repeat costs the agent one repeated call. (b) Retry once on a fresh host for the read ops (`validate`, `get_scene_file_tree`, `get_node_properties`, `get_node_signals`, `describe_class`), never for an edit. Worst case: a read that crashes the engine every time takes twice as long to fail, and the code has two paths per op. (c) Retry every op once. Worst case: an edit that saved and then crashed before answering is applied twice (a `duplicate_node` makes two copies). **Ruled (user, 2026-09-30): (a), the call fails, no retry.**
4. **Who walks a scratch scene's steps.** (a, recommended) The server, in a headless game session: `call_method PlayStep` then `wait_for {gameMs}` per step, the error feed and the output lines marked per step, the scene's own clock left off. Worst case: a scene whose steps rely on being played from its own `Timer` callback (the same point in the frame, or a behaviour keyed on `--scratch-auto`) plays differently than under the scripts, and the first run of each scene may need its pace or its code adjusted. (b) The scene's own `--scratch-auto` in a headless run with no bridge, the server parsing the log; each game adds one `[scratch] step <i>/<n> '<name>'` line as a step starts, so lines split per step. Worst case: failures that only log (an engine error with no throw) are found by text, as today, and the verdict depends on each game's log format. (c) Both: `--scratch-auto` with the bridge attached, the server only watching the feed. Worst case: the step boundaries come from log lines while the errors come from the feed, two clocks a frame apart, so an error printed at a step's edge lands under the wrong step. **Ruled (user, 2026-09-30): (a), the server, in a headless game session.**
5. **Where a scene's pace, known reason and patterns live.** (a, recommended) The project's `godot-mcp.json`, a `scratch` section parsed strictly with the rest of the profile, the reasons kept as strings beside each entry. Worst case: the comments that explain each pace today (delve's `$pace` has one a scene) become JSON strings or are lost, since JSON has no comments. (b) Arguments to each `run_scratches` call. Worst case: every agent must know delve's 28 paces, and a scene run without its pace goes red. (c) In the scene: an optional `GetPace()` on the scratch root that the runner calls. Worst case: a game change for a runner setting, in C#, and `known` still needs a home outside the scene. **Ruled (user, 2026-09-30): (a), a strict scratch section in godot-mcp.json.**
6. **How an agent ends a warm host.** (a, recommended) `list_sessions` lists hosts, and a host is stopped by the idle limit, an invalidation or the server's exit only; no tool stops one. Worst case: an agent that must remove a worktree while a host is idle there waits up to the idle limit or restarts its server. (b) A `stop_headless_host(projectPath)` tool. Worst case: one more tool for a rare need, and a stop racing a request fails that request. (c) `stop_project` accepts a host by a `<folder>.headless` name. Worst case: a session-shaped name for something that is not a session, and `get_debug_output` and the other session tools then have to refuse it. **Ruled (user, 2026-09-30): (a), no tool stops a host; reopened by the spike (section 9): `stop_project` stops a folder's host.**
7. **What turns a scratch step red besides a throw and an engine error.** (a, recommended) Also a stdout or stderr line in the step's window matching the project's `scratch.patterns` (a list of regexes, case-sensitive, anchored as written), default `^SCRIPT ERROR|^ERROR:|ObjectDB instances? (was|were) leaked` so a project with none set still catches the leak and Godot's own error lines. Worst case: a pattern too wide (delve's case-insensitive `ERROR` today) turns a note red, and a pattern too narrow misses a `GD.PrintErr` failure, each until the profile is fixed. (b) The error feed and the exit code only. Worst case: delve's steps that fail by `GD.PrintErr` from a timer (`TrayScratch.cs` L1070, L1172) pass green. (c) Each game's current text rule ported as is. Worst case: the two games keep disagreeing (case, the `WARNING: [` skip), and a line counts against no step in particular. **Ruled (user, 2026-09-30): (a), the profile's scratch.patterns with the default set.**
8. **Does one game session play several scratch scenes.** (a, recommended) No: one fresh headless game per scene, `parallel` at a time. Worst case: a launch per scene (1.63 s median to its hello for InputProbe, MAIN.md Wave 1; more for delve's client, unmeasured) on top of the paced steps, a small share of a scene's time at 0.5 s or more a step. (b) One game per folder reused with `change_scene_to_file`, a host like the edit host. Worst case: autoloads, statics, delve's temporary profile and the command line stay the first scene's (section 4), so a scene can pass or fail because of the scene before it, and leaks at exit are one total for the whole run. **Ruled (user, 2026-09-30): (a), a fresh game per scene.**

What it contradicts, and the rulings on it:

- **The host holds its folder.** `--path` sets the process's working directory to the project (4.7.2 `main/main.cpp` L1768-1772), whatever folder it starts from, so renaming an idle host's folder is refused (WinError 32); section 2's working-directory claim and section 5's "the host does not hold it" are wrong. **Ruled (user, 2026-09-30): question 6 reopens: `stop_project` stops a folder's host, and the worktree-removal recipe names it.**
- **Warm C# hosts log spurious engine errors** (the soak above). **Ruled (user, 2026-09-30): a C# project keeps one process per call in the first version; the warm host serves GDScript-only projects until a follow-up spike finds the cause.**
- **Idle CPU is not small everywhere.** **Ruled (user, 2026-09-30): the host sets `Engine.max_fps = 30` while idle and lifts it for a request.**
- **The has-cached self-check** would fire after every op that names a script: scenes are never cached after a reply, but the GDScript cache keeps a `.gd` after `attach_script`. The check skips script paths.
- The leak line reads `1 ObjectDB instance was leaked at exit` / `2 ObjectDB instances were leaked at exit`; question 7's default pattern matches both.
- Confirmed: no `frame_post_draw` headless (0 frames drawn); the leak warning reaches stderr after a `shutdown` and a `stop_project`; ~145 idle iterations a second; nothing in `headless/` holds a scene.
- Step 1 can be briefed as written: the spike's host needed no change to `operations.gd` beyond cutting the error log back to the entries logged at start before each request (a `reset_to(start)` on the error log, or `run_request` taking `start`), which reproduced a cold run's `engineErrors` byte for byte.

# Project tools: a game's own cheat and debug commands

Design draft for the plan item "Project-defined tools, so an agent finds and calls a game's own cheat and debug commands" ([MAIN.md](./MAIN.md) L29, the Track), from idea 13 of the [survey](../research/2026-09-29-godot-mcp-survey.md) (L160-163). Nothing here is decided until the open questions in section 6 are answered.

## 1. Problem

A game's cheats and debug hooks are ordinary C# methods today, and an agent reaches them through `call_method`, `cs_call`, `run_csharp` or `run_script` like any other member. The survey's fit note (L163) already names the gap: "`call_method` and `run_script` already reach any method; what is missing is discovery." The two C# games driven through the server show what that costs.

**delve-the-dungeon.** Its cheats are public methods of `NetClient` (`src/Delve.Client/Scripts/Net/NetClient.cs` L37, a `Node`), the `Net` autoload (`src/Delve.Client/project.godot` L24: `Net="*res://Scripts/Net/NetClient.cs"`): `ForceEnemyAim(int enemy, int seat)` L759, `ForceAllEnemiesAim` L773, `DownPartyMember(int seat)` L787, `FellPartyMember` L800, `PutPartyMemberFirst` L813, `SetHp(bool enemy, int index, int hp)` L855, `SetMaxHp` L871, `SetSpeed` L887, `SetStatus(bool enemy, int index, string kind, int magnitude, int turns)` L905, `ClearStatus` L923, `JumpToRoom(int x, int y)` L937, `JumpToRoomOfKind(string kind)` L951, `JumpToEncounter` L983, `WinFight` L995, `StillBots` L1000, `SetTrapped` L1021, `OpenBoard` L1031, `GrantXp` L1054, `SetLevel` L1067, `SetAbilityLevel` L1084, `TeachAbility` L1106, `TeachAbilityAt` L1131, and the `internal` `SetRewardChoice` L1164. The same class carries non-cheat public members an agent must not mistake for cheats: `Send` L636, `Submit(Seat?, GameCommand)` L666, `IsInFlight` L1224, `IsAnythingInFlight` L1227. The game's own dev console (`src/Delve.Client/Scripts/Components/DevConsole.cs` L7-14) sends "through the same `NetClient` methods a scripted drive calls", with a help list of every cheat, its arguments and when a server takes it (`DevConsoleText.cs` L260-305).

- **Discovery is prose.** An agent learns the cheats from one long paragraph of delve's `docs/DEVELOPMENT.md` (L67, with more in L68-70, L73, L77-78), and from each method's XML doc, which tells a driven session to reach it "through an MCP `run_script` call, `scene_tree.root.get_node("Net").ForceEnemyAim(0, 1)`" (NetClient.cs L748-750), while DEVELOPMENT.md L67 says "a cheat is one `call_method` on the `Net` autoload with no script". `cs_members {node: "Net"}` lists every member of `NetClient` with its signature (TOOLS.md L270), cheats and plumbing alike, with no description and no word on when each is taken ("from the map", "while the party plans"). The game keeps a list of what a drive could not do so a cheat can be added (DEVELOPMENT.md L80): the set grows, and each addition means a prose edit agents must re-read.
- **Argument shapes are guessed.** `SetHp(true, 0, 6)` is three positional values whose meaning (enemy or party member, index, hit points) lives in the XML doc; `SetStatus`'s magnitude is in tenths, and DEVELOPMENT.md L67 records that "`1` made the party take ×0.1"; a condition or room kind is a case-sensitive name matched with `StringComparison.Ordinal` (NetClient.cs L1193-1195, L1211-1219) that no listing enumerates; `SetHp` alone refuses a number above the maximum (L67).
- **Errors arrive late or sideways.** A cheat returns `true` when "the ask went to the server" (NetClient.cs L657-661), not when the server took it; the server's refusal comes later as a notice (the console waits a frame and prints `refused:`, DevConsole.cs L506-522). A cheat sent while another is in flight is skipped with only a notice (`SubmitCheat`, NetClient.cs L1173-1185), which is why DEVELOPMENT.md L67 prescribes "about 45 frames between them, `wait_for {condition: {frames: 45}}` between the calls". A bad name throws `ArgumentOutOfRangeException` (L1211-1219), which through `call_method` is a C# exception logged by the engine and read back from `errors` beside a null `value` (TOOLS.md L266).

**opening-hand.** It has no cheats; its debug surface is the scratch scenes' base class `ScratchScene` (`src/Duel.Client/Scripts/Diagnostics/ScratchScene.cs`): `PlayStep(int index)` L149, `GetStepCount()` L175, `GetStepName(int index)` L181, `GetStatus()` L192, public on purpose because "`has_method` and `call` see a C# method only while it is public" (L17-20). Its only autoload is `App` (`src/Duel.Client/project.godot` L22), so these live on the current scene's root, not an autoload. Agents drive them with `call_method {node: "/root/<Scratch>", method: "PlayStep", args: [i]}` (its `docs/DEVELOPMENT.md` L61), knowing the step count and names only by reading the scratch's source.

Both games are C# (MAIN.md L27); neither is GDScript-heavy.

## 2. Proposed design

A game marks the methods it wants agents to call; the server lists them with a description and a JSON schema per argument, and calls one by name with named arguments, through the C# helper the `cs_*` tools already load into the game. Each part below states the recommended option; section 6 holds the alternatives.

### How a game declares a tool (question 1)

A C# attribute the game declares itself, matched by name, so the game takes no package and no tracked build change beyond its own source file:

```csharp
[System.Diagnostics.Conditional("DEBUG")]  // optional: release builds carry no tool marks
[AttributeUsage(AttributeTargets.Method)]
internal sealed class GodotMcpToolAttribute(string description) : Attribute
{
    public string Description { get; } = description;
    public string? Name { get; init; }       // default: the method's name
    public string? When { get; init; }       // "from the map", "while the party plans"
    public bool ReadOnly { get; init; }      // informs the listing only
}

[GodotMcpTool("Jumps the party from the map into the first uncleared room of a kind.", When = "from the map")]
public bool JumpToRoomOfKind([Description("Enemy, Elite, Boss, …")] string kind) => …;
```

The helper finds every method carrying an attribute whose type is named `GodotMcpToolAttribute` in any namespace, reading its constructor argument and named properties through `CustomAttributeData`, so the attribute's identity never has to match a type the helper references. A parameter's description is `System.ComponentModel.DescriptionAttribute`, already in the base library (the server's own tools use it). The game's XML docs are not a source: neither game writes them to its build output (no `GenerateDocumentationFile` in either repo's `*.csproj`/`*.props`, searched).

### Which objects carry tools (question 2)

An instance method on the script type of an autoload (named by the `autoload/*` project settings, section 8, since a child of `/root` also matches the current scene: delve's `Net`), an instance method on the current scene's root (opening-hand's scratch root), or a static method anywhere in the game's assemblies. A tool on a type that is neither is listed with `available: false` and why, never called.

### How the server discovers them (question 4)

Per call, from the live game, through the helper: a new helper op `tools` walks the game's own load context once per game process, keeps the marked methods in a static for the process's life, and answers the list with each tool's owner and availability recomputed per call (section 8), so the server keeps no cache and `restart_project` or a new attach reads a fresh process. Nothing is read at launch, so a game no agent asks about never loads the helper for it. The listing is the running build's, so it can never offer a tool the running game lacks.

### How an agent lists and calls them (question 3)

Two ordinary runtime tools, not dynamic MCP tools:

- `list_game_tools(options {name, offset, limit}, session)`, read-only: `{tools: [{name, description, when?, readOnly, on: "Net" | "/root/HandScratch" | "static DuelRules", args: <JSON Schema object>, returns, available, reason?}], total, offset, next?}`, paged as `cs_members` is.
- `call_game_tool(name, args, options {timeoutMs, maxDepth}, session)`, destructive: `{tool, value, type, errors?}`.

`args` is an object keyed by parameter name (question 5): `call_game_tool {name: "SetHp", args: {enemy: true, index: 0, hp: 6}}`. Both are `RuntimeTools` partials, so `batch_drive` offers them with no change (it reflects `RuntimeTools`' tools, ARCHITECTURE.md L110), and delve's forty-five-frame spacing becomes a batch of `call_game_tool` and `wait_for {frames: 45}` steps. `ToolClasses.FromAttributes` gives `list_game_tools` the `read` class and `call_game_tool` `edit-live` from their attributes (`src/GodotMcp.Server/Agents/ToolClasses.cs` L43-56), so the install's agent sweep gives them to the right agents with no override.

### Argument schemas from C# signatures

Built in Core from `ParameterInfo`, one JSON Schema property per parameter: `bool` → `boolean`; integral types → `integer` with the type's range; `float`/`double`/`decimal` → `number`; `string` → `string`; an enum → `string` with `enum` its names (a number is still accepted, as `cs_set` accepts it, TOOLS.md L282); a nullable or a parameter with a default → not `required`, with `default` written; `string[]`, `List<T>` → `array` of the element's schema; a record or class → `object` with the constructor's or settable properties' schemas, one level, deeper levels as `{type: "object", "x-csharp": "<type>"}`; a `Node`-derived type → `{"$node": path}`. `description` from the parameter's `[Description]`, and `x-csharp` always carries the C# type name as `cs_members` spells it (`Signatures.ParameterType`, `src/GodotMcp.Dotnet.Core/Signatures.cs` L32-33). A parameter the value reader cannot fill (`out`, `ref`, pointers, `Span`-like, delegates, generic methods) makes the tool `available: false` with the reason, rather than an entry that always fails.

Named arguments are bound to positions in Core, then converted by the existing `ValueReader`; an unknown name, a missing required one or a wrong type is refused naming the parameter and its schema before any game code runs.

### Results and errors

The result is `cs_call`'s: the value through `ValueWriter` (a Godot object as `{"$node": path}`, a value over 20000 characters as `{valuePreview, valueLength}`), `type` its runtime full name, and the error feed's `errors`. A thrown exception fails the call with its type, message and stack (`Calls.Threw`, `src/GodotMcp.Dotnet/Calls.cs` L220-224), so delve's `ArgumentOutOfRangeException` for a bad room kind is the call's error, not a null beside a logged engine error. A tool that returns `Task` or `Task<T>` is awaited up to `options.timeoutMs` (10000 by default, at most 120000, load-adjusted), through the pending table `cs_call` already uses (Calls.cs L109-141). What "done" means for a fire-and-forget cheat is question 6.

### Main thread and await rules

The helper's ops run on the main thread (the bridge calls the helper's `Callable` from its own frame; `src/GodotMcp.Dotnet/Helper.cs` L14, Calls.cs L11), so a tool runs where game code runs and may touch nodes. An `await` inside a tool resumes through Godot's `SynchronizationContext`, whose `Post` queues the continuation for `ExecutePendingContinuations` on the main thread (4.7.2 `GodotSynchronizationContext.cs` L39-53); the bridge polls a pending call once a frame (ARCHITECTURE.md L15, `Dotnet`). A tool that blocks the main thread without yielding cannot be cancelled and ends in the hang watchdog's report, as a `cs_call` would. A tool that pauses the tree keeps running (the bridge is `PROCESS_MODE_ALWAYS`), but delve records that holding its tree paused across calls drops its server socket (its DEVELOPMENT.md L78): that is the game's rule, stated in its `When`.

### Safety

- Only on a running game session: both tools resolve `session` as every runtime tool does and send nothing without a live bridge; a project with no C# assembly or an unbuilt one is refused before the game is asked, as the `cs_*` tools are (`CSharpBridge`, ARCHITECTURE.md L16).
- The helper loads only into a game the server started or joined, since the bridge is injected through the marked `override.cfg`; whether an exported build reads `override.cfg` at all is unverified (survey idea 15), and the game's own guard stays the real one (delve's server refuses every cheat without `--dev-cheats`, NetClient.cs L746-748).
- `[Conditional("DEBUG")]` on the game's attribute class keeps tool marks out of a release build's metadata altogether (a conditional attribute class's specification is omitted when the symbol is undefined: C# language specification §23.5.3.4, and `ConditionalAttribute`'s remarks on learn.microsoft.com), so a shipped game lists no tools.
- `call_game_tool` calls only a method the listing marks; it never becomes a way to call an unmarked member (that stays `cs_call`, which is also destructive).

## 4. Edges

- **No tools.** A game that marks nothing gets `{tools: [], total: 0}` and a `hint` naming the attribute and where to declare it; a GDScript-only project is refused before the game is asked, naming `call_method` (question 7).
- **First call is slow.** The first C# call of a game loads the helper (about 2 s cold, TOOLS.md L272); `list_game_tools` pays it once per game process, then answers from the session's copy.
- **Two tools, one name.** Two marked methods (overloads, or two types) resolving to one tool name are both listed `available: false`, each with the other's `on`, until the game gives one a `Name`. No overload resolution: a tool is one method.
- **The owner is not there.** An autoload freed or renamed, or a scene-root tool while another scene is current, lists `available: false` ("needs the current scene to be a HandScratch; it is Main") and refuses a call with the same words. The list is rebuilt from type metadata once, but availability is checked at each list and call against the live tree.
- **A stale game.** A game running an older build than the one on disk lists what it loaded, which is what it can run; the list says `build: stale` when a game dll's MVID differs from the disk's, as `run_csharp`'s refusal checks (ARCHITECTURE.md L120), and points at `restart_project`.
- **Fire-and-forget cheats.** delve's cheats answer `true` for "sent" (question 6): the call succeeds and a later refusal reaches only the game's notice and log. The fix that makes the call honest is game-side (a `Task<string>` tool that awaits the server's answer), and the recommended result leaves room for it.
- **Several in flight.** Two `call_game_tool`s on one session run one after the other (the helper is single-threaded on the main thread); a game that skips a second cheat while one is in flight (NetClient.cs L1173-1185) reports that through its own return value.
- **Long or stuck tools.** Past `timeoutMs` the call fails as `cs_call`'s does and the `Task` keeps running in the game; a tool that never yields ends in the hang watchdog.
- **A tool that pauses, quits or reloads.** A tool that changes scene, pauses the tree or quits the game runs as any game code does; a quit ends the session and the call fails with the game gone. The tool's `When` is where a game says so.
- **Attached and joined games.** Both tools work on an attached session as the `cs_*` tools do; a dormant game has no helper until joined.
- **Values.** Arguments and results go through the same `ValueReader`/`ValueWriter` as `cs_call`, so a `Node` argument is `{"$node": path}` and a returned `Node` reads as its path.
- **Private tools.** A marked `internal` or `private` method is listed and called (the helper reaches it, as `cs_call` does); the attribute is the opt-in, not the access modifier.

## 6. Open questions for the user

1. **How a game declares a tool.** (a, recommended) A C# attribute the game declares itself, matched by the name `GodotMcpToolAttribute` in any namespace, read through `CustomAttributeData`; parameter descriptions from the BCL's `[Description]`. How: a ten-line attribute file in the game, a mark per method. Worst case: a game that renames or misspells the attribute gets an empty list with no error, and learns from the hint that nothing matched. (b) A `GodotMcp.Annotations` NuGet package holding the attribute. How: a `PackageReference` in the game's csproj, the attribute by type. Worst case: a tracked build change and a runtime dependency in the game's release for a dev-only feature, and a version skew between the package and the installed server refuses tools. (c) A method-name convention on autoloads (`Mcp_JumpToRoomOfKind`). How: the helper lists methods by prefix. Worst case: the game renames its API for a tool, and nothing carries a description or a `When`. (d) A manifest in `godot-mcp.json` (`tools: [{name, node, method, description, args}]`). How: the server reads it with the profile (`ProjectProfile`'s strict key list, `src/GodotMcp.Server/Tools/ProjectProfile.cs` L39, gains `tools`). Worst case: the manifest drifts from the code, and a renamed method fails only when called. (e) Every public method of a named autoload. How: `godot-mcp.json` names `Net`. Worst case: delve's `Send`, `Submit` and `IsInFlight` are offered beside the cheats. **Ruled (user, 2026-09-30): (a), the game's own attribute matched by name.**
2. **Which objects carry tools.** (a, recommended) Autoloads, the current scene's root, and statics. How: the helper matches the declaring type against the root's children and the current scene. Worst case: a tool on a deeper node (a card, a panel) is not found, and the game forwards it through its scene root. (b) Any node in the tree. How: a tree walk at each list. Worst case: several instances of one type (delve's cards) make one tool ambiguous, and a big tree makes each list slow. (c) Autoloads and statics only. Worst case: opening-hand's `ScratchScene.PlayStep` cannot be a tool. **Ruled (user, 2026-09-30): (a), autoloads, the current scene's root and statics.**
3. **One generic pair or dynamic MCP tools.** (a, recommended) `list_game_tools` and `call_game_tool`. How: two fixed tools; the game's tools are data. Worst case: an agent spends one list call before its first cheat, and a tool's schema lives in a result, not in the client's tool list. (b) Each game tool as its own MCP tool, added to `ToolCollection` when a session lists it and removed when the session ends, with `tools.listChanged` advertised. How: an `McpServerTool` subclass per game tool with the schema of section 2. Worst case: agents spawned with a `tools:` line never see them (the sweep runs at install), two sessions of different games need prefixed names, and whether Claude Code re-lists on `list_changed` is unverified. (c) Both: the pair, plus (b) behind a flag. Worst case: two ways to do one thing, and the docs must teach both. **Ruled (user, 2026-09-30): (a), list_game_tools and call_game_tool.**
4. **When the list is read.** (a, recommended) Per call from the live game through the helper, kept per game process. Worst case: the first list costs the helper's cold load, about 2 s. (b) Statically from the built assembly in the server with `System.Reflection.Metadata`, with no game running. Worst case: it lists what the build on disk has, not what the running game loaded, and needs a second metadata reader beside the helper's reflection. (c) Eagerly at every C# launch and attach, returned in `run_project`'s result. Worst case: every C# launch pays the helper load whether or not a tool is used. **Ruled (user, 2026-09-30): (a), per call from the live game, kept per game process.**
5. **How arguments are passed.** (a, recommended) An object keyed by parameter name (`{enemy: true, index: 0, hp: 6}`), checked against the schema before the game is asked. Worst case: a parameter renamed in the game breaks a stored drive by name, where a position would still fit. (b) A positional array, as `cs_call`'s `args`. Worst case: `SetHp(true, 0, 6)` again, the argument meanings read from the schema by position. **Ruled (user, 2026-09-30): (a), an object keyed by parameter name.**
6. **What a result means for a fire-and-forget cheat.** (a, recommended) The method's return value as `cs_call` returns it, a `Task` awaited; the docs tell games that a tool meant for agents returns what happened (`Task<string>` awaiting the server's answer), and delve is told so. Worst case: until delve changes, `call_game_tool {name: "SetHp"}` answers `true` for a cheat its server then refuses. (b) The server also waits a settle window (N frames) after each call and attaches the errors raised meanwhile. Worst case: every call is slower by the window, and delve's refusals are notices, not errors, so they still do not show. (c) The attribute names a companion "why refused" method (delve has `WhyForcedAimRefused`, NetClient.cs L826) that the server calls a frame later. Worst case: a second convention per tool that most tools lack, and a refusal later than a frame is still missed. **Ruled (user, 2026-09-30): (a), the method's return value, a Task awaited; delve is told to return what happened.**

## 8. Spike results (step 1)

Measured from the helper in a CsProbe copy (Godot 4.7.2 mono, Debug build), reached through `cs_call` on a throwaway helper class; eight marked methods (sync, `Task<string>`, an enum with a default, `int?`, a record with a `List<string>` and a `Node`, an `out` parameter, a static, `PlayStep` on the scene root) and a second `GodotMcpToolAttribute` in another namespace.

- **Load contexts.** The helper, GodotSharp, GodotPlugins and Core share one `IsolatedComponentLoadContext`; the game assembly sits alone in a `GodotPlugins.PluginLoadContext` that is **not** collectible in a game run; the framework is in Default. A node's `GetType()` and a walked method's `DeclaringType` are the same `Type`, so `==` matches an owner.
- **Reading the mark.** `method.GetCustomAttributesData()` matched by `AttributeType.Name == "GodotMcpToolAttribute"` finds both namespaces' attributes; `ConstructorArguments[0]` is the description; `NamedArguments` holds only the properties set explicitly, so unset ones take the attribute's defaults (`Name` the method name, `When` null, `ReadOnly` false). `[Description]` on a parameter reads typed (`GetCustomAttribute<DescriptionAttribute>()`), since the framework comes from Default. An enum default arrives typed, `int? x = null` has `HasDefaultValue` with null, an `out int` is `Int32&` with `IsByRef`. `[Conditional("DEBUG")]` keeps the attribute in the Debug build a game runs; the Release omission was not measured.
- **Walk time.** Only the game's own context (1 assembly, 31 types, 121 methods): 2.25 ms cold, 0.17-0.19 ms repeated; every assembly: 163 ms cold, 50-74 ms repeated. The first C# call, the helper's cold load included, took 2346 ms of game time.
- **Which context to walk**: the one holding the assembly named by `dotnet/project/assembly_name`, every assembly in it (a game's referenced project dlls load there too, reasoned from `PluginLoadContext`, not measured). Filtering on "declares the attribute" would miss an attribute declared in one game dll and used in another.
- **The autoload rule of section 2 also matches the current scene** (a child of `/root` whose type declares the method): `PlayStep` matched as autoload and as scene root. Step 3 reads autoload names from the `autoload/*` project settings, which also give the `on: "Net"` spelling.
- **Duplicate argument names** cannot be caught in Core: `JsonNode.Parse` accepts `{"hp":1,"hp":2}` and throws only on the first `Count`, while `JsonDocument` enumerates both; the server takes `args` as a `JsonElement` and refuses duplicates.

Settled for step 2 from the spike and the code:

- `ToolSchema.Describe(MethodInfo, Func<Type, bool> isNode)` returns a `ToolSignature(JsonObject? Arguments, string? Unavailable, string Returns)`, exactly one of the first two set; `NamedArguments.Bind(MethodInfo, JsonObject, IValueResolver)` returns the `OverloadChoice` `Calls` already invokes, and throws `OverloadException` for its refusals. `OverloadResolver`'s private `Unpassable` moves to a shared internal class the three use, so they agree on what cannot be passed.
- `ToolMark.Read(MethodInfo)` in Core reads the mark by name into `(Description, Name, When, ReadOnly)` with the defaults above, unit-tested with a sample attribute.
- Schemas: each converter-supported type as its JSON type (integers with their width's `minimum`/`maximum`; enum names as `enum`; a `[Flags]` enum as `{type: string, "x-flags": [names]}` taking comma-joined names; `Nullable<T>` and a defaulted parameter not required, the default written; `params` a non-required array; collections `array`, a set with `uniqueItems`; `Dictionary<string, V>` an object with `additionalProperties`; a record, class or struct one level deep with the union of its public constructors' parameters and settable members, `required` only with exactly one public constructor, `additionalProperties: false` as `ObjectReader` refuses unknown keys, deeper levels `{type: object, "x-csharp"}`; a `Node` `{type: object, properties: {"$node": {type: string}}, required: ["$node"]}`; an interface or abstract type an object noting `$handle`/`$node`; `object` `{}`); every property carries `x-csharp` spelled as `cs_members` spells it and `description` from `[Description]`.
- A `CancellationToken` parameter is left out of the schema and bound to `CancellationToken.None`; `in` converts like a plain value; `ref`, `out`, pointers, by-ref-like types, delegates, generic method definitions, `IReadOnlyCollection<>`, `ISet<>`, non-string-keyed dictionaries and `nint`/`nuint` make the tool unavailable.
- Names match ordinally, with a case hint. Refusal texts: unknown `SetHp has no parameter 'hitpoints'; it takes enemy, index, hp.` (plus `did you mean 'hp'?` when only case differs); missing `SetHp needs 'hp' (int); list_game_tools shows its schema.`; wrong type `parameter 'hp': expected an int, got "six"` (`OverloadResolver`'s form); unavailable `parameter 'value' is out int, which a game tool cannot pass`.
- For step 3: the helper keeps the walked methods in a static for the game process's life and recomputes each tool's owner and availability per call, so no server cache and no drop points (question 4's "kept per game process"); a tool unavailable for its signature is listed `available: false` with `reason` and no `args`, one unavailable for its owner keeps `args`; two tools on one name are both listed, each naming the other's `on`. The new server file is `RuntimeTools.CSharp.GameTools.cs`, so run.ps1 maps it to the `csharp` group only.

# Versioned install behind a stable launcher: the design behind GMCP-189

GMCP-189 (from opening-hand): `run.ps1 install` stops every running server and the games they drive. The owner ruled (settled on the issue): install into versioned folders and make `%LOCALAPPDATA%\godot-mcp\godot-mcp.exe` a stable launcher that starts the current version's real exe, so running servers keep the version they started with and `/mcp` picks up the new one. This file holds the measurements, the invariant pass (an `oracle` pass, read-only, against main a5841308) and the orchestrator's decisions; it moves to `docs/plans/archive/` once the last step lands, after its rulings are in `docs/DECISIONS.md`.

## Measured (spike, .NET 10, Windows; `.tmp/map-gmcp-189-spike.md` in the session that ran it)

- A running exe and its loaded DLLs can be renamed aside and replaced, but the old process then reads the new copy's data files and lazy-loads the new copy's assemblies (a v1 process loaded `spikelib 2.0.0.0` from the swapped folder). Renaming in place does not keep a server on one version.
- A junction keeps the launch path: `AppContext.BaseDirectory`, `Environment.ProcessPath` and the host's assembly paths all name the junction, so a repoint mixes versions the same way; resolving the real folder in the app pins data files but not assemblies.
- `MoveFileEx(MOVEFILE_REPLACE_EXISTING)` cannot replace a junction (error 5); a junction swap takes two renames with a gap.
- A folder a process runs from cannot be renamed; a recursive delete of it deletes everything but the locked files.
- So a server stays on one version only when it is launched by its real versioned path.

`I` below is `%LOCALAPPDATA%\godot-mcp` (or `GODOT_MCP_INSTALL_DIR`).

## Layout

`I\godot-mcp.exe` (the launcher), `I\current` (a file naming the current version folder), `I\VERSION` (a copy of the current version's, for the skill), `I\install.lock`, `I\versions\{n}\` (one complete server tree each: exe, dll, `bridge`, `headless`, `dotnet`, `capture`, both skills), and leftover `I\godot-mcp.exe.old-{guid}` files.

## Actors

The launcher (one per session, lives as long as its server); the versioned server (reads `bridge/`, `headless/`, `dotnet/`, `capture/` from `AppContext.BaseDirectory`, `Installation.cs` ~137-174, `RealtimeEnvironment.cs` ~89; writes shared state: the `override.cfg` marker and owners line, `override-folders.txt`, `armed.json`, dormant files, `godot-mcp-cache`); the MCP client (owns the launcher's stdio and can kill it, not the server under it); the games, headless hosts and capture helper a server starts (a welcomed game quits one frame after its connection drops); a clone install (`run.ps1 install` → `tools/install.ps1`); a release install (`tools/install-release.ps1`, PowerShell 5.1 and 7, with `InstalledServers.psm1` inlined by `package.ps1`), possibly from another session at once, and installers from before this change; the skill junctions and copies; `--sweep-agents`; the `override.cfg` files in project folders, which name the bridge by absolute path; AV and indexers; the user.

## Invariants and their sites

- **I1** A server never runs files from two versions: the launcher starts it by its real versioned path, and nothing writes into a version folder once the pointer has named it. Replaces `install.ps1`'s `robocopy /MIR` into the live folder (~:68, ~:148) and `install-release.ps1`'s empty-then-copy (~:289-299).
- **I2** The launcher never touches the protocol: it writes nothing to stdout and reads nothing from stdin; on an error it writes one `godot-mcp launcher: …` line to stderr and exits 1 before starting anything.
- **I3** The server dies with its launcher; its games still quit on their own. The launcher creates a job with KILL_ON_JOB_CLOSE and SILENT_BREAKAWAY_OK, starts the server suspended, assigns it, resumes it; the launcher stays out of the job. The server's children leave the job silently and quit by the welcome rule, as when a client kills a server today. The launcher waits for the server and exits with its exit code; arguments pass through as given, so `--sweep-agents` and `--list-tools` reach the server unchanged. Patterns to copy: `DesktopProcess.cs` (~164/245/360, start suspended, join, resume), `OwnWork.cs` (~228-233, kill on close).
- **I4** The pointer is read whole: `I\current` holds the folder name; an install writes `current.tmp-{guid}` and renames it over `current` (`File.Move(…, overwrite: true)` under PowerShell 7, `File.Replace` under 5.1). The launcher opens it with `FileShare.ReadWrite | FileShare.Delete` so its read never blocks the rename. A test proves no reader sees it missing or half-written.
- **I5** The pointer names only a complete version that has started once: copy, run `versions\{n}\godot-mcp.exe --list-tools` and require exit 0, then switch.
- **I6** Two installs never interleave: each holds `I\install.lock` (FileShare.None) from start to end, sweep included; a second install waits, then refuses naming the lock. Installers from before this change ignore it (accepted).
- **I7** An old version is deleted only when nothing can reach or use it: never the current one; it is first renamed to `versions\.trash-{guid}`, which fails while any process holds a file in it; only a renamed folder is deleted recursively; any failure leaves it for the next install. Replaces `install-release.ps1`'s `Remove-Item -Recurse` (~:262) and robocopy's purge.
- **I8** A version folder's name is unique per build: `{semver}-{sha}` from VERSION with `+` turned into `-`; a taken name gets `.2`, `.3`, …; a folder is never reused.
- **I9** Migrating today's flat folder (`godot-mcp.dll` beside `I\godot-mcp.exe`, no `current`) stops only the processes whose ExecutablePath is exactly `I\godot-mcp.exe`, printing today's `install: stopped …` line for each, then removes the flat entries except `versions`, `current` and the lock, then lays down the launcher. `Get-InstalledServer`'s prefix match (`InstalledServers.psm1` ~98-100) must tell launchers, versioned servers and the flat server apart.
- **I10** Replacing the launcher: compare hashes; when they differ, rename `godot-mcp.exe` to `.old-{guid}` (works while it runs), copy the new one in, delete `.old-*` files once deletable. So the launcher is one self-contained file: a multi-file one renamed aside would load from the new copy.
- **I11** The launcher-server contract never changes: the pointer's format, the `GODOT_MCP_LAUNCHER` variable (the launcher's own path, set for the child), arguments passed as given. Old launchers keep running across installs, so any launcher must start any later server.
- **I12** Registered paths keep naming the launcher (`install-release.ps1` ~:370, `README.md` ~:66, `run.ps1` ~:539). The `claude mcp add` hint (`Installation.cs` ~:28) names `GODOT_MCP_LAUNCHER` when set, never a version folder. A clone install points the skill junction at `versions\{n}\skill` (`install.ps1` ~:141-152).
- **I13** Shared state works across versions (see the cross-version rule below). `OverrideFile.cs` ~220-251 already refuses a second bridge path on one project folder; its message names `/mcp` for the older session.
- **I14** Matching a server to its client session (`Get-ClientSessionId`, `InstalledServers.psm1` ~20-31) steps up one more parent when the immediate parent is a launcher.

## Orchestrator decisions (not owner rulings; open to the owner)

- **D1 version folders** live in `I\versions`, so an old installer's prefix match still finds and stops versioned servers before it wipes the folder (worst case: a downgrade by an old installer stops everything, as every install does today).
- **D2 the pointer is a file** replaced by rename, not a junction (a junction swap has a gap). Worst case: AV holds it, the replace fails after retries, the install fails with the old pointer standing, which is safe.
- **D3 the launcher is NativeAOT**, `src/GodotMcp.Launcher`, AssemblyName `godot-mcp`, invariant globalization, `LibraryImport` only, about 200 lines; its size is measured in its first brief. The release runner already links the NativeAOT shim.
- **D4 death:** the job object with a suspended start (I3). Worst case: the hard kill skips the server's Shutdown, leaving a stale `override.cfg` until the next server's startup sweep, the same as a client kill today. Ruled out: a parent-pid watch in the server (a hung server could outlive its launcher and pin its version folder).
- **D5 retention:** keep the current and the previous version; older ones are removed when the rename probe succeeds.
- **D6** the start check before the switch (I5) is required.
- **D7** the newest installer given a `-Version` older than the launcher's release refuses and names that release's own `install.ps1`.
- **D8** the layout logic is one PowerShell module, `tools/InstallLayout.psm1`, runnable under 5.1, imported by `install.ps1` and inlined into the release installer by `package.ps1` as a second region (`Write-Installer` accepts two).
- **D9 install output** names every session still on an older version (session and project), so the user can `/mcp` them, after I14 is fixed.
- **Cross-version rule (the oracle's dissent, accepted):** versions N-1 and N now run side by side for hours. (a) Every file servers share (`override.cfg` marker and owners line, `override-folders.txt`, `armed.json`, dormant files, `godot-mcp-cache`) stays readable by the previous version: a release that changes one's format keeps reading the old form and says so in its changelog. (b) One project folder is driven by one version at a time; the existing refusal's message names `/mcp` in the session on the older version. (c) Between an install and `/mcp`, a session reads the new skill while talking to the old server; accepted, and the install output's list of older sessions is the remedy. `DRIVING_CONVENTIONS.md` ~:18's "the skill always matches the server" is amended to say so.

# Drives across processes: a host, its clients and the server between them

Design for Linear GMCP-47, "Drives across several processes" (project "Ideas from the survey and the projects"). The issue cites delve-the-dungeon, whose drives start a .NET server and a second headless client in the background, and whose docs say "a tool call cannot stop a server while a script runs". The survey's nearest idea is 18, network conditions between instances ([survey](../research/2026-09-29-godot-mcp-survey.md) L184-187), which this design does not adopt (section 5). Section 7's questions are ruled; the step 1 spike's results are in section 2.

## 1. Need

### What works today with several sessions

- **Named sessions side by side.** `run_project` and `attach_project` take `options.session`; several sessions run at once, on one folder or several, and share one name space ([DECISIONS.md](../DECISIONS.md) decision 10, L33-34; [ARCHITECTURE.md](../ARCHITECTURE.md) L64-65). The itest `TwoSessionsOnOneProjectRunTogether` launches `server` and `client` on one InputProbe copy, screenshots both and stops them one at a time (`tests/GodotMcp.IntegrationTests/SessionLifecycleTests.cs` L132-162). Input calls are serialised per session, not across sessions (ARCHITECTURE.md L151).
- **A headless client is a run like any other.** `run_project` refuses `--headless` only for a recording (`src/GodotMcp.Server/Session/GodotCommandLine.cs` L183-204), and `run_scratches` launches every scratch scene as a headless game session with `["--headless"]` as its engine arguments (`src/GodotMcp.Server/Session/ScratchRun.cs` L309; ARCHITECTURE.md L119). Such a session is driven and read through the bridge; its stdout and stderr are captured.
- **One batch across sessions, in order.** `batch_drive` takes `session` on every step, the batch's own as the default (`src/GodotMcp.Server/Tools/RuntimeTools.Batch.cs` L61-68, L308-311), so "click in `host`, then wait in `guest`" is one call with one result. A `no_errors` step on a session checks that session's feed from the batch's start (`MarkErrorFeeds`, L240-253).

### What an agent cannot do

- **Start, wait on or stop a process that is not a Godot game.** delve's server is `dotnet run --project src/Delve.Server` (delve `docs/DEVELOPMENT.md` L32), not a Godot run. Decision 11 keeps it outside: "Presets launch Godot only, so delve's `dotnet run` server stays outside" (DECISIONS.md L46). So the drive starts it from the shell: "Started from an agent's tool call, `server -Detach` does not hand the shell back …: run it as a background command and poll `http://localhost:<n>/version`" (delve L65), and must `.\dtd.ps1 stop -Port <n>` before any build because the server holds `Delve.Server.dll` (L65). `dotnet run` also leaves a `Delve.Server` child listening after its parent is stopped, so an instance is stopped by its port (L33). The glossary's session entry (README.md L53, "delve's 'server' and 'client-1' share one folder") and TOOLS.md's profile example (L502-510, a `server` preset with `--server`) picture that server as a Godot run; it is not one.
- **Stop that server at a moment chosen against the client's timeline.** The issue's line, now delve L71: "A swap to `Connecting` is the server stopped under the client: start `Start-Sleep -Seconds 4; pwsh <worktree>/dtd.ps1 stop -Port <n>` as a background command, then the sampling script at once, since a tool call cannot stop a server while a script runs". The four seconds are a guess at how long the next tool call takes to start sampling.
- **Run a second player through the server.** delve L67: "A second player for a drive is a headless client the drive launches itself once the host's room code is read off the lobby's `Code` label: `Godot_console.exe --headless … --smoke-join=<code>` … Launch it as a background command with its output to a file and stop it by its command line when the drive ends." Its progress is read by reading that file for `[client] joined <code> with 2 players` and `[client] claimed seat 1 as Brian`. A headless game never goes dormant on an armed folder (ARCHITECTURE.md L75), so `attach_project` cannot reach a client launched that way. delve L107 notes that "a second client can be a session of its own (`run_project` with `options.session: "client-2"` …) … not yet tried on this game".
- **Wait in one process on another's output.** The lobby smoke orders three processes by their logs: it starts the server and waits for `Now listening on` (delve `tools/smoke/Smoke-Common.ps1` L42), starts the host and reads the room code from `\[client\] hosted (\S+)` (`tools/smoke/Smoke-Lobby.ps1` L104-110), starts the joiner with that code and waits for its `joined` and `claimed` lines (L114-122), then waits for `[client] dice settled` in both clients' logs (L126-127). `Wait-ForLine` polls the file every 500 ms (`Smoke-Common.ps1` L20-33). The server's only output read today is the scratch runner's own marker lines (`ScratchRun.cs` L458-491); no tool waits on a line.
- **Arm a wait in one game before acting in another.** Every step of a batch starts after the step before it has answered, and an input tool answers once its gesture has ended and two more frames have run (TOOLS.md L144). An effect the host's click causes in the guest can land and pass before the guest's `wait` step starts; the same holds for a `capture_frames` in the guest meant to film the guest's reaction to the host's input, since `capture_frames` blocks until its last point. `wait_for {uiChanged}` is refused in a session where no gesture took a baseline (`bridge/godot_mcp_time.gd` L80-81, L579-580), so a change the guest shows because of the host's input cannot be waited on that way at all.
- **See errors one process raised because of another.** A runtime tool attaches the errors raised in its own session's game while it ran (ARCHITECTURE.md L46). A host click that throws in the guest's handler returns clean; only a `get_errors` on the guest, or a `no_errors` step naming it, finds it.
- **Order what two processes did.** Each result's frame numbers are its own process's (`frame_control`'s `processFrames`, `get_game_state`'s `frame`, the watch's `startFrame`), and Godot's `Time.get_ticks_usec()` counts from each process's own start (section 2). delve stamps its rows with `Time.get_ticks_msec()` (L71), which cannot be compared between the host and the guest. A drive cannot say how long after the host's lock-in the guest showed it, or whether the guest's `Connecting` screen came before or after the server's last log line.
- **Stalls across players.** delve L107: "the host watching over the joiner is asked `Take the hit instead?` when the enemy attacks him, and the turn stays `Resolving` on every client until the `Take` button … is pressed": an input in one client waits on a prompt in another, which a drive only finds by reading both.

**opening-hand** has no networked play today: its DEVELOPMENT.md drives one client, and two sessions there are two worktrees' drives of the same game (`docs/DEVELOPMENT.md` L58). Its plan lists "DUEL-52 Design online multiplayer duels" (`docs/plans/MAIN.md` L71), so it is the next user of this design.

## 3. Design

Six parts. Parts A to C close the process gap, D and E the concurrency and error gaps inside `batch_drive`, F the ordering gap. Each states the recommended option; section 7 holds the alternatives.

### A. A second Godot client is a session (question 1's base)

Nothing to build: `run_project {projectPath, engineArgs: ["--headless", "--resolution", "<the project's viewport size>"], userArgs: ["--server=localhost:<port>", "--profile=<name>", "--smoke-join=<code>"], options: {session: "guest"}}` starts delve's joiner as a session, with its output captured and its game driven by every runtime tool. Both sessions on the folder must agree on `quiet` and `shutOutRealGamepads` (decision 10). `--resolution` matters because a headless root window is 64 × 64 (section 2); a guest that needs screenshots is a quiet windowed run instead, since a headless one has no picture and no `window` in its result. Step 2 proves it with a networked fixture and documents it in TOOLS.md and SKILL.md, replacing delve L67's background launch.

### B. Process sessions (questions 1, 2)

A process a project needs beside its games (a .NET server, a mock backend) is declared in `godot-mcp.json` and started by name. This amends decision 11 (L46): presets still launch Godot only; companions get their own section.

```jsonc
"processes": {
  "server": {
    "command": ["dotnet", "run", "--project", "../Delve.Server", "--", "--dev-cheats"],
    "cwd": ".",                                  // relative to the project folder; default the folder
    "env": {"Delve__DataDir": "../../.tmp/drive-runs"},
    "ready": {"output": "Now listening on", "timeoutMs": 120000},
    "description": "the game server; pass --port <n> as args"
  }
}
```

- `command` resolves as `prepWrapper`'s program does (a program with a folder in it is relative to the project folder, a bare name is found on `PATH`; TOOLS.md L496). Parsing is strict, as the rest of the file (an unknown key, a wrong type, an empty `command`, a `ready.output` that is not a valid regex are refused with the file's path and the fix).
- **`run_process(projectPath, process, args?, options {session, ready})`**: four parameters, within the five-parameter limit. `args` append to `command`. `options.session` names the session (default the process's name, fitted to the name rule as a folder name is); `options.ready` overrides the profile's. With `ready`, the call returns once a stdout or stderr line matches `ready.output` (`timeoutMs` 1 to 600000, default 60000, load-adjusted), else at once. Result: `{session, projectPath, process, processId, command, log, ready?: {line, stream, ms}}`.
- It is started as the warm host is (`ToolProcess.Start`, a kept-running process, stdin closed; ARCHITECTURE.md L32-33), with no ceiling and no stall kill, in a job of its own with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so `dotnet run`'s child (delve L33) and every other descendant end with it, and a server that dies takes its processes with it. Its stdout and stderr fill the session's two ring buffers (`GodotRun.OutputCapacity` lines) and `.godot/godot-mcp/process-<session>.log`.
- **What reaches it**: `list_sessions` (kind `process`, `processId`, `live`), `get_debug_output`, `stop_project` (the job terminated at once: `{session, projectPath, kind: "process", exitCode, killed, alreadyExited}`), `restart_project` (stopped, started again with its stored command and arguments, `ready` waited on again), and `wait_for {output}` (part C). It writes no `override.cfg` and holds no folder reference. `SessionRegistry.Shutdown` ends it with the runs. A stopped process stays listed as a stopped run does.
- **Refusals**: no `godot-mcp.json`: `No godot-mcp.json beside project.godot in <path>: run_process starts only the processes its "processes" section declares.`; an unknown name: `<path>/godot-mcp.json has no process 'srv'; it declares: server (the game server; pass --port <n> as args).`; a live session of that name: as `run_project`'s; an exit before ready: `The process 'server' exited (code 1) before a line matched 'Now listening on'; its last stderr lines: …` (up to 20); a ready timeout: `The process 'server' printed no line matching 'Now listening on' within 120 s of load-adjusted time, so it was stopped; its last output lines: …`; a runtime tool other than `wait_for {output}` on a process session: `Session 'server' is a process (dotnet), not a Godot game: only wait_for with an output condition, get_debug_output, restart_project, stop_project and list_sessions reach it.`
- **Annotations**: as `run_project` (neither read-only nor destructive, the `drive` class), so every agent that launches a game can launch its server.

### C. Waiting on a line (question 6)

`wait_for` gains `{output: "<regex>", stream?: "stdout" | "stderr" | "any"}` (default `any`), for a run or a process session. It is answered by the server from the session's ring buffers, polled as the scratch runner polls for its markers (`ScratchRun.cs` L491), with no bridge request, so it works on a paused game. It looks at lines that arrive after the call starts; `after` (a line number from `get_debug_output`'s `stdoutTotalLines` or `stderrTotalLines`, or a previous match's `lineNumber`) looks back from there, within the lines the buffer still holds. Met: `{met: true, elapsedMs, value: {line, stream, lineNumber, groups, at}}` (`groups` the regex's captures, so delve's room code is `groups[0]` of `\[client\] hosted (\S+)`; `at` on the drive clock, part F). Timeout: `{met: false, elapsedMs, last: {stdout, stderr}}`, the last line of each. A line is matched with a 1 s regex timeout, as `scratch.patterns` are (TOOLS.md L140), and a timeout fails the wait naming the pattern. Refused: an attached session (`Session 'x' is attached: the server captures no output from a game it did not start; wait on a node, a property or an expression instead.`), `options.call` and `options.screenshot`, `timeoutMs: 0` (check once) without `after`, and an invalid regex (`condition.output is not a valid regular expression: <reason>.`). `batch_drive`'s `wait` assertion takes it like any condition.

### D. Steps at once in a batch (questions 3, 4)

A batch step may be a **parallel group**: `{parallel: [step, step, …]}`, 2 to 8 tool or assertion steps, each on its own session (a group naming one session twice is refused: `step 3: parallel steps 0 and 2 both address session 'host'; each step of a group addresses its own session.`), no group inside a group. The server starts the members in listed order, each one's request written before the next starts, and the group ends when all have answered; its members count toward the batch's 100 steps and its time toward the 300 s once. A failed member cancels the others still running (the bridge's `cancel`, ARCHITECTURE.md L48), whose entries say `cancelled: true`; the batch then stops as at any failed step, with `failedAt: {index, member, reason}`.

- **Arming before acting**: `{parallel: [{assert: "wait", node: "Lobby/Seat1/Name", property: "text", equals: "Brian", session: "host"}, {tool: "click", args: {target: {text: "Claim"}}, session: "guest"}]}`. The wait's request reaches the host's socket before the click is sent to the guest, so the host checks from a frame no later than the one the guest's message can arrive in; a change that lives under one frame is the watch's job (its signal tracks, [timeline-watch.md](./archive/timeline-watch.md)).
- **Filming one game while driving another**: a `capture_frames` member in the guest beside a `click` member in the host.
- **Two inputs at once** (a race for one seat): two `click` members on two sessions are sent one socket write apart, where two sequential steps are a reply and two settle frames apart.
- **`{uiChanged: "now"}`** (question 7): a `wait_for` condition that takes its UI baseline when the wait starts rather than from a gesture, so a wait member in a group sees the change another session's input causes. `{uiChanged: true}` keeps its meaning and refusal, whose text gains `, or wait for {uiChanged: "now"} in a parallel group beside an input in another session`.

### E. Errors from every session the batch drives (question 5)

The feeds of every session a batch names are marked at its start (`MarkErrorFeeds` widened from the `no_errors` steps' sessions to all). Each step's entry gains `errorsElsewhere: {"<session>": [errors]}` for the errors raised in the batch's other sessions while that step ran, shaped by `ErrorReport` (repeats collapsed, at most 20 a session, then `errorsOmitted`), and left out when there are none. `no_errors` takes `sessions: "all"` (every session the batch names) or a list, beside today's default of its own session. A tool called outside a batch is unchanged: the batch is what says which sessions belong together.

### F. One clock for every process (question 8)

The **drive clock** is the server's `Stopwatch`, in milliseconds since the server started, to 0.1 ms. Each game session keeps a **clock offset**: the bridge's hello and every `pong` add `ticksUsec` (`Time.get_ticks_usec()` when the bridge handled it); for each ping the server knows its send time `S` and receipt time `R`, so the offset lies in `[S - t, R - t]`, and the session keeps the tightest bounds seen (the largest lower, the smallest upper). The server sends five pings 7 ms apart from one start after the handshake, without awaiting replies (so they land at different points of the 60 fps frame; pings that wait for each reply lock to the frame, section 2), later pings at random gaps, and one more before converting a stamp when the bounds are wider than 2 ms. Stamps converted through it carry the bound's half-width once per result as `clockErrorMs`.

Where the clock shows:

- `batch_drive`: the result's `startedAt`, and on every entry `startMs` and `endMs` (exact: the server's own clock).
- `wait_for`: `metAt`, the drive time of the frame whose check met (the bridge adds its ticks to the met reply), with `clockErrorMs`; an output wait's `value.at` is the server's receipt time of the line.
- The watch ([timeline-watch.md](./archive/timeline-watch.md), decision 29): each point and event gains a fourth element, its drive time (the bridge keeps one `ticks_usec` per kept point), and the result `clockErrorMs`. This changes decision 29's point shape `[frame, gameMs, value]`, so it waits on question 8 and on the watch's own landing (GMCP-19).
- A process session's output lines: the receipt time, shown in `wait_for {output}`'s `at`; `get_debug_output` is unchanged.

So "the guest showed the host's lock-in 46 ms after the host's click step began" is `metAt - startMs`, two numbers of one result, and a watch on each game lines up on `at`.

### Interactions

- **Sessions**: process sessions share the name space and `list_sessions`; a name refused or replaced as a run's is. `stop_project {projectPath}` stops the folder's game session and warm host as today, never a process session, which is stopped by name.
- **`frame_control`**: unchanged and per session. A paused host still answers a parallel group's members on other sessions; delve's rule that a tree held paused across calls drops its socket (delve L79) is why no cross-session pause is offered (section 5).
- **Recording**: a recorded session's `metAt` and watch `at` are drive time, while its `clipMs` stays clip time; a group mixing a recorded and a plain session is allowed.
- **The error feed**: unchanged per session; part E only reads other sessions' feeds.
- **`wait_for`**: `output` is a server-side condition beside the bridge's ones; `uiChanged: "now"` is the bridge's.
- **The watch**: one per session, so a host watch and a guest watch run at once; the swap of delve L71 becomes `watch start` (guest), `stop_project` (the `server` process session), `wait_for` (guest, the `Connecting` screen), `watch stop` (guest), four sequential calls with no sleep.

## 4. Costs and risks

- **Per frame**: nothing for parts B to E. Part F adds one `Time.get_ticks_usec()` per kept watch point and per met wait (well under the 0.5 µs a monitor read costs, timeline-watch.md section 8) and one integer on each pong.
- **Wire**: `errorsElsewhere` is at most 20 errors a session a step; a 100-step batch over three sessions of a game that errors every frame could carry 4000 entries. Every `at` is one number. The pings are five small frames per session at handshake.
- **Running any program**: an MCP client whose rules allow `mcp__godot__*` would, with a free-form command, let an agent run any program without the shell's permission prompt. The profile allow-list (part B) keeps the command in a tracked file the user reviews; question 1 (b) removes that guard.
- **A process left running**: a process session holds its port and its build output until stopped (delve L65's lock on `Delve.Server.dll`), across agent turns; `list_sessions` lists it, the server's exit ends it, and the kill-on-close job ends it when the server is killed. A process started by another server is out of reach, as another server's sessions are.
- **No graceful stop**: a process session is terminated, as `dtd.ps1 stop` does; a server that saves on shutdown loses what it had not saved.
- **Careless use**: a parallel group of eight 120 s waits holds the batch near its 300 s deadline; two `run_script` members block two games at once. A pathological regex is cut at 1 s a line. A `wait_for {output}` started after the line printed misses it, which `after` and `run_process`'s `ready` exist for.
- **Clock error**: the offset is as good as the shortest round trip seen, which the bridge's per-frame poll lengthens to as much as a frame (section 2). The spike measured 1.4-1.9 ms after the five handshake pings and 0.2-0.3 ms after a minute of randomly spaced ones: enough to order a network hop (3-15 ms), not two events in one frame.

## 5. Alternatives considered

- **The shell keeps companions** (decision 11 as it stands): the agent starts and stops the server with background commands. Why not: delve's own guesses (`Start-Sleep -Seconds 4`, L71), the port lock it must remember (L65), output read from files by hand, and no way to wait on it or order it inside a batch.
- **Companions started with a preset** (a preset's `processes` list started before the game and stopped with it). Why not: one lifetime for two processes, while delve's L71 drive stops the server under a running client.
- **A multi-session `wait_for`** (any or all of several sessions' conditions). Why not: the parallel group gives that and also films, reads and presses at once.
- **Lockstep frame control across sessions** (pause or step every game together). Why not: a networked game's socket drops while paused (delve L79), and a .NET server cannot be paused.
- **The system clock** (`Time.get_unix_time_from_system()` in each bridge). Why not: millisecond fields through `GetSystemTime` at an unmeasured granularity, and adjustable under the drive (Time.xml L11); the QPC offset needs no new engine read.
- **A network conditioner** (survey idea 18, a `MultiplayerPeerExtension` wrapping the peer). Why not: delve's client speaks WebSocket to a .NET server (delve L32, `/ws`), outside Godot's multiplayer API, so it would not reach the user's networked game.
- **Concurrent tool calls from the client** instead of groups. Why not: whether Claude Code sends two calls to one MCP server at once is unmeasured, and a group's timing is the server's own, independent of the client.

## 6. Steps

Each step lands with its tests, docs (TOOLS.md, SKILL.md, ARCHITECTURE.md, README.md for a new capability, the glossary's new terms) and changelog bullet, and passes the build, `gdlint`, `gdcomplexity`, `gdtest`, the unit tests and its itest class.

## 7. Open questions

Settled by the recommended option under CLAUDE.md's autonomy rule: 1 (a), processes declared in `godot-mcp.json` `processes` and started by name with `run_process`, amending decision 11; 2 (a), no process stop inside a batch; 3 (a), `{parallel: [...]}` groups of 2 to 8 steps, one per session; 4 (a), the members still running are cancelled when one fails; 5 (a), `errorsElsewhere` on each step plus `no_errors {sessions}`; 6 (a), an output wait sees lines after the call starts, with `after` to look back; 7 (a), `{uiChanged: "now"}`; 8 (a), the server's clock with per-session offsets, adding a fourth element to watch points (amending decision 29's point shape). Every question is ruled. Steps 2 to 9 land on `main` one by one, with no feature branch, each with its own docs and changelog lines.

New terms, for the glossary when the design is adopted: new term: process session; new term: parallel group; new term: drive clock; new term: clock offset.

1. **Processes that are not Godot games.** (a, recommended) Declared in `godot-mcp.json`'s `processes` section and started by name with `run_process` as a process session; amends decision 11. How: part B. Worst case: a project's first server drive needs a profile edit (a tracked file) before it can start. (b) `run_process` takes any command line. How: `run_process {command: ["dotnet", "run", …]}` with no profile. Worst case: a client that auto-allows the godot tools now runs any program without a shell prompt. (c) None: the shell keeps them, and only documentation changes. Worst case: delve's background launch, port lock and four-second sleep stay as they are (delve L65, L71).
2. **Stopping a process inside a batch.** (a, recommended) Not in a batch: `stop_project` stays a lifecycle call, and delve L71's swap is four calls around a watch. How: section 3, Interactions. Worst case: the moment the server stops is a tool call's latency after the watch starts, which the watch records rather than controls. (b) A batchable `stop_process` runtime tool for process sessions only. How: `{tool: "stop_process", session: "server"}` as a step or a group member. Worst case: a second way to stop a session, and a batch that kills its own server mid-way leaves later steps failing on the clients. (c) Every lifecycle tool batchable. Worst case: a batch that launches and stops games blows its 300 s deadline on launches and preps.
3. **Steps at once.** (a, recommended) `{parallel: [...]}` groups of 2 to 8 steps, one per session, started in listed order. How: part D. Worst case: a group of long waits holds the batch's 300 s. (b) A `background: "<id>"` flag on a step and a later `{join: "<id>"}` step. How: a wait starts in the background, later steps run, the join collects it. Worst case: a forgotten join leaves a wait running into the next batch, and an entry's result arrives out of step order. (c) None: rely on the watch for transients. Worst case: no film of one game while driving another, and no input race between two players.
4. **A failed member of a group.** (a, recommended) Cancels the members still running, whose entries say `cancelled`. How: the bridge's `cancel` (ARCHITECTURE.md L48). Worst case: a wait that would have shown why the click failed is cut short. (b) The others run to their end. Worst case: a failed click leaves its partner wait running to its full timeout, up to 120 s.
5. **Errors from the batch's other sessions.** (a, recommended) Each step's entry carries `errorsElsewhere` by session, and `no_errors` takes `sessions`. How: part E. Worst case: a game that errors every frame repeats its errors on every step's entry, up to 20 a step. (b) Only `no_errors {sessions: "all"}`. Worst case: the agent learns there was an error but not which step caused it. (c) One batch-level `errors` by session at the end. Worst case: the error and its step are lined up by hand from `seq` numbers.
6. **Which lines an output wait sees.** (a, recommended) Lines after the call starts, `after` to look back by line number. How: part C. Worst case: a line printed between the agent's last read and the call is missed unless `after` is passed. (b) Every line the buffer holds (500 a stream). Worst case: a wait for `joined` is met at once by the previous run's line kept from before a restart. (c) Lines since this session's last output wait. Worst case: the window depends on hidden state, so the same call means different things in different turns.
7. **A UI change caused by another session.** (a, recommended) `{uiChanged: "now"}`, a baseline taken when the wait starts, used in a parallel group. How: part D. Worst case: used alone after the other session's input, it waits for a second change that never comes, and times out. (b) An input tool's `options.uiBaselineIn: ["guest"]`, taking the baseline in other sessions as it presses. Worst case: a new option on every input tool, and a press in one session reaching into another. (c) None: wait on an expression or use a watch. Worst case: the agent must know in advance which node will change, which `uiChanged` exists to avoid.
8. **A clock shared by every process.** (a, recommended) The drive clock with a per-session offset: `startMs`/`endMs` on batch entries, `metAt` on waits, a fourth element on watch points (changing decision 29's point shape), each with `clockErrorMs`. How: part F. Worst case: an offset no better than a frame (about 8 ms at 60 fps) if the spike finds no short round trip, which orders a network hop but not two events in one frame. (b) Batch stamps only (`startMs`, `endMs`), no game stamps. Worst case: "when did the guest show it" is bracketed by its wait step's end, a reply and a frame late. (c) None. Worst case: ordering across processes stays causal guesswork, as today.

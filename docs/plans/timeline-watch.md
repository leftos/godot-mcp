# Timeline watch: several values and signals over one window, then performance monitors

Design draft for the plan item "One timeline watch over several properties and signals, then performance monitors over a frame window (ideas 3, 2)" (GMCP-19), from ideas 3 and 2 of the [survey](../research/2026-09-29-godot-mcp-survey.md) (L105-113). Section 6's questions are ruled, and the rulings are [DECISIONS.md](../DECISIONS.md) decision 29, which wins where this file differs; steps 1 to 4 of section 7 are done, steps 5 and 6 open.

## 1. Problem

An agent that wants to know how a game moved over a stretch of time (when a dialog went, where the focus landed, when a beat started, whether a frame hitched) has four tools today, each for one thing: `monitor_property` samples one property of one node for up to 600 frames and is refused while the game is paused or a step runs (TOOLS.md L232-236); `wait_for {signal}` catches one emission of one signal (L238-242); `capture_frames` saves images at set moments (L226-230); a recording keeps a video (L368-372). Anything wider is a hand-written `run_script` that loops over `process_frame`, and while it runs no other tool call can reach the game.

**delve-the-dungeon** writes that script again for each drive:

- **The leaving screen's drive.** `docs/DEVELOPMENT.md` L70: "One `run_script` opens the thing, triggers the swap and samples every frame until it is over, returning only the rows that changed: the children of `Main/Safe/Screens`, whether the dialog is visible, hidden or freed (`is_instance_valid` first), and `gui_get_focus_owner()`'s path, each stamped with `Time.get_ticks_msec()`". Two of those three values are not properties (a node's children, the focus owner), and the third needs a freed node told apart from a hidden one. The same line: a swap to `Connecting` needs the server stopped from a background shell command started before the script, "since a tool call cannot stop a server while a script runs".
- **Motion and timing.** L93: "Motion is measured, not watched: `monitor_property` … returns one property's changes frame by frame in one call, and a `run_script` that samples several nodes or values every frame or every 0.1 s and returns the rows gives a throw's length, the lowest point a die reaches and when a merge starts." The same line: "Time is read off `Time.get_ticks_msec()`, never counted in frames: a frame is no fixed span". L73: the numbers of a mid-beat shot "are read from a sampling script, never from the shot".
- **Beat starts.** L75: `Combat.StartedBeatCount` is a public `int` the game added so a drive can `wait_for` it, and beats are lined up against `[play]` stamps in `client.log`: the game writes its own timeline because no tool keeps one.
- **Hitches.** L93: "a first-appearance frame time is measured twice …; the longest gap between two `process_frame`s, read off `Time.get_ticks_msec()`, is the measure" (the first roll's longest frame 834 ms cold, 35 ms warm; the launch's dice 637 ms without the warm-up, 8 ms with). `docs/fight-effects.md` L90: "Stamp both ends of a measured gap on the same clock", and `SmiteScratch` stamps the level 3 chain "about 420 ms late" from a first-draw hitch, so "a timing claim is measured in a real beat".
- **Scratch code instruments itself.** Seven scratch scenes stamp `Time.GetTicksMsec()` at the moments they check (`CrushBeatScratch`, `FightDiceScratch`, `FlightScratch`, `ProvokeScratch`, `SmiteBeatScratch`, `SmiteScratch`, `WindowScratch`, found with `rg` over `src/Delve.Client/Scratch`); `FlightScratch.cs` L858 keeps a per-frame trail of each ghost's centre.

**opening-hand** has less: `DuelBoardScratch.cs` L4088-4104 counts the process frames a playback runs for inside scratch code; its `docs/DEVELOPMENT.md` and `GODOT_CONVENTIONS.md` name no sampling script, `monitor_property` or hitch (`rg` for "every frame", "sampl", "monitor_property", "hitch", "stutter": no hits).

**The monitor half** has little direct evidence, as MAIN.md says. Issue #6 (closed) found quiet runs drawing at about 240 fps by reading a `wait_for`'s `frames` against its `elapsedMs` (720 frames in 3004 ms), which led to the 60 fps cap (DECISIONS.md L39). delve's frame gaps above are the rest, and its `docs/godot-feature-audit.md` L749-757 and L910 propose `Performance.add_custom_monitor` for `net/messages_queued`, `net/commands_in_flight` and `combat/events_pending`, "not used" today.

The survey's source servers: satelliteoflove's `watch_start`/`watch_collect` (a 200-event budget shared fairly per signal, per-field summaries of start, end, min, max, mean and slope, a time-sorted timeline) and Godot MCP Pro's `watch_signals` (a callable per signal per node; five or more arguments dropped) for idea 3; satelliteoflove's `godot_profiler` (a ring of 300 frames, whole-run aggregates, spike detection), gda's `perf monitors --frames` with budget verdicts and Godot MCP Pro's `get_performance_monitors` for idea 2 (survey L105-113). The survey's "Not verified" list names no engine question for either idea.

## 2. Proposed design

One runtime tool watches a set of tracks over one window: properties of nodes, expressions, signals, and performance monitors. It starts, runs in the bridge while any other tool drives the game, and returns a compact timeline when stopped or when its window ends. Each part below states the recommended option; section 6 holds the alternatives.

### The tool (questions 1, 2, 11)

`watch(action, tracks, window, options, session)`, a `RuntimeTools` partial, so `batch_drive` offers it with no change (ARCHITECTURE.md L127):

- `action: "start"`: checks the tracks, connects the signals, answers at once with `{startFrame, tracks}` (each track's resolved form: the node's path, the group's member count), and samples from the next frame until the window ends or `stop` comes.
- `action: "stop"`: ends the watch (or collects one whose window already ended) and answers the timeline. It takes no id: one watch runs per session, so a `batch_drive` whose steps are `watch start`, `click`, `wait_for`, `watch stop` works, though a later step cannot read an earlier step's result (TOOLS.md L322).
- `action: "run"`: start, wait for the window's end, answer the timeline: one call, as `monitor_property` is today. `run` replaces `monitor_property` (question 11): `watch {action: "run", tracks: {properties: [{node, property}]}, window: {frames: 60}}` is the same read.
- `options.call {node, method, args?}` on `start` or `run`: called in the watch's first frame, before the nodes process it, so the window counts from the method's entry, as `capture_frames` and `wait_for {gameMs}` take it (DECISIONS.md L70, decision 22). delve's L70 script opens the thing and triggers the swap itself; this is that, with no script.

A watch runs beside every other tool (question 2): input, `wait_for`, `capture_frames`, `get_game_state`, `run_script` and `frame_control`'s `pause`, `step` and `resume`. It does not take the `Time` module's `_running` guard, which makes `monitor_property`, a step and a capture exclude each other (`bridge/godot_mcp_time.gd` L86-88). Only a second `start` is refused while one runs or holds an uncollected result.

### What a call watches (questions 3, 4)

```
tracks: {
  properties: [{node, property}],              // as monitor_property and wait_for take them: position:y, modulate:a
  expressions: [{name, expression, node?}],    // wait_for's inputs: node, root, tree, Input, Engine
  signals: [{node | group, signal}],           // one node, or every member of a group at start
  monitors: ["frame_ms", "raster/total_draw_calls", "object/nodes", "Game/NumberOfNPCs", ...]
}
```

- A **property track** reads `node.get_indexed(property)` each sample, as `monitor_property` does (`godot_mcp_time.gd` L821-831), so a non-exported C# field Godot can marshal is read too (decision 21). A node freed during the window samples as the marker `{"$freed": true}` from then on, once, so "hidden" and "freed" read apart (delve L70's `is_instance_valid` first).
- An **expression track** runs a parsed `Expression` each sample with `wait_for`'s inputs (`EXPRESSION_INPUTS`, `godot_mcp_conditions.gd`), parsed once at start: `{name: "focus", expression: "root.gui_get_focus_owner()"}`, `{name: "screens", node: "Main/Safe/Screens", expression: "node.get_children()"}`, each Node in the value written as its path by the JSON module's rule (a null focus owner as null). `name` keys it in the result. delve L70's rows are three tracks.
- A **signal track** connects one variadic lambda per node (`func(...args: Array)`, as `_wait_for_signal` does, L880), so any argument count is kept; it records `[frame, node, args]` at each emission. `{group, signal}` connects every member of the group at start that has the signal; a member without it is listed in the start reply's `skipped`, not refused.
- A **monitor track** names a built-in monitor by its Godot name (`Performance.get_monitor_name`'s, such as `raster/total_draw_calls`, see below), a custom monitor by its id (`Performance.has_custom_monitor`), or `frame_ms`, the bridge's own frame time (question 10).

Limits, checked by the server before anything is sent: at most 32 property and expression tracks together, 16 signal tracks resolving to at most 200 connections, and 16 monitors.

### The window and paused games (question 5)

`window: {frames: N}` (1 to 7200) or `{gameMs: N}` (1 to 120000), exactly one, the ranges and the clock of `wait_for`'s `frames` and `gameMs` (TOOLS.md L241): unpaused process frames, or the sum of their scaled delta, so a window follows `Engine.time_scale` and a game's own timers. Left out on `start`, it is 600 frames; `run` needs it.

A watch may start on a paused game. Frames that find the tree paused are not counted toward the window and not sampled; the result lists them as `paused: [[fromFrame, toFrame]]`. A `frame_control` step's frames are unpaused frames, so a watch started while paused and then stepped samples exactly the stepped frames. A signal emitted in a paused frame (a `PROCESS_MODE_ALWAYS` node's) is still recorded. `monitor_property`'s rule that a game pausing itself ends the monitor (TOOLS.md L236) does not carry over: the watch waits it out, bounded by its deadline.

The watch's deadline is the window's own allowance, as `step`'s and `wait_for {frames}`'s are (10 s + 100 ms a frame; N + 10 s for `gameMs`), load-adjusted, plus the time a `start`ed watch spends paused, up to 600 s; a watch past it ends with `stopped: "deadline"` and what it has. A `run` is cancelled as a monitor is (`CANCELLABLE`, `godot_mcp_bridge.gd` L39-41).

### Sampling point (question 6)

Every track samples at `SceneTree.process_frame`, which is emitted each frame before the nodes' `_process`, paused or not (4.7.2 `scene_tree.cpp` L713, L719): the point `monitor_property` samples at, so a sample shows the state the previous frame left, physics ticks of this frame included. `options.unit: "physics"` samples at `physics_frame` instead (L649, L655), as `monitor_property`'s `unit` does. A signal is stamped with `Engine.get_process_frames()` at its emission. A value set in frame N's `_process` therefore appears at sample N+1, while a signal emitted beside it is stamped N; TOOLS.md says so, and the result's `frame` numbering (0 at the first sample) makes the offset one frame everywhere.

### Result shape (questions 7, 8)

```
{startFrame, frames, gameMs, wallMs, paused?: [[from, to]], stopped?,
 tracks: [{node?, property? | name?, first, last, changes, min?, max?, minAt?, maxAt?,
           points: [[frame, gameMs, value]], dropped?}],
 events: [[frame, gameMs, node, signal, args]], eventCounts: {"<node>:<signal>": n}, eventsDropped?,
 monitors: [{name, p50, p95, p99, max, maxAt, mean, over?: {budget, count, frames}, spikes: [[frame, value]]}],
 skipped?, errors?}
```

- `startFrame` is `Engine.get_process_frames()` at the first sample, so the timeline lines up with `get_game_state`'s `frame` and a `frame_control` reply's `processFrames`; every other `frame` counts from 0 there. `gameMs` on each point is game time since the first sample, the clock delta L93 asks for; `wallMs` is the whole window's wall time.
- A track's `points` are its change points: a sample kept only when it differs from the last kept one (numbers within 1e-6, `monitor_property`'s `changesOnly` rule, `_repeats`, L407), the first always kept. `first`, `last` and `changes` cover every sample; `min`, `max` and the frame of each only for a numeric track (a `Vector2`'s per component). delve's "lowest point a die reaches" is `min` and `minAt`.
- `events` is one list across every signal track in emission order, so the moment a dialog's `visibility_changed` fired sits beside the moment `StartedBeatCount` moved.
- The bridge applies the budgets as it records (each track's first 200 and last 50 change points with `dropped`, a bounded event list with full counts, values converted to JSON when kept) and sends monitor series summarised or as packed arrays, since the spike (section 8) measured an unbounded 16-monitor, 7200-frame series holding the game's main thread about 200 ms through `to_json`; the server shapes the result, the fair share of events and the 40000-character cut, where they are unit-testable in C#.

Budgets (question 8); the point and event caps are the bridge's, as it records, and the rest the server's:

- A value in a point or an event's argument over 200 characters is `{valuePreview, valueLength}` (the shape TOOLS.md L49 names), cut by the server.
- A track keeps its first 200 and last 50 change points (the bridge keeps a ring of the last 50 past the first 200); the ones between are counted in `dropped`, and `first`, `last`, `min`, `max` and `changes` still cover every sample. `tracks[].minDelta` (numeric tracks only) raises the change threshold for a value that moves every frame (a tween's `position:y` with `minDelta: 1`).
- `events` holds at most 300, shared fairly across signal tracks (satelliteoflove's rule): each track keeps its share of the earliest, a track under its share lends the rest; `eventCounts` counts every emission and `eventsDropped` the ones left out.
- A monitor returns its summary and at most 20 `spikes` (the frames furthest over `options.budgetMs` for `frame_ms`, else the highest), never the whole series.
- The whole result is at most 40000 characters of JSON, `get_game_state`'s list budget: past it the longest tracks' `points` are cut from the middle first and the cut is counted.

### Performance monitors (questions 9, 10)

A monitor is a track of the same watch, so a hitch sits on the same frame numbers as the signal that caused it (delve's first-draw hitch against a beat, fight-effects.md L90). The recommended set:

- **`frame_ms`**: the wall time between this frame's `process_frame` and the last one's, read with `Time.get_ticks_usec()`: the measure delve takes by hand (L93, "the longest gap between two `process_frame`s"). It covers physics, process, draw and the frame cap's wait, so a 60 fps quiet run floors at about 16.7 ms and a 420 ms pipeline compile reads as one frame of about 420 ms. `options.budgetMs` (default 1000 / the project's target fps: `Engine.max_fps`, else 60) gives `over: {budget, count, frames}`.
- **Built-in monitors read per frame** with `Performance.get_monitor`, named by 4.7.2's `get_monitor_name` strings (`object/nodes`, `object/objects`, `object/orphan_nodes`, `raster/total_draw_calls`, `raster/total_objects_drawn`, `raster/total_primitives_drawn`, `video/video_mem`, `pipeline/compilations_draw`, …; `main/performance.cpp` L165-237), which the bridge maps from the `Performance.Monitor` enum (`ClassDB.class_get_enum_constants`) through a table of its own, since `get_monitor_name` is not bound to scripts.
- **`time/fps`, `time/process` and `time/physics_process` are refused** with a pointer to `frame_ms`: the engine sets them once a second, `time/process` to the longest frame of the last second (section 3), so read per frame they repeat one value for a second and hide which frame was slow.
- **Custom monitors** by id, each read with `Performance.get_custom_monitor`, which calls the game's callable: game code, once a frame (question 13).

## 4. Edges

- **A node that does not exist at start.** A property or node-scoped expression track naming a missing node is refused up front, as `monitor_property` refuses it (TOOLS.md L236), with the not-found text every tool uses. A node that appears later is watched through an expression that looks it up (`root.get_node_or_null(...)`), which TOOLS.md shows.
- **Freed during the window.** A property track's node freed mid-window records `{"$freed": true}` once and stops sampling; an expression that raises from then on is recorded once as `{"$error": text}` (the bridge's error feed across the call, as `wait_for`'s expression reads it) and keeps sampling, so it recovers when the thing comes back. A freed emitter's signals simply stop.
- **Group members that join later** are not followed (question 4); the start reply's member count says who was connected.
- **A signal the node lacks** is refused for `{node, signal}`; for `{group, signal}` the members without it go into `skipped`, and a group where none has it is refused.
- **Paused, then stepped.** Covered by section 2: paused frames are skipped and listed; stepped frames count. A game held paused past the deadline ends with `stopped: "deadline"`. delve's rule that holding its tree paused across calls drops its socket (L78) is the game's.
- **Minimized window or low-processor mode.** Sampling at `process_frame` goes on; `render/*` monitors repeat the last drawn frame's values and `frame_ms` still measures. A result whose window drew no frame adds a `warning`.
- **A recording.** Game time advances 1/60 s a frame and the game runs uncapped (TOOLS.md L372), so `gameMs` is clip time and `frame_ms` measures how fast Movie Maker renders, not what a player sees: the result adds a `warning` when the session records, as delve L104 found for its own stamps.
- **`time_scale`.** `gameMs` follows it; `frame_ms` is wall time and does not.
- **Side effects.** An expression can call methods, and a custom monitor and `options.call` run game code, every frame for the first two. The convention says expressions only read; the server cannot check it.
- **Cost.** 32 tracks, 200 connections and 16 monitors each frame is a per-frame cost the spike measures; a watch whose sampling takes over 2 ms a frame on average adds a `warning` with its cost, since it moves the `frame_ms` it measures.
- **Restart, stop, detach.** A watch belongs to the bridge's run: `restart_project`, `stop_project` or a lost connection drops it, and a `stop` then says no watch runs. A dormant game answers nothing until joined.
- **An uncollected result.** A window that ended holds its timeline until `stop`; a `start` then is refused, naming `stop`, so a result is never dropped silently.
- **`batch_drive`.** `start` and `stop` are steps like any other; a `run` step blocks the batch for its window, and its allowance counts against the batch's 300 s.
- **The bridge's own nodes** cannot be watched, as no tool reads them.

## 5. Where the code goes and the tests

- **Bridge**: a new module `bridge/godot_mcp_watch.gd` (the `Watch` child): track resolution, the per-frame sampler on `process_frame`/`physics_frame`, the variadic signal catchers, the monitor reader and name map, the window clock (`advance_game_clock`, `godot_mcp_time.gd` L632, made reachable), and the raw buffers; the change-point test reuses `Time`'s `_json_equal`, made public. `godot_mcp_bridge.gd` gains the child, the `watch` command in `_command_handlers` and `watch` in `CANCELLABLE`, a few lines. `Conditions`' `check_property` and `parse_expression` (`godot_mcp_conditions.gd`) are public for the watch to share.
- **Server**: `src/GodotMcp.Server/Tools/RuntimeTools.Watch.cs` (`watch`, its validation and allowances), `WatchTracks.cs` (the `tracks` and `window` records), `WatchTimeline.cs` (the summaries, percentiles, spikes, budgets, the fair share of events and the 40000-character cut). Unit tests in `tests/GodotMcp.Tests/Tools/WatchValidationTests.cs` (limits, one window key, refused monitors, `minDelta` on a non-numeric track) and `WatchTimelineTests.cs` (change-point caps, `dropped`, fair shares, percentiles against a known series, the budget cut). `McpServerSmokeTests` gains the name and annotations, `BatchValidationTests` its batchable count, `ToolClassesTests` its class.
- **gdtests** (`tests/bridge/test_watch.gd`): the window clock across paused frames, freed nodes, the monitor name map against `ClassDB`, the group resolution and `skipped`, expression errors recorded once.

## 6. Open questions for the user

1. **The call's shape.** (a, recommended) One `watch` tool with `action` `start`, `stop` or `run`, one watch per session, `stop` taking no id. How: `start`, drive with any tools, `stop`; or `run` for a one-call window. Worst case: an agent that forgets `stop` leaves the result held until its next `start` is refused, and a watch lives only as long as the run. (b) One blocking call only, `monitor_property`-shaped, with `options.call` to start the action. How: `watch {tracks, window, options: {call}}`. Worst case: nothing else can run during the window, so a watch over a `click`, a `key` or a `wait_for` is impossible, which is delve L70's case (the swap is triggered by an input or a stopped server). (c) Two tools, `watch_start` and `watch_stop`, plus `monitor_property` kept for the one-call form. Worst case: three tools where one does, and the one-call form stays single-property. **Ruled (user, 2026-09-30): (a), one watch tool with start, stop and run.**
2. **What runs beside a watch.** (a, recommended) Everything: input, waits, `capture_frames`, `get_game_state`, `run_script` and `frame_control` `pause`/`step`/`resume`; only a second watch is refused. How: the watch never takes `Time`'s `_running` guard. Worst case: a step inside a watch is fine, but a `run_script` that blocks the main thread stalls the watch's frames with it, and the result shows the gap only as one long `frame_ms`. (b) Share `monitor_property`'s guard: exclusive with steps and captures. Worst case: a stepped sequence cannot be watched, which is the precise frame-by-frame case. (c) Beside input and waits only, refused while a step or capture runs. Worst case: the same loss as (b) for steps, for no engine reason (the sampler reads on `process_frame`, which a step emits). **Ruled (user, 2026-09-30): (a), everything runs beside a watch; only a second watch is refused.**
3. **What a track can name.** (a, recommended) Properties, expressions (with `wait_for`'s inputs), signals and monitors. How: section 2. Worst case: an expression with a side effect runs every frame. (b) Properties and signals only, idea 3 as the survey wrote it. Worst case: delve L70's focus owner and children list still need a sampling `run_script`, the thing the watch exists to replace. (c) (a) plus state keys read through `get_game_state`'s state methods each frame. Worst case: every frame calls game code in every marked node, and in a C# game the helper (about 50-80 µs a node warm); it waits for state-digest's C# step anyway. **Ruled (user, 2026-09-30): (a), properties, expressions, signals and monitors.**
4. **Signals on many nodes.** (a, recommended) `{node, signal}` or `{group, signal}`, the group resolved once at start. How: `get_nodes_in_group` at start, one lambda each. Worst case: cards dealt during the window are not connected; the agent watches the hand's own signal or a count instead. (b) (a) plus nodes that join the group or appear under a node during the window, followed through `SceneTree.node_added`. Worst case: a handler on every node added anywhere for the window's length, and a screen that rebuilds its rows (delve's lobby, L72) connects and reconnects each rebuild. (c) `{node, signal}` only. Worst case: a signal on every card is up to 200 tracks by hand, and a reordered hand (delve L77) changes their paths. **Ruled (user, 2026-09-30): (a), a node or a group resolved once at start.**
5. **The window's clock.** (a, recommended) `{frames}` or `{gameMs}` over unpaused frames, `wait_for`'s ranges; paused frames skipped and listed. How: section 2. Worst case: a watch started on a paused game that is never stepped or resumed runs to its deadline. (b) Wall milliseconds. Worst case: a window drifts from the game's timers under load or `time_scale`, the drift #25 reported for screenshots (DECISIONS.md L56). (c) Frames only. Worst case: a beat measured in seconds (delve's 1.90 s flight beat, L73) needs the agent to guess a frame count at a rate the game does not keep. **Ruled (user, 2026-09-30): (a), frames or gameMs over unpaused frames.**
6. **When each frame is sampled.** (a, recommended) At `process_frame`, before the nodes process, as `monitor_property` does; `unit: "physics"` for ticks; signals stamped with the frame they fired in. How: one handler, every frame, drawn or not. Worst case: a value set in frame N's `_process` shows at sample N+1 while a signal emitted beside it shows at N, a one-frame offset TOOLS.md must explain. (b) At `RenderingServer.frame_post_draw`, the state as drawn, aligned with signals. Worst case: no samples at all while the window cannot draw (minimized, low-processor mode), so a quiet run's watch can fall silent. (c) Both, chosen by an option. Worst case: two sampling rules to test and teach for a difference of one frame. **Ruled (user, 2026-09-30): (a), sampled at process_frame.**
7. **The result's layout.** (a, recommended) Per track: a summary and its change points `[frame, gameMs, value]`; signals as one merged event list; monitors as summaries and spikes. How: section 2. Worst case: to line up a property change with a signal the agent reads two lists by frame number. (b) One merged, time-sorted timeline of every change and emission (satelliteoflove's). Worst case: a tween's hundreds of changes interleave with and bury the three emissions that matter, and the caps cut both together. (c) Summaries only unless `options.points: true`. Worst case: the first call rarely answers "when", so most watches are run twice. **Ruled (user, 2026-09-30): (a), per-track change points and one merged event list.**
8. **A track that changes too often.** (a, recommended) Keep its first 200 and last 50 change points, count the rest in `dropped`, keep the summary over every sample, and offer `minDelta` per numeric track. How: section 2's budgets. Worst case: a one-frame spike in the middle of a long, busy track is in `max`/`maxAt` but not in `points`. (b) Decimate evenly to the cap. Worst case: a one-frame event between kept samples disappears from `points`, and the spacing hides where the change clustered. (c) Fail the watch when a track overflows. Worst case: the agent re-runs with narrower tracks and the moment is gone, unrepeatable for a first-draw hitch. **Ruled (user, 2026-09-30): (a), the first 200 and last 50 points with dropped and minDelta.**
9. **Monitors in the watch or their own tool.** (a, recommended) A `monitors` track kind in the same watch. How: `tracks: {signals: [...], monitors: ["frame_ms"]}`. Worst case: the watch's tool description grows by one kind, and a monitor-only question still names tracks and a window. (b) A separate `perf_window` tool with its own window. Worst case: a hitch cannot be tied to the signal or value change beside it except by comparing two results' frame numbers, and the two cannot run at once unless both run in the background. (c) Monitors first, the value and signal watch later (the plan line's order reversed). Worst case: delve's strongest evidence (L70, L93 sampling) waits behind the weakest (#6). **Ruled (user, 2026-09-30): (a), a monitors track kind in the same watch.**
10. **How a frame's time is measured.** (a, recommended) `frame_ms` from `Time.get_ticks_usec()` between `process_frame` emissions, plus the built-ins that change per frame; `time/fps`, `time/process` and `time/physics_process` refused with a pointer to `frame_ms`. How: section 2. Worst case: `frame_ms` includes the cap's and VSync's wait, so it shows a slow frame but not whether CPU or GPU made it slow. (b) (a) plus per-viewport render CPU and GPU time, the bridge turning `viewport_set_measure_render_time` on for the root viewport during the window. Worst case: the watch changes a rendering setting the game did not ask for, and GPU time rises under the 60 fps cap's low power state (RenderingServer.xml L4105-4110), so a quiet run's reading misleads. (c) Godot's `time/*` monitors as they are. Worst case: they hold the last second's maximum, so a 420 ms hitch shows up to a second late and on no particular frame. **Ruled (user, 2026-09-30): (a), frame_ms, with time/fps, time/process and time/physics_process refused.**
11. **`monitor_property`.** (a, recommended) Replaced: `watch {action: "run"}` covers it, and `monitor_property` is removed in the step that lands `run`. How: one tool for watching; marked agent files lose the name at the next install. Worst case: delve's DEVELOPMENT.md L93 and any unmarked agent file name a tool that is gone until `godot-mcp-docs-sync` runs. (b) Kept as it is beside `watch`. Worst case: two tools for one job, the `Time` guard keeps a kind only it uses, and its flaky test (GMCP-28) stays. (c) Kept as a thin form that forwards to `watch run`. Worst case: a second schema to keep in step with `watch`'s for no new capability. **Ruled (user, 2026-09-30): (a), monitor_property is replaced by watch run.**
12. **C# members and events Godot cannot read.** (a, recommended) Not in the first version: property tracks read what Godot's `get` reads (every marshalable C# field, decision 21), `[Signal]` delegates connect as Godot signals, and a record or `List<T>` member reads null with a hint naming `cs_get` and the state digest. How: no helper call per frame. Worst case: delve's `Combat.ShownView` (a record) cannot be watched; the game keeps Godot-visible members for what drives watch, as it did for `StartedBeatCount` (L75). (b) `cs` tracks read through the C# helper each frame. Worst case: the helper's 2 s cold load at `start`, and about 50-80 µs a member each frame on the main thread, which moves the `frame_ms` being measured. (c) Plain C# `event`s caught through the helper as well. Worst case: the helper subscribes a delegate per event, with its own lifetime and unsubscribe rules, for a pattern neither game drives by. **Ruled (user, 2026-09-30): (a), not in the first version.**
13. **Annotations and tool class.** (a, recommended) `Destructive = true`, since expressions, custom monitors and `options.call` run game code, and a `ToolClasses` override to `read`, as `get_game_state` and `cs_get` have. How: the read-only agents that list `monitor_property` today (Explore, the playtester, the reviewers) are swept `watch` at install. Worst case: a client that asks before every destructive tool asks before each watch. (b) `wait_for`'s annotations (neither read-only nor destructive, the `drive` class). Worst case: the read-only agents lose the watching they have today through `monitor_property`. (c) `ReadOnly = true`, as `monitor_property` is. Worst case: a client that auto-approves read-only tools runs expressions and custom monitors every frame unasked. **Ruled (user, 2026-09-30): (a), destructive with a read override.**

- **`frame_ms` measures a hitch as one frame**, the delay plus about 1-3 ms, and keeps measuring while nothing draws; the frame after it reads near zero, because `OS::add_frame_delay` clamps its target to `now - delay` (`core/os/os.cpp` L730-739) and skips that frame's wait. A quiet run's idle frames sit within ±1 ms of 16,667 µs: 754 of 1802 exceed 16,667 µs, none 18 ms; a budget of exactly 1000 / `max_fps` flags 42% of idle frames.
- **Monitors.** Over 600 frames only `memory/static` changed every frame, and that is the sampler's own buffers; object and render counts change in steps, `time/*` every 60 frames and right after a frame over 1 s (`time/process` read 1.645 s after a first 3D draw). A 2D-only UI reads 19 draw calls, 53 objects and 1120 primitives in both renderers: 4.7.2 counts the canvas (`renderer_viewport.cpp` L965-968; GLES3 `rasterizer_canvas_gles3.cpp` L1318-1321), and `RenderingServer.xml` L1675's "only 3D" note is stale. `pipeline/compilations_*` are cumulative (Forward+: canvas 2 → 3 on a new canvas shader, surface and specialization 0 → 3 on a first 3D draw, held to the end) and always 0 under Compatibility (`rasterizer_canvas_gles3.h` L377, `rasterizer_scene_gles3.h` L878), which both fixtures use; `engineArgs: ["--rendering-method", "forward_plus"]` shows them in a quiet run.
- **C#.** `[Signal]`s of 0, 3 and 6 arguments reach a `func(...args: Array)` lambda with `[]`, `[int, String, Vector2]` and `[int, float, String, Vector2, Node, Array]`, stamped with the emitting frame; a plain C# `event` is no signal (`has_signal` false; `ScriptSignalsGenerator.cs` L117-122). Rest parameters in lambdas are 4.7.2 syntax (`gdscript_parser.cpp` L1699-1731, L3765). `get` and `get_indexed` read a private int, float and Vector2 and an internal property every frame, none of them in `get_property_list`.
- **Offset.** A value set and a signal emitted in frame F's `_process`: the `process_frame` sample at F reads F-1, the signal is stamped F, a `frame_post_draw` sample at F reads F. Question 6's offset is as written, and a post-draw sampler would have taken no samples in the minimized and low-processor rows.
- **Payload.** 16 monitors × 7200 frames is 755,365 bytes of JSON; through `to_json` and `JSON.stringify`, as a `run_script` reply goes, it holds the game's main thread 190-210 ms (the next run's `frame_ms` max read 209 ms), and the reply reached the next call 244-472 ms after `execute` returned. Stringified as `PackedFloat64Array`s it takes 60-71 ms; summarised in GDScript (sort, p50/p95/p99/max/mean) 3-4 ms; as change points it is 7,551 of 115,200 samples. 32 tracks × 250 kept Vector2 points is 212,545 bytes, 109-119 ms through `to_json`.
- **What this changes in section 2.** Rulings 6 and 10 (a) stand. The split of work moves toward the bridge: it keeps each track's first 200 and last 50 points and a bounded event list with full counts, converts a value to JSON when it is kept (+12 to +142 µs a frame), and summarises monitor series itself (3-4 ms) or sends them as packed arrays, so no `stop` sends an unbounded result or stalls the game for its conversion. Ruling 8 fixed the numbers, not the side that applies them, so this is no reversal. The `frame_ms` budget default needs headroom over one frame's length (step 4 decides it), and TOOLS.md's `watch` section says a hitch is one frame with a near-zero frame after it, that `render/*` counts 2D, and that `memory/static` moves while a watch records.

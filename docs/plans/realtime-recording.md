# Real-time recording: the game's window as a player sees it

Design draft for Linear GMCP-6 (GitHub #61), "record: only Movie Maker, which runs faster than real time", in the project "Ideas from the survey and the projects", whose description says #61 "needs a design pass". The issue carries no survey idea number: the [survey](../research/2026-09-29-godot-mcp-survey.md) lists video recording as a capability only this server has (L67, "Y (MP4 clips)"; L212, "MP4 recordings with marks and idle drop"), and no surveyed server records in real time. Every question in section 7 is ruled.

Status: the spike (section 6's step 1) is done and on `main` (cd63e9b); its results are section 8, which settles question 3 as a refusal of quiet sessions. Step 2, the helper in the repo, is done, and so is step 3, video on a run (3a and 3b, section 6); next is step 4, ending with the session.

## 1. Need

A recording today is Godot's Movie Maker, chosen at launch: `run_project` `options.record` adds `--write-movie <…>.avi --fixed-fps 60 --quit-after 36000` (ARCHITECTURE.md L71), `record_mark` notes movie frames through the bridge's `movie_frame` (L116; `bridge/godot_mcp_bridge.gd` L589-594), and the run's end cuts each start-stop pair to an MP4 with ffmpeg (`RecordingCut`). Under Movie Maker, game time advances 1/60 s a frame whatever the wall clock does, and the main loop skips its frame delay, so the game renders as fast as the machine allows (TOOLS.md L381: "the game runs uncapped"). Two things follow that an agent cannot change today:

- **A step that measures time on the wall clock is wrong under a recording.** The issue: Movie Maker "renders faster than real time (11 ms a frame on this machine). A step that measures a motion on `Time.GetTicksMsec()` throws under it (`FightScratch` read a 0.35 s flight as 222 ms)". The numbers agree with the cause: 350 ms × 11 / 16.7 ≈ 231 ms. delve-the-dungeon `docs/DEVELOPMENT.md` L106 (at 843bf6a): "the server's recording is Movie Maker too, so a step that measures a motion still throws there, and such a step's numbers are read from a run without `record`".

  The spike (section 8) found Movie Maker off the wall clock in both directions, not only faster: delve's `FightDiceScratch` at 1080p Forward+ ran at 41 to 43 fps under it and read the 0.35 s flight as about 0.5 s. The need is a recording at real time.
- **The clip is not what a player sees.** A hitch, a dropped frame or a slow first draw never shows: every frame lasts 1/60 s in the clip however long it took. delve L105: "A clip for the user is recorded with the user-level `video-capture` skill (`/video-capture`: the real window, in real time, through Windows.Graphics.Capture), never Movie Maker (`--write-movie`). Movie Maker renders faster than real time, so what it shows is not what a player sees".

**The workaround written by hand.** delve L106 records "the windowed client while it plays, the game untouched" with `~/.claude/skills/video-capture/scripts/Record-Window.ps1 -Title 'Delve the Dungeon (DEBUG)' -Seconds 50 -Out .tmp/<name>.mp4 -Sheet`, outside the server: the agent finds the window by title (which carries `(DEBUG)` only when the client runs from `Godot_console.exe --path`), guesses a fixed length up front, starts the drive "five seconds after the recording", and crops the title bar off by hand (`-vf crop=1920:1080:1:31`, since the capture is 1922 × 1112 for a 1920 × 1080 client). The same line records why the two ffmpeg routes were dropped: "`ddagrab` records whatever is on top of that part of the screen (two recordings of the app covering the game), and `gdigrab` gives black for the Vulkan window". L107 adds that `PrintWindow` of a GPU-drawn window "that is off screen or minimized comes back black".

**opening-hand** records only through the server: `docs/DEVELOPMENT.md` L62 (at b527905) is the Movie Maker recipe ("The recording runs at a fixed 60 fps, so waits count clip time"), and L53 writes PNG frames with `--write-movie … --fixed-fps 10` without the server. It has no real-time need written down.

So the need is: a recording an agent starts and stops on a session it already drives, run or attach, in which the game keeps its own clock and the file shows the window as it was shown, with the game's sound, cut to the client area, with no window title to guess and no length to fix in advance.

## 3. Design

A real-time recording is started and stopped on any live session, run or attach, with the same `record_mark` an agent already uses; the server captures the game's window through Windows.Graphics.Capture in a helper process it ships, pipes the frames into the ffmpeg it already locates, and records the game process's own audio. Movie Maker stays as it is for frame-exact recordings. Each part states the recommended option; section 7 holds the alternatives.

### The call (question 2)

`record_mark(mark, options, session)`, `options` new and taken by `start` only:

- **On a session launched with `options.record`** (a movie recording): unchanged. `options` there is refused: "options belong to a real-time recording; session '<s>' records with Movie Maker, whose marks take none."
- **On any other live session**, a real-time recording. `start` captures until `stop`, and answers once ffmpeg has opened its encoder (about 0.1 to 0.3 s after the first frame), so the agent's next action is in the file: `{mark: "start", mode: "realtime", path, width, height, fps, audio, encoder, warning?}`.
  `stop` ends the capture, finalises the file and answers `{mark: "stop", mode: "realtime", clip: {path, seconds, frames, averageFps, width, height, audio}, warning?}`. A movie mark keeps `{mark, frame, seconds}` and gains `mode: "movie"`.
- `options {fps, audio, maxSeconds}`: `fps` 1 to 60, default 30 (question 8); `audio` default true (question 4); `maxSeconds` 1 to 600, default 600, the same 10 minute cap the movie route has.
  `audio` arrives with step 5: until then the key is refused as unknown and the results carry no `audio` field.
- One real-time recording per session; several sessions may record at once.

Refusals, each before anything starts:

- `A real-time recording is already running in session '<s>' (started <n> s ago); record_mark stop first.`
- `No real-time recording is running in session '<s>'; record_mark start first.`
- A minimized window: `The game's window is minimized, so Windows composes no picture of it; restore it, then record_mark start again.`
- A quiet session, unless the spike shows the hidden desktop is captured (question 3): `Session '<s>' is quiet, so its window is on the server's hidden desktop, which a real-time recording cannot see. Launch it with options.quiet: false (options.mute: true keeps it silent), or with options.record for a Movie Maker recording.`
- No ffmpeg: `A real-time recording needs ffmpeg: set FFMPEG_PATH to ffmpeg.exe, or install it with winget install Gyan.FFmpeg.` (Unlike the movie route, there is no file to keep without it.)
- No helper or an older Windows: `A real-time recording needs Windows 10 1903 or later and capture/godot-mcp-capture.exe beside the server (<path>); reinstall godot-mcp.`
- A headless session (`run_scratches`' games, `preview_scene`): `Session '<s>' is headless and has no window to record.`

Not refused, warned: audio asked on a muted or quiet session (`no audio: session '<s>' renders no sound (options.mute or a quiet run), so the clip has no audio track`); an average below 90% of `fps` (`the capture got <a> fps of <fps>: the machine was busy, so the clip repeats frames`); a window resized mid-capture (`the window changed size at <t> s; the clip ends there`).

### How it captures (questions 1, 6, 7, 9)

- **The window.** The bridge's hello gains `hwnd`, `DisplayServer.window_get_native_handle(WINDOW_HANDLE)` as a decimal, kept on the session beside `GameProcessId`; no title search (delve L106's `(DEBUG)` trap, the skill's `FindWindow` trap at SKILL.md L124). The server crops to the client area: the capture's origin is the window's extended frame (`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`), the client's is `ClientToScreen` of (0, 0), both in physical pixels; the helper copies only that rectangle to its staging texture, so the clip's size is the window `run_project` reports, as a screenshot's is, and no CPU crop runs (question 9).
- **The helper.** `godot-mcp-capture.exe`, a port of the skill's `WgcCapture` into this repo as `src/GodotMcp.Capture/` (net10.0-windows10.0.26100.0, Vortice), published into the install folder's `capture/` beside `godot-mcp.exe` and found by `Installation.FindCaptureHelper` (question 6). Arguments: `--hwnd <n> --crop x,y,w,h --fps <n> --until-file <deadline> [--audio-pid <pid> --audio-pipe <name>]`, plus `--probe`.
  It writes raw BGRA at a constant rate on stdout (the newest frame repeated when none arrived), pads an odd side by a black pixel, ends when the deadline passes, the window closes or resizes (exit 3), and prints `N frames in X s` when its capture ended after the first frame; a failure before the first frame prints none. The server's `clip.frames` is the bytes it copied divided by the frame size, not that line.
- **The encode.** `helper | ffmpeg -use_wallclock_as_timestamps 1 -f rawvideo -pix_fmt bgra -video_size WxH -framerate <fps> -i - [-f s16le -ar 48000 -ac 2 -i \\.\pipe\<name>] -c:v <encoder> -fps_mode vfr <stem>-realtime.mkv`, the skill's measured pipeline (wall-clock stamps keep a slow capture at its real length, SKILL.md L35, L131).
  The encoder is chosen once per server by a one-frame test encode: `h264_nvenc` when it passes (a frame never touches the CPU encoder), else `libx264 -preset ultrafast -pix_fmt yuv420p`, else `h264_mf`; `hevc_nvenc` past 4096 px (question 7).
  An encoder that passes its probe but fails as the recording starts (ffmpeg ends, or stops taking frames: NVENC with no capable device, or past its session limit) is followed by the next one that probes usable, in the same order, with the failed encoder's lines kept in the log, and later starts on that ffmpeg skip it until the server restarts; a failure after the first frame is not retried and is reported at `stop`. An NVENC session-limit failure after the first frame is unverified.
  The file is Matroska while it records, so a server killed mid-capture leaves a playable file; `stop` remuxes it to `<stem>-realtime.mp4` with `-c copy -movflags +faststart` and deletes the `.mkv`.
- **Ending.** `stop` moves the deadline file to now, as the skill's `-Stop` does; the helper ends, ffmpeg drains and exits, then the remux. `maxSeconds` is the deadline the helper is started with. The session's end finalises a running capture the same way: `stop_project`'s `recording` gains `clips` for it (a session that was not a movie recording now carries `recording` when it recorded in real time), `restart_project`'s `previousRecording`, `list_sessions`' `recording` (`{mode: "realtime", path, startedSeconds}` while it runs), and `detach_project` gains `recording?`. A game that exits ends the helper (its WGC item closes) and the clip is kept.
- **Processes and ceilings.** The helper and ffmpeg start through `ToolProcess.Start`, which opts into two stdio modes: `PipeStandardOutput` hands the helper's stdout to the server (only its stderr is logged), `KeepStandardInput` keeps ffmpeg's stdin open for the server to write; the server copies the one into the other, both trees in `OwnWork`.
  `start`'s wait for ffmpeg to open its encoder (its first `-progress` report, from `-progress pipe:1 -stats_period 0.1 -nostats`) is 10 s of load-adjusted time; ffmpeg's log holds its errors and the remux's output, not the status line. The helper and ffmpeg run under a ceiling of 10 s + `maxSeconds` + 60 s, a helper probe under 30 s, an encoder probe under 10 s and the remux under `max(60 s, a tenth of the clip)`, each with the backstop and the stall kill.
  A failed capture answers the helper's or ffmpeg's last lines and its log: `recordings/<stem>-capture.log` and `<stem>-ffmpeg.log` (the remux appends to the latter), with `<stem>` the recording's `<UTC yyyyMMdd-HHmmss-fff>-<session>-realtime`, and `<stem>-probe-<guid>.log` for a start's encoder probes. There are separate logs because a `ToolProcess` log is opened with `FileShare.Read`, so two running processes cannot share one.

### Audio (question 4)

The game's own process tree through WASAPI process loopback, `--audio-pid` the hello's `pid`: the user's other sound and notifications never reach the track (SKILL.md L78). A quiet run (Dummy driver) and a muted one (`options.mute` mutes Master, which zeroes the bus after its effects) render silence, so the clip has no audio track and a `warning` says why; the track is never a silent one passed off as sound.

### Interactions

- **Bridge timing.** The bridge treats a run as a recording only under Movie Maker (`clip_fps`), so durations, `wait_for`, `drag`, `stress_input` gaps and `hover`'s wait stay real time and no `clipMs` appears; nothing in the bridge changes but the hello field.
- **`batch_drive`.** `record_mark` is already a `RuntimeTools` partial, so `start` and `stop` are batch steps; a recording a batch started keeps running after it.
- **`frame_control`.** A paused game records as a held still; a step's frames are recorded at the rate they were drawn. The clip shows what was on screen, which is the point.
- **Watch.** `frame_ms` measures the game's frames with the capture running; the capture lives in another process, so its cost to the game is GPU contention only (unmeasured). Timeline-watch's recording warning (timeline-watch.md L137) applies to movie recordings only.
- **Screenshots and `capture_frames`** are the engine's frames and unchanged; a non-embedded popup (`embed_subwindows` off) is a separate OS window that the window capture does not hold, while `grab_frame` pastes it into screenshots (decision 15).
- **Attach and join.** An attached or joined game gives its `hwnd` in its hello as a run does; a quiet attach is parked off-screen, and whether WGC sees a parked window is the spike's.
- **Error feed.** A real-time recording raises nothing into the game; helper and ffmpeg failures are the tool's errors.

### Where it lives

- `src/GodotMcp.Capture/` (new): the helper, with `CaptureArgs.cs`, `WindowCapture.cs`, `ProcessAudioCapture.cs`, `Deadline.cs` from `WgcCapture`, plus the crop.
- `src/GodotMcp.Server/Session/RealtimeRecording.cs` (state, deadline file, the two processes, the outcome), `RealtimeEncode.cs` (ffmpeg arguments, the encoder probe and choice; pure where it can be), `WindowRect.cs` (the DWM and client rectangles, the crop); `Installation.cs` (`FindCaptureHelper`); `GodotSession` (`Hwnd`, the running recording, finalising at stop, restart, exit and detach); `Tools/RuntimeTools.Record.cs` (the branch and `options`); `ProjectTools.cs` (result fields).
- `bridge/godot_mcp_bridge.gd`: `hwnd` in the hello.
- `run.ps1` publish and `tools/package.ps1` (`Assert-PublishLayout` gains `capture/godot-mcp-capture.exe`), `tools/install.ps1` and `tools/install-release.ps1` (the folder is mirrored as a whole today; the check names the new file).

## 4. Costs and risks

- **In the game.** Nothing per frame in the game process: the capture copies the composited surface in the helper, and NVENC encodes on the GPU. On a machine without a hardware encoder, `libx264` at 1080p30 takes CPU from the game and from every other agent's gate, which moves the game's own frame times, the thing the recording exists to show honestly; the `averageFps` warning names it. Unmeasured: the spike measures `frame_ms` with and without a capture, per encoder.
- **Wire.** One integer in the hello; no frames cross the bridge.
- **Disk.** One clip per start-stop pair, capped at 10 minutes. Bitrate unmeasured; the Matroska intermediate is the clip's size, not raw.
- **Per-machine failures.** No NVIDIA GPU, or the driver's concurrent NVENC limit reached by several recording sessions (unmeasured here): the probe falls back to `libx264`. A DPI-unaware rectangle read comes out short at 150% scaling (SKILL.md L139): the server reads the rectangles DPI-aware. Windows older than 1903 or 20348: no capture, or no process audio, refused or warned. A user-level `ffmpeg` without `libx264` and no GPU encoder: `h264_mf`, else refused. The yellow capture border shows on the user's screen around a visible game while it records.
- **What a careless agent can do.** Start and never stop: the clip ends at `maxSeconds` and the file is kept. Start on every session of a three-client drive: three helpers and three encoders, the fallback encoder loading the machine. Record a session it launched with `quiet: false` while the user works: the game's window and its border sit on the user's desktop for the whole drive (the capture does not need it in front, so the user can keep working over it). Record a window covered by private content: WGC captures the game's own surface only, unlike `ddagrab`, which would record whatever covers it.
- **Testing.** `run.ps1 itest` runs on its own hidden desktop (README glossary, "Hidden desktop"), so a visible-window itest depends on the same unmeasured fact as quiet runs; if WGC cannot see a hidden desktop, the itest class runs only on the visible desktop: `RealtimeRecordingTests` is in the `capture` group, which `$itestVisibleGroups` runs on the user's desktop, not in the `recording` group.

## 7. Open questions

Ruled by the owner: 1 (a), the Windows.Graphics.Capture helper piped into ffmpeg; 2 (a), `record_mark` on any session not launched with `options.record`; 3 (a), quiet sessions allowed if the spike shows WGC sees the hidden desktop, else refused with the fix; 4 (a), the game process's own audio; 5 (a), Movie Maker kept as it is; 6 (a), a separate `godot-mcp-capture.exe` in the package; 7 (a), NVENC, else libx264 ultrafast, else h264_mf; 8 (a), 30 fps by default, `options.fps` 1 to 60; 9 (a), cropped to the client area. Every question is ruled.

1. **The capture route.** (a, recommended) Windows.Graphics.Capture of the game's window in a helper process, piped into ffmpeg. How: section 3. Worst case: a quiet run's window may be out of its reach (the spike's question), and a machine without a hardware encoder spends CPU the game needed. (b) The bridge reads each drawn frame and pipes it to ffmpeg from the game. How: `frame_post_draw`, `get_image` (Compatibility) or `texture_get_data_async` (Forward+), `OS.execute_with_pipe`. Worst case: the readback and an 8 MB write per frame on the game's main thread change the frame times the clip is meant to show. (c) ffmpeg `ddagrab` over the window's rectangle. How: no new binary, region from `GetWindowRect`. Worst case: any window over the game, a notification or the user's own work, is in the clip (delve L106). (d) Movie Maker paced to the wall clock. How: the bridge sleeps each frame until its wall time. Worst case: `delta` stays fixed, so a slow frame still bends the game's timing and the clip never shows a hitch.
2. **How an agent starts one.** (a, recommended) `record_mark start`/`stop` on any session not launched with `options.record`, with `options {fps, audio, maxSeconds}` on start; `stop` returns the clip. How: section 3. Worst case: an agent that meant a frame-exact recording and forgot `options.record` gets a real-time clip; the result's `mode` says which. (b) A new tool, `record_window {action: start | stop, options}`. How: the same behaviour under its own name; `record_mark` stays Movie Maker's. Worst case: two recording tools to choose between, a new name for every agent file at install, and `record_mark` on a plain session still refused. (c) A launch option, `options.record: "realtime"`, capturing from launch with marks cutting it as Movie Maker's are. How: one capture per run, clips cut at the end. Worst case: an attach cannot record, the whole run is captured and encoded for a clip of seconds, and the clips arrive only when the session ends.
3. **Quiet sessions.** (a, recommended) Allowed when the spike shows WGC sees the hidden desktop (video only, since a quiet run is silent); otherwise refused with the fix (`options.quiet: false`, `mute: true` to keep it silent). How: the refusal text in section 3. Worst case: if refused, every real-time recording puts a window and the capture border on the user's desktop for the drive. (b) A quiet session falls back to the bridge's frames (question 1's (b)) where WGC cannot see it. How: two capture routes behind one call. Worst case: a quiet clip's game pays the readback per frame and the two routes' clips differ (chrome, popups). (c) Always refused, whatever the spike finds. How: a real-time recording means a visible window. Worst case: the quiet default (decision 10, DECISIONS.md L38) never meets recording, and every recorded drive is a visible one.
4. **Audio.** (a, recommended) Process loopback of the game's tree; no track and a warning on a quiet or muted session. How: the helper's audio pipe. Worst case: a recording an agent wants silent on the user's speakers but with sound in the file cannot have both: `mute` silences the file too. (b) The bridge adds an `AudioEffectCapture` to the Master bus for the recording's length and streams its frames to the server, muxed at `stop`. How: the effect runs before the bus mute and the Dummy driver mixes in real time, so quiet and muted runs keep their sound in the file. Worst case: a bus effect is added to the game's own layout while it records (a game that saves its bus layout then saves it), PCM crosses the wire (192 KB/s), and the Dummy driver's clock drifts from the video's (unmeasured). (c) No audio. Worst case: a fight's `Sounds/<Kind>` beat (delve's sound scratches) cannot be checked from a clip.
5. **Movie Maker.** (a, recommended) Kept as it is beside the real-time route, for frame-exact recordings of any run, quiet and minimized ones included. How: `options.record` unchanged. Worst case: two recording kinds to teach, and an agent picking the wrong one for a timing check. (b) Kept, and paced to the wall clock while the machine keeps 60 fps. How: question 1 (d) applied to `options.record`. Worst case: its clips look real-time and are not under load, so the difference from (a)'s real-time route is harder to explain. (c) Removed. How: `options.record`, `dropIdle`, the AVI cut and the bridge's clip time go. Worst case: no frame-exact, quiet or minimized recording remains, and opening-hand's L62 recipe and every movie-based drive change.
6. **Where the capture code runs.** (a, recommended) A separate `godot-mcp-capture.exe` in the package's `capture/` folder. How: section 3. Worst case: a second project, a second publish and a file the install must carry; a stale or missing helper is a refusal. (b) Inside the server. How: the server's framework becomes `net10.0-windows10.0.26100.0` with Vortice. Worst case: a D3D or WinRT fault ends the MCP server and every session it holds. (c) The user-level `video-capture` skill's `WgcCapture` when installed. How: the server looks for it under `~/.claude/skills`. Worst case: the public server records in real time only on this machine.
7. **The encoder.** (a, recommended) `h264_nvenc` when a one-frame test encode passes, else `libx264 -preset ultrafast`, else `h264_mf`. How: probed once per server. Worst case: on a machine with no GPU encoder the CPU encode competes with the game. (b) Always `libx264`. How: the movie cut's encoder. Worst case: every recording spends CPU even on a machine with NVENC, and the game's frame times move with it. (c) A fast lossless capture, encoded to H.264 at `stop` as the movie cut is. How: `-c:v ffv1` or `utvideo` while recording. Worst case: a minute of 1080p30 is gigabytes on disk, and `stop` waits for the encode.
8. **The frame rate.** (a, recommended) 30 by default, `options.fps` 1 to 60. How: the skill's default. Worst case: a fast motion at 60 fps loses every other frame unless asked. (b) 60 by default. How: matches a quiet run's cap and Movie Maker. Worst case: twice the copy and encode cost on every recording, and a busy machine falls short of it more often. (c) The game's own frame rate, each drawn frame once. How: the helper writes on WGC's frame-arrived event only, with wall-clock stamps. Worst case: a visible run at 240 Hz writes 240 frames a second.
9. **Window chrome.** (a, recommended) Cropped to the client area, the size `run_project` reports. How: the DWM and client rectangles, cropped in the helper on the GPU. Worst case: a game that draws in its own title bar (none of the user's) loses it. (b) The whole window as WGC gives it. How: no crop. Worst case: every clip carries the title bar and border, and screenshot and clip coordinates differ by 31 px (delve's hand crop, L106).

Terms in the glossary (`docs/README.md`): **Real-time recording** (a recording of the game's window on the wall clock, started and stopped by `record_mark` on a session not launched with `options.record`), **Movie recording** (the Movie Maker recording `options.record` launches; the glossary's "Recording, mark, clip" entry is reworded to name both).

**Capture helper** (`godot-mcp-capture.exe`, the process that captures a window through Windows.Graphics.Capture and the game's audio through process loopback).

Decisions this design touches without reversing: decision 9's in-engine recording stays (L28); decision 10's quiet default holds, and question 3 decides how recording meets it (L38); decision 13 kept "recording" for the video (L52), and this adds a second kind of it; decision 15's hidden desktop and parking (L57) are what the spike tests; decision 30 (L127): no patched Godot is needed.

## 9. Rulings from the build (step 3)

- **`start` answers when ffmpeg has opened its encoder**, its first `-progress` report about 0.1 to 0.3 s after the first frame, not when the helper's first bytes arrive: the agent's next action is then in the file. That wait is 10 s of load-adjusted time, and the encoder probe is outside it.
- **The fallback moment.** An encoder that passes its probe but ends ffmpeg, or stops it taking frames, as the recording starts is followed by the next usable encoder in the order of section 3, and later starts on that ffmpeg skip it until the server restarts; every one failing refuses the start with ffmpeg's last lines and the logs the cached verdicts came from. After the encoder has opened there is no retry: a failure is reported at `stop`.
- **A start that does not go ahead** (refused, failed or cancelled) deletes its `.deadline`, `.deadline.tmp` and `.mkv` and keeps its logs. `detach_project` during a `start` lets the start answer and ends its capture at once, the `.mp4` finished. The server's shutdown ends every real-time recording and waits for its `.mp4` within the 10 s shutdown cap.
- **The seams.** `SessionRegistry.Realtime` (`RealtimeEnvironment`) is the environment seam the unit tests replace; the movie session's `options` refusal is an itest, since it needs a real Movie Maker run.
- **The ceilings** (load-adjusted, each with the backstop and the stall kill): the helper and ffmpeg 10 s + `maxSeconds` + 60 s, the helper's size probe 30 s, an encoder probe 10 s, the remux `max(60 s, a tenth of the clip)`.
- **The server's cost.** Copying the helper's frames into ffmpeg costs 2.9% of one core at 1080p30 on a 16-core machine (74.9 s with `h264_nvenc`).
- **The itest bounds.** A clip's length is within the wall time between the marks minus 0.2 s and plus 0.45 s, since the helper reads its deadline every 200 ms; a frame matches a `take_screenshot` within a mean channel difference of 6 per channel, since lossy H.264 cannot meet the screenshot baselines' 2.
- **Unverified.** An NVENC session-limit failure after the first frame (the spike ran 12 sessions without one) would be reported at `stop`, not at `start`.

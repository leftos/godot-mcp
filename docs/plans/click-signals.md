# Fired signals: a click that reports what it set off

Design draft for Linear GMCP-22, "Design a click that reports the signals it fired" (project "Ideas from the survey and the projects"), from the survey's list of what godot-mcp-runtime had that this server lacks ([survey](../research/2026-09-29-godot-mcp-survey.md) L206), not one of its numbered ideas. It builds on the input targets as decision 25 and [input-targets.md](./archive/input-targets.md) design them, the popup items of that design's step 5 included, not on the code in flight. Every question in section 7 is ruled; the build is GMCP-43 (Report the signals a gesture fired), section 6's steps 1 to 6.

## 1. Need

An input call answers what it hit (`pressedOn`, `releasedOn`, `hoveredOn`, `scrolledOn`, `aimedAt`: TOOLS.md L144-171) and the errors the game's handlers raised, but not what the press set off. To learn whether a click did anything an agent reads state afterwards (`inspect_node`, `get_game_state`, a screenshot, `wait_for {uiChanged}`), which says that something changed but not which handler ran. It cannot wait for the signal itself: a press's signals are emitted synchronously while the bridge dispatches the event (section 2), so a `wait_for {signal}` sent after the `click` misses them, and one sent before it blocks until it is met (TOOLS.md L249); `batch_drive` plays its steps one after another (ARCHITECTURE.md L131), so it cannot hold a wait open across a click either. The timeline watch catches named signals across a `watch start`, a `click` and a `watch stop` (decision 29, its signal tracks), but only on nodes and signals the agent names in advance, which is the knowledge it lacks.

So the game repos replace the press with the signal they guess it raises, emitted by hand, and that skips the input path a player takes and fires a different set of signals than the press would:

- **delve-the-dungeon, `docs/DEVELOPMENT.md` L67** ("Reaching a screen"): `Ready Up` "is a toggle, pressed with `button_pressed = true` on the `BaseButton` named `Ready`", which emits `toggled` but never `pressed`, `button_down` or `button_up` (`BaseButton::set_pressed`, section 2); the lobby listens on `Toggled` only (`src/Delve.Client/Scripts/Screens/Lobby.cs` L90), so it works here by luck of which signal the game chose. A seat is named "through the `LineEdit` named `PcName` … (set `text`, then emit `text_submitted` with it)", and the dev console "whose line is filled by setting `text` and emitting `text_submitted`" (`DevConsole.cs` L87 listens on `TextSubmitted`). The `Assign` `OptionButton`: "`select` the index whose text is the player's name, then emit `item_selected` with it" (`OptionButton.select` never emits it, section 2). Action cards are "pressed through `call("Press")` on the card (…; `pressed` emitted on the button leaves the toggle untouched)": `ActionCard.Press()` emits `pressed` on its button by hand (`ActionCard.cs` L464), while the button listens on both `Pressed` and `Toggled` (L219-220), so the hand path runs one handler of the two a click runs.
- **delve L72** ("Pressing things"), the rule the agents follow: "A toggle that ignores its `pressed` signal is still pressed through the scene's own method (`call("Press")` …, `button_pressed = true` on `Ready`), from `call_method` or a `run_script`. A `LineEdit` is filled by a `click` on it and `type_text` …, or by setting `text` and emitting `text_changed` or `text_submitted`."
- **delve L77** ("A shot of a turn while it plays"): a timed shot presses `Take it` as `options.call: {node: "<Take it's path>", method: "emit_signal", args: ["pressed"]}`, because `options.call` takes a method, not a gesture (decision 22).
- **opening-hand** has no hand-emitted signal in its drive docs (`rg -n -i 'emit|signal|toggle|pressed'` over `docs/DEVELOPMENT.md` finds only a toggle icon, L30); its seeded rule for scripted drivers, `docs/GODOT_CONVENTIONS.md` L336-340 "Press the control a player presses, or say the driver does not", names the same substitution (`BaseButton.SignalName.Pressed` raised instead of a press).

The issue (GMCP-22) cites delve L67 and L71; the line numbers have moved, and the hand-emission lines are now L67, L72 and L77.

godot-mcp-runtime's `simulate_input` reports "`signals` fired by a clicked Control within the settle frame" per action (survey L206, from its current docs; the 3.4.0 copy in the local npx cache has no such field: `rg -n -i 'settle|signals'` over its `dist/scripts/mcp_bridge.gd` finds none).

With the press's signals in the result, an agent clicks `Ready`, reads `toggled [true]` with one listener, and drops the workaround; clicks a card and sees the card's own `Pressed` beside the button's `toggled`; presses Enter in `PcName` and sees `text_submitted`; and learns at once when a press landed and set off nothing (a disabled button, a paused game).

## 3. Design

Each part states the recommended option; section 7 holds the choices the owner makes.

### What the result gains (questions 1, 6, 7)

Every input call in scope (question 4) answers three more keys, with no new argument, so no tool signature changes (`drag` already has five parameters):

```
fired: [{node, signal, args?, frame, listeners, count?}],
firedDropped?: n,
leftTree?: ["/root/Main/Safe/Screens/Lobby"],
listenedOn: ["/root/Main/Safe/Screens/Lobby/…/Ready"],
warning?
```

- `fired` lists the emissions the gesture set off on its hit chain (below), in the order the bridge's handlers ran (an emission raised inside a game handler comes before the signal that handler answered; sections 4 and 5), each with the emitter's path, the signal's name, its arguments converted by the JSON module's `to_json` (a Node as its path; omitted when there are none), `frame` (process frames since the gesture's first press, 0 for the press's own frame), and `listeners`, the Godot connections the signal had besides the bridge's (null for a C# `[Signal]`, whose `+=` handlers Godot cannot see; TOOLS.md says so). A run of the same signal on the same node in a row folds into one entry with `count` and the last `args` (`type_text`'s `text_changed` once per character).
- `listenedOn` names the bottom node of each chain listened on, so an empty `fired` says where nobody emitted anything.
- `leftTree` lists the topmost chain nodes that left the tree during the window (a screen swap), in place of their tree signals.
- A `warning` joins any other warning when `fired` is empty and the reason is known: the pressed Control is a disabled `BaseButton` ("…/Ready is disabled, so the press set off nothing"), or the game is paused and the pressed Control cannot process ("the game is paused and …/Ready cannot process, so it received no input; resume, or step with frame_control"), the same wording family as `hover`'s paused-tooltip warning (`godot_mcp_input.gd` L19-22).

Illustrative, for a click on delve's `Ready` (the spike records the real list): `{node: "/root", signal: "gui_focus_changed", args: ["/root/…/Ready"], frame: 0, listeners: 0}`, `{node: "…/Ready", signal: "focus_entered", frame: 0, listeners: 0}`, `{… "button_down", frame: 0, listeners: 0}`, `{… "toggled", args: [true], frame: 1, listeners: 1}`, `{… "pressed", frame: 1, listeners: 0}`, `{… "button_up", frame: 1, listeners: 0}`.

### Which emitters: the hit chain (question 2)

The bridge connects one variadic lambda per (node, kept signal) on the **hit chain** and disconnects them all when the gesture's settle frames end:

- **Pointer gestures**: right after the aim motion (where the hit check already reads the hovered Control), the Control `_hovered_control` gives (the topmost embedded window's for a popup, `godot_mcp_input.gd` L312-323), then each of its ancestors up to the child of `/root`; plus the root viewport for `gui_focus_changed` alone. After each later event (the press, each drag motion) the chain is refreshed from the Control then hovered, adding any new nodes, so a popup that opens under the pointer, or a drag's drop target, joins. An emission made inside the very dispatch that changed the hover is missed for the new nodes; TOOLS.md says so.
- **A world or text target** adds the target node and its ancestors (a world node's `input_event` from physics picking; a text match's own scene root, whose script signals a card raises).
- **An item target** needs nothing more: a `PopupMenu`'s parent is its `OptionButton` or `MenuButton` (`option_button.cpp` L715), and a tab's `TabBar` sits under its `TabContainer`, so `item_selected`, `index_pressed` and `tab_changed` are on the chain.
- **A `BaseButton` on the chain with a `ButtonGroup`** adds the group's other buttons, which emit `toggled(false)` as the click unpresses them.
- **A `mouse_button` release** (a separate call from its press) listens on the chain of the Control its press landed on, which the bridge keeps from the press, since Godot sends the release there (`viewport.cpp` L2015-2040).
- **Keys** (`key`, `type_text`): the focus owner of the window that holds focus (an embedded popup's when one has it) and its ancestors, refreshed after each key event, since Tab moves focus.
- **Never**: the bridge's own nodes, as no tool reads them; nodes off the chain, such as an autoload or a `_unhandled_input` handler elsewhere. For those an agent starts a `watch` with signal tracks around the call.

### Which signals of a chain node (question 3)

Every signal `get_signal_list` returns (script signals included) except a fixed **noise list**, emitted by layout, drawing or the pointer's own motion on every gesture: `draw`, `item_rect_changed`, `gui_input`, `mouse_entered`, `mouse_exited`, `mouse_shape_entered`, `mouse_shape_exited`, `resized`, `minimum_size_changed`, `maximum_size_changed`, `size_flags_changed`, `theme_changed`, `pre_sort_children`, `sort_children`, `child_order_changed`, `property_list_changed`, `script_changed`, `renamed`, `ready`, `replacing_by`, `editor_description_changed`, `editor_state_changed`, and on a Window `window_input`, `nonclient_window_input`, `dpi_changed`, `title_changed`, `titlebar_changed`, `size_changed`, `output_max_linear_value_changed`. The tree signals (`tree_entered`, `tree_exiting`, `tree_exited`, `child_entered_tree`, `child_exiting_tree`) are not listed per emission: a chain node that leaves the tree goes into `leftTree`, the topmost one only, since a screen swap would otherwise list `tree_exiting` and `tree_exited` on every ancestor. Kept: `focus_entered`, `focus_exited`, `visibility_changed`, `hidden`, `about_to_popup`, `popup_hide`, `close_requested`, every class signal below Control (`BaseButton`, `LineEdit`, `OptionButton`, `TabBar`, …), `input_event`, and every script signal.

### The window (question 5)

From the press (after the aim motion, so the pointer's own `mouse_entered` never counts) to the end of the gesture's existing two settle frames (`SETTLE_FRAMES`, `godot_mcp_input.gd` L10, L105-106). Synchronous emissions land inside the dispatch, deferred slots at the next `MessageQueue` flush, and a world node's `input_event` at the next physics tick, all inside the settle frames whenever a physics tick runs in them (the spike confirms). The call takes no longer than today. Later effects (a timer, a tween, a server round trip) are the watch's: `watch start`, the click, `watch stop`.

### Where it lives

- **Bridge**: a new module `bridge/godot_mcp_fired.gd`, the `Fired` child of `Gestures`, created from the input module's own folder as `Targets` is (`_create_targets`, `godot_mcp_input.gd` L83-90), so `godot_mcp_bridge.gd` gains no line: the noise list, `listen(node)` (a chain, its kept signals, a lambda each, skipping nodes already listened), the `ButtonGroup` and kept-press rules, the catcher (records `[frame, path, signal, args, listeners]`, converting args with `to_json` as it records, at most 200 raw entries, then counting), `leftTree` from `tree_exiting`, and `stop()` (disconnect what is still valid, answer the raw list). The input module's `play` starts and stops it around the gestures in scope and calls `listen` after the aim motion and each press or motion, and the key path after each key event: about 20 lines on its 883.
- **Server**: `src/GodotMcp.Server/Tools/FiredSignals.cs` shapes the raw list in `SendInputAsync` (`RuntimeTools.Input.cs` L432-453) before `ErrorReport.AddTo`: folds runs into `count`, keeps the first 50 entries with `firedDropped`, cuts an argument over 200 characters to `{valuePreview, valueLength}`, the watch's per-value cut. The tool descriptions gain one shared note (a `FiredNote` beside `TargetNote`, L26-31).
- **Annotations and class**: unchanged. Listening runs no game code; the input tools stay `drive`.

### With the other tools

- **`batch_drive`**: a tool step's result carries `fired` as any field, so a batch's report shows each press's signals; an assertion on it is question 8.
- **The error feed**: unchanged; an error a handler raises is in `errors` beside the entry that set it off.
- **`wait_for {uiChanged}`**: independent; the click still takes its baseline.
- **`watch`**: independent; a watch's signal track on the same signal adds its own lambda, and both record. The watch's signal tracks (its step 3) can reuse this module's catcher and argument conversion, decided at that step's briefing.
- **`frame_control`**: a gesture on a paused game listens as usual; ordinary Controls cannot process, so `fired` is empty with the paused warning.
- **`capture_input`, recording, sessions**: no interaction; nothing is kept between calls, and the session's input gate serialises gestures.
- **`simulate_input` (its `click_element` too) and `stress_input`**: not reported (question 4); they play raw events through `godot_mcp_raw_events.gd`, whose result merges no hits today (`godot_mcp_input.gd` L114-115).

## 4. Costs and risks

- **Per gesture, not per frame.** Nothing runs between gestures. A gesture connects and disconnects a lambda per kept signal on each chain node: a delve card's chain is about 15-20 nodes deep (unmeasured), times the signals each keeps after the noise list (unmeasured; a Button keeps about eight engine ones plus its script's). Connect and disconnect costs are unmeasured; the spike measures them. Each emission then costs one variadic call, about 1.1-1.5 µs (the watch spike, [timeline-watch.md](./timeline-watch.md) section 8), plus its arguments' `to_json`.
- **Wire size.** A plain click lists about six entries, under 1 KB (unmeasured); the cap is 50 entries with arguments cut at 200 characters, about 15 KB at worst.
- **A handler that emits in a loop** (a list rebuilt row by row, each row a script signal on a chain node): the bridge stops recording at 200 raw entries and counts the rest, and the server folds and caps. The fastest way to fill the cap is `type_text` of a long string into a LineEdit with a script `text_changed` relay, which folding turns into one entry per alternating signal.
- **A huge argument** (an Array of thousands of entries on a game signal) is converted on the main thread inside the emission; the JSON module's depth limit bounds nesting, not length (unmeasured). The bridge converts no argument once 200 entries are recorded.
- **Game code that inspects its own connections** (`get_signal_connection_list(...).size()`, `has_connections`, `is_connected`) sees one more connection during a gesture. A handler that disconnects every slot of a signal drops the bridge's too, and later emissions of it go unlisted; neither breaks the game.
- **`listeners` read as proof.** `listeners: 0` on an engine signal means no Godot connection, not that nothing reacts: a game may poll `button_pressed` in `_process`, or react to a C# `[Signal]` whose `+=` handlers Godot cannot count (`listeners: null`). TOOLS.md says both.
- **Order read as cause.** An emission raised inside a game handler is listed before the signal whose handler raised it (section 2, slot order): a card's own `Pressed` appears before the button's `pressed`. TOOLS.md says entries are in handler order and `frame` groups them.
- **What a careless agent can do**: nothing new to the game. The report is read-only for the game's state; its abuse is cost, through thousands of input calls, each paying the connect cost.

## 5. Alternatives considered

- **Listen to every node of the current scene, or of the tree.** Catches an autoload's or a sibling's signal too, but connects thousands of lambdas per click on delve's fight screen and lists every Label's layout churn; the watch does wide listening on named nodes for the price of naming them.
- **Report only the hit Control's own signals.** Misses exactly the cases in section 1: a card's `Pressed` is on its scene root (an ancestor), and `item_selected` is on the `OptionButton` above the clicked `PopupMenu`.
- **Make the bridge's slot run first,** by disconnecting the game's slots on each chain signal and reconnecting them after its own, so `fired` lists in emission order. Rejected: it rewrites the game's connections on every press, a `CONNECT_REFERENCE_COUNTED` connection's count or a C# `EventSignalCallable` might not survive the round trip, and an error midway would drop a game handler.
- **Opt-in through an `options.signals` argument.** `drag` has no room under the five-parameter limit, and the agents who need the report are the ones who do not know to ask for it (question 1).
- **A separate `click_and_report` tool, or a gesture inside `watch`.** Two ways to click; and a watch needs its emitters named before the click, which is the knowledge the agent lacks.
- **Count C# `+=` subscribers through the C# helper** (reading a `[Signal]`'s backing delegate's invocation list). Costs the helper's load, about 2 s cold (the state-digest spike), on a click; question 6 (c).
- **A longer or adaptive settle** (until no chain signal fires for N frames). Holds the input gate behind a node that emits every frame, and moves every input call's timing; question 5.

## 6. Steps

Each step lands on its own with its tests, docs (TOOLS.md, SKILL.md, ARCHITECTURE.md, the glossary, README for the new capability, a `CHANGELOG.md` `## Unreleased` bullet) and passes `pwsh run.ps1 build`, `pwsh run.ps1 test`, `pwsh run.ps1 gdtest` (with `gdlint` and `gdcomplexity`), its itest class with `pwsh run.ps1 itest -Filter "*<Class>"`, then `pwsh run.ps1 itest -Since origin/main`.

1. **Spike** (no bridge edit; `pwsh run.ps1 drive -Calls <file.json>` on InputProbe and CsProbe copies, catchers installed by `run_script`): (i) the connect-plus-disconnect cost of a 20-deep chain with every non-noise signal, in µs, and the count of kept signals per class; (ii) the list for a click on a plain Button, a toggle, a toggle in a `ButtonGroup`, a disabled Button, a `TabBar` tab, an `OptionButton` item (opened by click, then the item: needs popup items landed, else probe by `{x, y}`), Enter in a `LineEdit`, and an `Area2D` under the root, each confirmed inside the two settle frames; (iii) a nested emission's order; (iv) a C# `[Signal]`'s `get_signal_connection_list` entries, and how the `EventSignalCallable` is told apart. Results into section 2's unverified line.
2. **Click and `mouse_button`**: `bridge/godot_mcp_fired.gd`, the input module's calls for `click` and `mouse_button` (the kept press chain), `FiredSignals.cs`, the descriptions. Tests: gdtest `tests/bridge/test_fired.gd` (chain building, the noise list, `ButtonGroup` buttons, bridge nodes left out, `leftTree` keeping the topmost, the 200 cap; signals emitted by hand in a headless tree); unit `tests/GodotMcp.Tests/Tools/FiredSignalsTests.cs` (folding, the 50 cap and `firedDropped`, the 200-character cut, order kept); itest `FiredSignalsTests` (a new class in the `input` group of `run.ps1` `$itestGroups`, with a `src/GodotMcp.Server/Tools/FiredSignals.cs` rule mapping to `input` beside L205): widgets built by `run_script` on the shared InputProbe session, as `WorldTargetTests` builds its own; a Button, a toggle with one listener, a disabled Button and its warning, a `ButtonGroup`, a `TabBar` item, a text target on a card-like Label beside a Button with a script signal on their root, a world `Area2D`'s `input_event`, a press-then-release `mouse_button` pair, a paused game's warning. `McpServerSmokeTests` is unchanged (no new tool).
3. **`drag`, `key` and `type_text`**: the drop target's chain and the focus-owner chain, refreshed per key event; `FiredSignalsTests` gains a drag onto a drop target, Enter in a LineEdit (`text_submitted`), `type_text` folding `text_changed`, and Tab moving focus to a second LineEdit.

## 7. Open questions

Ruled by the owner: 1 (a), always on with no new argument; 2 (a), the hit chain plus the target's chain, `ButtonGroup` buttons, the focus chain for keys and the root's `gui_focus_changed`; 3 (a), every signal but the noise list, tree signals folded into `leftTree`; 4 (a), `click`, `mouse_button`, `drag`, `key` and `type_text`; 5 (a), the existing two settle frames; 6 (a), Godot connections counted, null for a C# `[Signal]`; 7 (a), the key `fired`; 8 (a), a `fired` assertion in `batch_drive`. Every question is ruled.

1. **On by default, or asked for.** (a, recommended) Always on for the gestures in scope, no new argument. How: every click answers `fired`, `listenedOn` and, when they apply, `leftTree` and the warning. Worst case: every input call pays the chain's connect cost and about 1 KB, needed or not. (b) Opt-in through `options.signals: true` on `click`, `mouse_button`, `key` and `type_text`. How: a new `options` parameter on each. Worst case: `drag` cannot take it under the five-parameter limit, and the agents who replace presses with hand emissions never learn to ask. (c) No list; only a `warning` when the pressed Control emitted nothing. How: the same listening, reduced to one bit. Worst case: a toggle that ignores `pressed` (delve's cards) looks fine, and nothing says which signal did fire.
2. **Which emitters.** (a, recommended) The hit chain: the hovered Control and its ancestors, refreshed after each event, plus the target's chain, a pressed toggle's `ButtonGroup` buttons, the kept press chain for a separate release, the focus owner's chain for keys, and the root's `gui_focus_changed`. How: section 3. Worst case: an autoload's or a sibling screen's signal (delve's `Net` sending a plan) is not listed, and the agent needs a `watch` for it. (b) The hit Control only. Worst case: a card's own `Pressed` (on its scene root) and `item_selected` (on the `OptionButton` above the popup) are missed, which are section 1's cases. (c) Every node of the current scene. Worst case: thousands of connections per click on a busy screen, and a list buried in other nodes' churn.
3. **Which signals of a chain node.** (a, recommended) Everything but the noise list, with tree signals folded into `leftTree`. How: section 3. Worst case: a game whose real reaction is a layout signal (`resized` driving a re-layout it cares about) does not see it listed. (b) Only signals declared below Control (the class's own and the script's). Worst case: `focus_entered`, `visibility_changed` and `popup_hide` (a dialog closing on its Cancel) disappear. (c) Everything, unfiltered. Worst case: every click lists `mouse_entered`, `gui_input` three times and a `draw` per redrawn ancestor before the one line that matters.
4. **Which gestures.** (a, recommended) `click`, `mouse_button` press and release, `drag`, `key` and `type_text`, in steps 2 and 3. How: pointer chains for the first three, the focus chain for keys. Worst case: `simulate_action`, the gamepad gestures, `hover` and `scroll` stay silent, so a pad-driven menu's press is checked by reading state. (b) `click` only, the issue's word. Worst case: delve's `PcName` and console keep setting `text` and emitting `text_submitted`, since Enter is a `key`. (c) Every input tool, `simulate_input` and `stress_input` included. Worst case: `stress_input` pays the connect cost every iteration, and a raw event list changes its chain at every event.
5. **How long a gesture listens.** (a, recommended) From the press to the end of the existing two settle frames. How: no change to any call's timing. Worst case: a reaction on a timer (delve's rewards board pays out about 250 ms after the fourth pick, L78) is not listed; the agent wraps the click in a `watch`. (b) An `options.settleMs` on the tools in scope. Worst case: `drag` cannot take it, a long settle holds the session's input gate, and agents set it high "to be safe". (c) Until no chain signal fires for 5 frames, capped at 1 s. Worst case: a node that emits every frame (an animated label's script signal) holds every click for the full second.
6. **Listener counts.** (a, recommended) `listeners` on every entry: the Godot connections besides the bridge's, null for a C# `[Signal]`. How: `get_signal_connection_list` at record time, the C# instance's own `EventSignalCallable` left out. Worst case: `listeners: 0` on an engine signal read as "nothing reacted" while the game polls `button_pressed` in `_process`. (b) No count. Worst case: `pressed` fired into nobody and `toggled` fired into the handler read alike, which is delve's card. (c) (a) plus C# `+=` subscribers counted through the helper. Worst case: a 2 s cold helper load on the first click of a C# game, and a helper call on every press.
7. **The result's key.** (a, recommended) `fired`. How: section 3. Worst case: one more word for agents to learn. (b) `signals`, godot-mcp-runtime's name. Worst case: it collides with `describe_class`'s and `get_node_signals`' `signals`, which list declarations, not emissions.
8. **`batch_drive`.** (a, recommended) A `fired` assertion, `{assert: "fired", node, signal, args?}`, checked against the previous tool step's `fired`, failing the batch when no entry matches. How: step 5. Worst case: an assertion bound to the step before it breaks when steps are reordered. (b) No assertion; the step results carry `fired` for the agent to read after. Worst case: a replayed batch cannot check that a press still sets off its signal, only that state changed afterwards.
9. **New terms** for the glossary when the design is adopted: new term: hit chain (the nodes a gesture listens on: the hovered Control and its ancestors, the target's chain, the focus owner's for keys); new term: fired list (an input result's `fired`: the emissions on the hit chain from the press to the settle frames' end); new term: noise list (the layout, drawing and pointer signals a fired list leaves out).

# Step until a condition, and render diagnosis

Design draft for GMCP-20, "Design step-until-a-condition and render diagnosis (ideas 5 and 6)", from ideas 5 and 6 of the [survey](../research/2026-09-29-godot-mcp-survey.md) (L120-128). It also answers GMCP-7 (GitHub #62, "wait_for: no call in the frame an expression or property condition is met"). The two halves share no code: the first is three options on the existing `wait_for` and `frame_control` (no new tool), the second is documentation now and, only if the owner chooses it, one read tool later. Section 6 orders the steps so either half ships alone. Section 7's questions are open.

## 1. Need

### What an agent cannot do today

The time tools are `frame_control` (pause, resume, step N drawn frames and stay paused, time scale; TOOLS.md L229-233), `wait_for` (a condition checked each frame on a running game, a frame-exact `options.screenshot`, and `options.call` at the start of a `gameMs` or `frames` wait only; L247-251), `capture_frames` (L235-239), `batch_drive` (a list of steps run server-side, stopping at the first failure; L355-359) and the `watch` of [timeline-watch.md](./timeline-watch.md) (decision 29; step 2 is being built), which records how values and signals move over a window and runs beside every other tool, steps included. Checked against that set, four things have no tool:

| Job | Closest today | What is missing |
|---|---|---|
| Act in the frame a condition becomes true (start slow motion when a beat's first line types) | `wait_for {expression}`, then `frame_control time_scale` | The second call arrives after the reply's round trip and the agent's turn; the moment has passed. `options.call` is refused on any condition but `gameMs` and `frames` (TOOLS.md L250) |
| Stop the game paused on the frame a condition first holds, so every read tool sees that frame | `wait_for` with `options.screenshot` | The screenshot freezes an image, not the game: `get_game_state`, `inspect_node` and `snapshot_subtree` called next read a later frame. A `frame_control pause` after the wait lands frames or seconds late |
| Advance a paused game frame by frame until a condition holds, in one call | `frame_control step 1`, then `wait_for` with `timeoutMs: 0`, repeated | Two round trips a frame. `batch_drive` cannot loop: it stops at its first failed assertion and takes at most 100 steps, so "step until" is not expressible, only "step while" |
| Press a key or an action inside a stepped frame | `simulate_input` while paused, then `frame_control step` | Input sent while paused never reaches a pausable node's `_input`, `_unhandled_input` or a Control's `gui_input` (section 2), and its just-pressed edge belongs to the frame it was sent in, which the step has left behind. A game that polls `Input.is_action_pressed` sees the key held; one that reacts to `is_action_just_pressed` or to an input callback sees nothing |

What `batch_drive` already gives, and this design does not replace: `pause`, a `call_method`, `step N` and check-once assertions in one call, each step at least one frame after the last (each request is read in the bridge's `_process`, `bridge/godot_mcp_bridge.gd` L341-366; how many frames pass between batch steps in practice is unmeasured).

### Evidence from the game repos

- **delve-the-dungeon, slow motion started by a poll script** (`D:/delve-the-dungeon/docs/DEVELOPMENT.md` L80): "A beat is shot in slow motion without pausing: a `run_script` polls each frame until the log's `visible_characters` reaches `get_parsed_text().rfind("<the beat's first line>")` (or until `Combat/FightTray` is `visible`, for a roll), sets `Engine.time_scale = 0.2` and returns, and `capture_frames` follows on game time". This is GMCP-7 verbatim (the issue quotes it as L79; the file has since moved a line). The same line: "A slowed clock drops the socket like a paused tree: at 0.1 for about 35 s of wall time the connection went and the rejoin emptied the log, while 0.2 for 15 s held."
- **delve-the-dungeon, never paused across calls** (L79): "Never hold the tree paused across tool calls (unverified on the current godot-mcp: its audits could not settle it from the server's source): the socket drops, the screen goes to `Connecting` and the rejoin comes back with an empty log and the card put down." So for delve a pause-on-met is a hazard and an action in the met frame (GMCP-7) is the useful form; GMCP-20's own text ranks idea 5 low for this reason.
- **delve-the-dungeon, a press loop until a condition** (L80): "a `run_script` loop presses any visible `Let it land` until the header reads the next turn's planning". This loop spans network turns, not frames; it stays a script (or an agent's loop) under this design, and section 5 says why.
- **delve-the-dungeon, the pause gaps already closed**: GitHub #9 (no timed wait while paused), #10 (a `wait_for` then `take_screenshot` missed the frame; answered by `options.screenshot`), #25 (`capture_frames`), #41 (game-time waits; its workaround (1) was "pause the game, `call_method PlayStep`, then `frame_control step` N frames"), all closed.
- **opening-hand** (`D:/opening-hand/docs/DEVELOPMENT.md` L61) holds a scratch step on screen with `call_method PlayStep` and `wait_for {frames}` or `{gameMs}` between steps, and catches a short step with `wait_for` `options.screenshot` or `capture_frames` `options.call`: every one a running-game form. Its #10 workaround was `time_scale 0.25` "and the right scale is a guess". Neither repo writes input into a paused step by hand.
- **The survey** (L120-123): satelliteoflove's `godot_game_time` steps with inputs riding inside the step, because "inputs injected while frozen miss their `is_action_just_pressed` edge"; godot-ai's `input_sequence` places actions by frame number.

### Render diagnosis

Neither repo writes a visibility probe by hand. What they do write: delve L95 compares renderers by passing `engineArgs: ["--rendering-driver", "vulkan"]` and measures a first-draw hitch as "the longest gap between two `process_frame`s" (the watch's `frame_ms`); delve L101 projects a die's mesh points "through the tray's `Camera3D.unproject_position`" in a `run_script` to measure a numeral's angle, an orientation question, not a visibility one; delve L93 notes the headless renderer "never triangulates", so a failed polygon logs nothing headless. opening-hand (2D) reads detail at 2x through `--resolution` (L53). The survey's own fit line (L128) names the cheapest step: the `--debug-collisions` family already passes through `engineArgs`, undocumented. The world-node aim of [input-targets.md](./input-targets.md) (decision 25) already explains why a node's origin is not on screen when an input tool aims at it: off-screen with the point and the rect, behind the camera, no current camera, hidden, not drawn by any viewport.

## 3. Design

### 3.1 `wait_for` `options.then`: act in the met frame (GMCP-7)

`wait_for(condition, timeoutMs, options, session)` keeps its four parameters; `WaitOptions` gains `then`:

```
options.then: {call?: {node, method, args?}, timeScale?: number}
```

- At least one key; `timeScale` above 0 and at most 100, `frame_control`'s range. `call` is the `MethodCall` record `options.call` uses, so GMCP-8's widening (#65, a game tool by name with named arguments) reaches both at once.
- Any condition kind takes it, `gameMs` and `frames` included (beside or without `options.call`, which still runs at the start).
- It runs once, right after the check that met the condition, in that frame: a plain wait checks at `process_frame`, so `then` runs before that frame's nodes process (a call's effect gets that frame's `_process`, as `options.call`'s does, decision 22); a wait met at its first check runs it inside the request's handler; a wait with `options.screenshot` checks at `frame_post_draw`, so `then` runs after the frame drew and after its capture. A time scale set there scales the next frame on (`main.cpp` L4936). The order is `call`, then `timeScale`.
- A timeout runs nothing. A check-once wait (`timeoutMs: 0`) runs `then` at once when met, paused or not, as `call_method` and `frame_control time_scale` would.
- The result adds `then: {frame, call?: {value}, timeScale?}`, `frame` being `Engine.get_process_frames()` when it ran, the numbering of `get_game_state`'s `frame` and the watch's `startFrame`.
- A call refused as `call_method` refuses it, or one that raises an error (read across the call from the error feed, as `options.call` reads it), fails the wait, and the time scale is not set: `The condition was met after <n> frames (frame <f>), but then.call failed, so timeScale was not set: <reason>` (the clause after the comma only when `timeScale` was given). Question 4 weighs the alternative.
- Refusals before the wait starts: `options.then needs call, timeScale or both.`; `options.then.timeScale must be greater than 0 and at most 100; got <v>.`; the `call` record's own checks.
- In `batch_drive` a `wait_for` tool step takes `then` as its own argument; the `wait` assertion stays as decision 22 left it (question 7).

GMCP-7 is answered by this part alone: delve's L80 script becomes `wait_for {condition: {node: "<log>", expression: "node.visible_characters >= node.get_parsed_text().rfind(\"…\")"}, options: {then: {timeScale: 0.2}}}`, then `capture_frames`.

### 3.2 `frame_control` step `options.until`: stop paused on the met frame

`frame_control(action, count, scale, options, session)` is at the five-parameter limit, so the new keys go into `StepOptions`:

```
frame_control {action: "step", count?, options: {unit?, screenshot?, until?, input?}}
```

- `until` is a `wait_for` condition object (`WaitCondition`, every kind but `frames`, which `count` already is; `state` too once GMCP-17 adds it). With it, `count` is the most frames the step runs, 1 to 1000 as now, and left out it is 1000 (without `until` it stays 1).
- **Process unit**: the condition is checked at each stepped frame's `frame_post_draw`, where the step already counts the frame, so it sees the state that frame drew; the first met check ends the step there, re-pausing as the step always does, and `options.screenshot` captures that frame. The game is left paused on the met frame, and every read tool, the screenshot included, sees it until the agent steps or resumes.
- **Physics unit**: checked at each `physics_frame` after a counted tick (the state the last tick left), where `_run_ticks` re-pauses (`godot_mcp_time.gd` L323-333).
- The check runs after each stepped frame, never before the first, so a step runs at least one frame even when the condition already holds.
- A signal condition is connected when the step starts; with the process unit it is met at the draw of the frame it fired in. A `gameMs` condition counts the stepped frames' delta, as `wait_for`'s clock does. A `uiChanged` condition compares with the pending baseline, which the step's own `input` takes when none is pending (3.3).
- The step works from a running game too (it waits for the next `frame_post_draw` first, as today), so "run until X, then freeze" is `frame_control step {count: 1000, options: {until: X}}`; a longer lead-in is a `wait_for` on an earlier sign first.
- The result: `{paused, timeScale, processFrames, physicsFrames, frame, met?, value? | last?, screenshot?}`. `processFrames` (or `physicsFrames`) is the frames stepped; `frame` (new on every step) is `Engine.get_process_frames()` at the stop; `met` with `value` or `last` as `wait_for` reports them. A step whose `until` is never met runs `count` frames, stays paused and answers `met: false` with `last`, a result, not an error.
- Refusals: `frame_control step's until takes any wait_for condition but frames: count is the most frames a step runs.`; `options.until and options.input apply to step only.`; and today's step refusals (the window cannot draw, low-processor mode, a step, monitor or capture already running, the game pausing itself mid-step).

### 3.3 `frame_control` step `options.input`: input that rides a stepped frame

```
options.input: [{frame?: k, type: "key" | "mouse_button" | "mouse_motion" | "pan_gesture" | "joypad_button" | "joypad_motion" | "action", …}]
```

- Each entry is one of `simulate_input`'s raw events (TOOLS.md L198-202), with `x`, `y` in viewport coordinates as everywhere, plus `frame`, the 0-based stepped frame it arrives in (default 0). At most 100 entries.
- Each is sent at its stepped frame's `process_frame`, before that frame's nodes process, through the input module's `dispatch` (parse, then flush). The tree is unpaused there, so `_input`, `_unhandled_input` and `gui_input` reach the game's nodes at once, and `is_action_just_pressed` holds in that frame's `_process` (`input.cpp` L1036, L441). Its physics edge is the next tick (L1035), which is the next frame's first tick: one frame later than a real event's, since a real event is flushed between iterations, where no script hook runs (section 2). TOOLS.md says so.
- An event with `pressed` left out is a press at `frame` and a release at `frame + 1`, `simulate_input`'s rule, and the release must fall inside the step.
- The input plays under the session's input gate, sets the bridge's `_gesture_playing` so a watched run's real mouse is swallowed as during a gesture, goes into a running `capture_input`, and takes the `uiChanged` baseline when none is pending, so `until: {uiChanged: true}` with a key in `input` steps until that key's effect shows.
- With `until` met early, the events of later frames are not sent; the result adds `inputNotSent` (their count) and, when the step leaves keys, buttons or pad buttons pressed, `held: {keys, mouseButtons, padButtons}`.
- Refusals: `options.input rides process frames; it cannot be used with unit physics.`; `options.input[<i>].frame is <k>, past the step's last frame <count - 1>.`; `options.input[<i>] presses and releases (pressed left out), so its release lands at frame <k + 1>, past the step's last frame <count - 1>; pass pressed: true and a release event, or raise count.`; `options.input[<i>] is a wait: a step's input is placed by frame; give the event a frame instead.`; `options.input[<i>] is click_element, a gesture that plays over frames of its own; in a step send mouse_button and mouse_motion events with x, y.`

### 3.4 How it sits with the other tools

- **The watch** (decision 29). A watch runs beside steps, and samples only unpaused frames, so `watch start`, `frame_control step {options: {until, input}}`, `watch stop` records exactly the stepped frames up to the met one: that is the "report over the step" (question 6). The step's `frame` and `then.frame` line up with the watch's `startFrame` plus its relative `frame`. `until` and `then` reuse the time module's probes and `_parse_expression`, which watch step 2 makes public.
- **`frame_control`'s guard**: a step with `until` or `input` is a step: it holds `_running` (`godot_mcp_time.gd` L86-88), so a monitor, a capture, another step, `pause` and `resume` are refused while it runs, as today.
- **`batch_drive`**: `frame_control` and `wait_for` tool steps carry the new options; a step-until counts its frames against the batch's 300 s.
- **Recording**: a step counts drawn frames, which are movie frames; `then.timeScale` changes game time, not the clip's fixed 60 fps (TOOLS.md L381).
- **The error feed**: errors raised during stepped frames or by `then.call` ride on the result as on every runtime tool.
- **Sessions and annotations**: per session as every runtime tool; `frame_control` and `wait_for` keep their annotations (neither read-only nor destructive), as `wait_for`'s expressions and `options.call` already run game code under them, so no agent sweep changes.

### 3.5 Where it lives

- **Bridge**: a new module `bridge/godot_mcp_step.gd` (the `Step` child of `Time`) takes the step out of `godot_mcp_time.gd` unchanged first (about 190 lines, L145-333: `_guarded_step`, `_step`, `_run_step`, `_save_capture`, `_run_frames`, `_run_ticks`, `_stalled`, `_next`, keeping `Time`'s `_begin`/`_end` guard), then gains `until` (a probe from `Time._make_probe` called at each counted frame) and `input` (a per-frame schedule played through `Gestures.dispatch`). `then` stays in `godot_mcp_time.gd`'s wait path (`_poll`, `_poll_capturing`, `_check_drawn_frame`), about 40 lines, after watch step 2 moves the compare family (L904-935) out.
- **Server**: `StepOptions.cs` (`Until`, `Input`), `WaitOptions.cs` (`Then`, a new `WaitThen` record), `RuntimeTools.Time.cs` (`BuildFrameParameters` and the wait's parameters: the checks above, the input's expansion and frame checks, the step's input gate); the raw-event checks `simulate_input` already runs are shared, not copied.

### 3.6 Render diagnosis

- **Documentation first.** A TOOLS.md subsection "See why something is not drawn" under "See the game", with a line in SKILL.md:
  - Collision shapes, paths, navigation and avoidance are launch flags: `run_project {engineArgs: ["--debug-collisions"]}` (also `--debug-paths`, `--debug-navigation`, `--debug-avoidance`, and `--debug-canvas-item-redraw` for what redraws in low-processor mode), or a `godot-mcp.json` preset (`"collisions": {"engineArgs": ["--debug-collisions"], "description": "collision shapes drawn"}`); they cannot be turned on mid-run (SceneTree.xml L266-276), so a running session needs `stop_project` then `run_project` with the flag.
  - Draw modes are `Viewport.debug_draw` on the root: `set_property {node: "/root", property: "debug_draw", value: 3}` (overdraw), back to 0 afterwards; lighting and overdraw replace custom shaders, wireframe under Compatibility shows nothing unless the game generates wireframes before its meshes load, normal buffer needs Forward+ (`engineArgs: ["--rendering-method", "forward_plus"]` to try it on a Compatibility project).
  - A world node's on-screen point, or why it has none, comes from the input tools' world aim (`aimedAt`, or the off-screen, behind-camera, no-camera and hidden refusals); a `hover` reports it, and moves the pointer.
  - A screenshot baseline taken in one draw mode fails in another.
- **A read tool later, if the owner wants it now** (question 8): `render_probe {node, session}` answering why a `CanvasItem` or `GeometryInstance3D` is not drawn: the visibility chain (the first hidden ancestor), the product of `modulate` alphas, `visibility_layer` against the viewport's `canvas_cull_mask` (2D) or `layers` against the camera's `cull_mask` (3D), the global AABB against the camera's frustum, near and far, the visibility range against the camera distance, and the projected rect against the viewport; read-only, no game code, reusing `godot_mcp_targets.gd`'s projection and viewport chain. No game repo writes such a probe by hand today (section 1).

## 4. Costs and risks

- **Per frame.** `until` runs one probe a stepped frame: an expression costs about 5 µs (the watch spike measured 32 expression and property tracks at 146-164 µs a frame at p50, timeline-watch.md section 8); a `uiChanged` check walks the visible Controls every frame (its cost is unmeasured, and the costliest condition for a 1000-frame step). `input` is one `dispatch` per event. `then` runs once. Nothing runs on frames outside a step or a wait.
- **Wire.** At most 100 input events a request (a few kilobytes); results grow by a few keys.
- **Holding the game.** A step-until whose condition never holds runs `count` frames (1000 is about 17 s at 60 fps; its deadline is 10 s + 100 ms a frame, 110 s) and leaves the game paused; meanwhile monitors, captures and other steps are refused. A networked game held paused may drop its connection: delve's does (L79). TOOLS.md names `then.timeScale` as the form for such games.
- **A crawling clock.** `then.timeScale: 0.01` leaves the game near frozen: delve's socket dropped at 0.1 after about 35 s (L80), and a later `wait_for {gameMs}` or `capture_frames` takes 1/scale as long in wall time and meets its derived timeout first. The result's `then.timeScale` says what was set; `frame_control time_scale 1` puts it back.
- **Held input.** A riding press with no release leaves the key held after the step; `held` lists it, and a `key` release clears it.
- **Game code.** `until`'s expression runs every stepped frame and `then.call` once, at a moment the agent does not see; both already run under `wait_for` and `options.call`. A side-effecting expression changes the frames it is checking.
- **The fastest way to exhaust it**: `frame_control step {options: {until: {uiChanged: true}}}` with no gesture pending and no `input`: the baseline is missing, so it is refused before stepping (`wait_for`'s `NO_UI_BASELINE`); with a baseline that never changes, 1000 frames of full UI walks. And a `batch_drive` of 100 step-until steps never met runs into the batch's 300 s.
- **Render docs.** `--debug-collisions` draws every shape every frame, which moves a watch's `frame_ms`; a `debug_draw` left set stays until set back or the game restarts.

## 5. Alternatives considered

- **A new `step_until` tool** (satelliteoflove's `godot_game_time`: until, a frame budget, an input timeline, a report, a then): a third tool on one clock beside `frame_control` and `wait_for`, its own refusals, annotations and agent-sweep entry, for options the two tools already have room for.
- **`then.pause` on `wait_for`** in place of `until` on the step: it works only from a running game (`wait_for` refuses a paused one, decision 11), so the paused case needs the step anyway, and two tools would pause the game by two rules. Question 2.
- **Pausing where `wait_for` checks** (`process_frame`): the frame left has run its physics ticks and not its process, the partial frame the step's design avoids (`godot_mcp_time.gd` L10-15). Pausing at `frame_post_draw` needs a drawn frame, which is the step's rule already.
- **A loop in `batch_drive`** (`repeat` until an assertion holds): each batch step is one bridge request, at least a frame after the last, so it cannot stop on the met frame, and the batch becomes a language.
- **Input sent while paused, then a step** (today): pausable nodes get no input callback while paused (`scene_tree.cpp` L1471) and the just-pressed edge is stamped with the sending frame (`input.cpp` L1036). `Input.action_press` in a `run_script` is stamped the same way (L1419-1420).
- **Sending riding input at the previous frame's `frame_post_draw`**, where the step unpauses: the first tick of the stepped frame gets the physics edge, but the process edge is stamped with the frame just drawn and is lost, and `_input` runs a frame early. The process edge is the one UI and `_process` code reads. Question 5.
- **Gestures inside a step** (a `click` with a target): a gesture plays over frames of its own, with a hit check and two settle frames (`godot_mcp_input.gd` L10, L98-117); scheduling it inside a frame budget changes every gesture.
- **`options.call` on a step** (a method at the first stepped frame): `call_method` while paused, then the step, gives the same frames, differing only in an `Engine.get_process_frames()` stamp the method takes; no repo asks for it.
- **The press-until loop of delve L80** as a step-until with input: the loop waits on the server's turn over the network for seconds a pass; a frame-bounded step is the wrong clock, and a paused game drops delve's socket.
- **A `report` list evaluated on the met frame**: question 6.
- **Toggling the SceneTree debug hints with `set_property`**: the class reference says they are not designed to change at run time (SceneTree.xml L268).
- **A `debugDraw` option on `take_screenshot`**, set for one capture and restored: worth it only if `set_property` cannot reach the root's `debug_draw`, which step R1 checks.
- **satelliteoflove's `godot_validate_meshes` and `godot_scene3d`**: neither game builds meshes or asks for a spatial dump; delve reads a die's mesh arrays (L101) for an orientation question a `run_script` answers.

## 7. Open questions for the owner

Ruled by the owner: 1 (a), options on `frame_control` step and `wait_for`; 2 (a), pausing on a condition only in the step's `until`; 3 (a), `then` carries `call` and `timeScale`; 4 (a), a failing `then.call` fails the wait and leaves `timeScale` unset; 5 (a), riding input sent at the stepped frame's `process_frame`; 6 (a), no report on the met frame; 7 (a), `batch_drive`'s `wait` assertion unchanged; 8 (a), render diagnosis as documentation only; 9 (a), GMCP-7 first as step A1, then step-until and render docs as two issues. Every question is ruled.

New terms, for the glossary once adopted: **met frame** (the frame a condition was first found true, the one `then` acts in and `until` stops on), **then action** (`wait_for`'s `options.then`), **step-until** (a step with `options.until`), **riding input** (a step's `options.input`, sent inside a stepped frame).

1. **The shape of step-until.** (a, recommended) Options on the existing tools: `until` and `input` on `frame_control` step, `then` on `wait_for`. How: section 3. Worst case: `frame_control`'s description grows by two keys, and an agent reading only `wait_for` misses that pausing on a condition lives in the step. (b) A new `step_until` tool with until, a frame budget, an input timeline, a report and a then. How: one call does all of it. Worst case: three tools on one clock with overlapping options and refusals, and one more name every agent file needs. (c) Documentation only: `batch_drive` recipes of pause, step and check-once. Worst case: no loop and no riding input, so the gaps of section 1 stay, GMCP-7 included.
2. **Where pausing on a condition lives.** (a, recommended) Only in the step's `until`; `wait_for` never pauses. How: `frame_control step {count: 1000, options: {until}}` from a running or paused game. Worst case: a stop more than 1000 frames (about 17 s) away needs a `wait_for` on an earlier sign first. (b) Both: `until` on the step and `then.pause` on `wait_for`. Worst case: two ways to pause on a condition, checked at different points (a draw and a `process_frame`), so the frame they stop on differs by one. (c) Only `then.pause` on `wait_for`. Worst case: a paused game cannot be advanced to a condition, since `wait_for` refuses a paused game.
3. **What `then` carries.** (a, recommended) `call` and `timeScale`. How: section 3.1. Worst case: setting any other property in the met frame needs a game method to call. (b) `call` only. Worst case: delve's slow motion (L80) needs a game method that sets `Engine.time_scale`, a game change for a drive. (c) `call`, `timeScale` and `set {node, property, value}`. Worst case: a second way to set a property, with `set_property`'s conversion and read-back rules to carry into the met frame.
4. **A `then.call` that fails.** (a, recommended) The wait fails, its error naming the met frame and that `timeScale` was not set. How: section 3.1. Worst case: an agent that only wanted the condition loses the met result to a call error and reads it from the error text. (b) The wait answers `met: true` with `then: {error}`, and `timeScale` is still set. Worst case: an agent that skims `met` captures frames of an effect that never started, the failure decision 22 ruled out for `options.call`.
5. **Riding input.** (a, recommended) Raw `simulate_input` events placed by stepped frame, sent at that frame's `process_frame`, process unit only. How: section 3.3. Worst case: `_physics_process` sees the just-pressed edge one frame after a real event would give it, which TOOLS.md must say. (b) The same events sent at the previous frame's `frame_post_draw`, where the step unpauses. Worst case: `_process` and UI code never see the just-pressed edge, and `_input` runs a frame before the frame it was placed in. (c) No riding input; TOOLS.md says input to a paused game reaches only `Input`'s held state. Worst case: a game that reacts to `is_action_just_pressed` or an input callback cannot be driven frame by frame.
6. **A report on the met frame.** (a, recommended) None: a step-until leaves the game paused on the frame for any read tool, `then.call` returns what a game method gives, and a watch around the step records the frames up to it. How: no new key. Worst case: a game that cannot stay paused (delve, L79) and has no method returning its state takes a watch to read several values on the met frame. (b) `report: [{name, expression}]` on `wait_for` and the step, evaluated in the met frame. Worst case: a second expression list beside the watch's tracks, with its own budget and errors. (c) `report: "state"`, a `get_game_state` read in the met frame. Worst case: every C# game pays the helper's load on the first report, and a game with no marked nodes reports nothing.
7. **`then` in `batch_drive`'s `wait` assertion.** (a, recommended) No: a `wait_for` tool step carries `then`, and the assertion stays as decision 22 left it. Worst case: in a batch, a `then` wait that times out is a step result (`met: false`), not a failed assertion, so the batch goes on unless an assertion follows. (b) Yes, the assertion takes `then`. Worst case: assertions start running game code, which decision 22 kept out of them for `options.call`.
8. **Render diagnosis.** (a, recommended) Documentation only (section 3.6, step R1); a read tool waits for a game repo to need one. How: the flags through `engineArgs` and presets, `debug_draw` through `set_property`, the world aim's refusals. Worst case: a 3D node that is in front of the camera but drawn nowhere (a culled layer, a visibility range, a zero alpha) is found by reading properties one by one. (b) R1 plus the `render_probe` read tool (step R2). Worst case: a tool built ahead of any evidence, one more name in every read-only agent's list. (c) R1 plus a `take_screenshot` `options.debugDraw`. Worst case: it duplicates a `set_property` pair if R1 finds that pair works.
9. **How the work is filed.** (a, recommended) GMCP-7 lands as step A1 under its own issue first (a filed request ranks ahead of the ideas); step-until (A2-A5) and render docs (R1) become two issues in the "Ideas" project, R2 a third only if question 8 picks it. Worst case: three issues to keep in order, and A2 waits for watch step 2. (b) One issue, GMCP-20's steps in section 6's order. Worst case: GMCP-7's one-step answer waits behind the render docs or the step-until work in review.

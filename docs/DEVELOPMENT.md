## Commands

Everything runs from the repo root through `run.ps1`, and every command runs under `tools/gate.ps1` (`pwsh tools/gate.ps1 -Log <path> -TimeoutSeconds <n> [-Tail <n>] -- <command>`). A gate writes `.tmp/<name>.log`, prints the tail and ends with `gate: passed.` or `gate: FAILED (status n).`. A command that reaches its ceiling is killed with its process tree and exits 124 with `gate: TIMED OUT`. That means it hung, not that it was slow: read the log, never raise the ceiling.

- **C# line length** (`tools/linelength.py`, tested by `tests/tools/test_linelength.py`): a line's characters without its ending (`\n` or `\r\n`), a byte-order mark not counted; a file that is not UTF-8 fails the check.
- **GDScript complexity** (`tools/gdcomplexity.py`, tested by `tests/tools/test_gdcomplexity.py`): cyclomatic complexity over gdtoolkit's parse tree, 1 plus each `if`/`elif`, loop, match branch after the first, `when` guard, ternary and `and`/`or`, lambdas counted in their function; length from the `func` line to its last line. `tools/gdcomplexity-baseline.txt` lists the `file:function` entries still over the limits (none today; a new function over a limit is split, never listed); it can only shrink, since an entry within the limits fails the check until it is deleted.
- **Install** (`tools/install.ps1`, tested by `tests/tools/test_install.py`, Windows only): the mirror into a fresh folder and the junction to the skill, a second run changing nothing, a junction pointing elsewhere replaced, a real folder at the link refused and left alone, a missing `SKILL.md` refused. A locked exe (robocopy status 8 or more) and the worktree warning are not covered.

## Footguns

- **gdformat writes CRLF on Windows.** A file it reformats comes back with CRLF endings, which dirties it against the repo's LF: convert it back (`sed -i 's/\r$//' <file>`) and check `git ls-files --eol <file>` shows `w/lf`.
- **A `git commit` whose hooks all passed can hang forever on Windows: prek deadlocks in its own exit.** `main` calls `runtime.shutdown_background()` and returns, and `ExitProcess` can kill a waking tokio blocking thread while it holds the `thread_local` crate's `THREAD_ID_MANAGER` lock; the main thread's thread-local destructor then waits on it for good (stack measured 2026-09-26 with `cdb -pv`: `LdrShutdownProcess` → `ThreadGuard::drop` → `WaitOnAddress`; exit code already 0, process handle never signalled). `Get-Process` calls such a process exited; `Get-CimInstance Win32_Process -Filter "Name='prek.exe'"` still lists it, and the hook's `sh` and git wait on it. A rare race (none in 443 runs), not caused by the build servers, worktrees or `tools/gate.ps1`. The prek itself cannot be killed: `taskkill` and `Stop-Process` answer that no such process runs (measured 2026-09-26), and it lingers until a reboot. Kill the hook's `sh` instead, which releases git (prek restores the tree before it exits), then check `git log -1` and commit again if the commit did not land.
- **A running server locks the installed exe.** Every Claude session in a game repo holds `%LOCALAPPDATA%\godot-mcp\godot-mcp.exe` open, so `install` fails (robocopy status 8 or more) until those sessions stop; `publish` alone never touches the installed copy. Installing from a linked worktree points the skill junction into that worktree (`install` warns): install from the main checkout.
- **A child process of the server must not inherit its stdin.** stdin is the MCP pipe; on Windows a child started while the server blocks reading it stalls until the read returns (`run_project` hung until stdin closed). Godot and git are started with their own stdin, closed at once. A quiet run on Windows inherits exactly its three pipe handles (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`), made inheritable only around its `CreateProcessW`; every other child start in the server goes through `ChildProcesses.Start`, under the same `StartLock`, because a child started meanwhile would inherit the game's pipe ends and hold its output open.
- **Only an `McpException`'s message reaches the client.** Any other exception becomes "An error occurred invoking '<tool>'.", so tools rethrow session errors as `McpException`. That wrapping is the server pipeline's: `McpServerTool.InvokeAsync`, which `batch_drive` calls, rethrows the tool's exception as it is, an argument of the wrong type as a raw `JsonException`.
- **Logging goes through `[LoggerMessage]` methods in `Log.cs`**: CA1848 and CA1873 are errors under `latest-recommended`. Everything logs to stderr; stdout is the protocol.
- **GDScript's JSON parser reads every number as a float**, so the bridge echoes `int(id)` and the server accepts integral floats as ids.
- **Cyclomatic complexity is capped at 8** by CA1502, a warning and so a build error. The threshold is in `CodeMetricsConfig.txt` at the root, which `Directory.Build.props` passes to every project as AdditionalFiles: the analyzer reads that file, not `.editorconfig`.
- **The error feed needs debug builds for stacks and for GDScript runtime errors.** Godot routes GDScript runtime errors to loggers in debug builds only, and fills script backtraces only in debug builds or with `debug/settings/gdscript/always_track_call_stacks` (cited from 4.7.2's source in the plan's "error feed" section). Errors raised before the bridge's `_init`, and with `application/run/disable_stderr` on, never reach it. A `run_script` source has no path, so its frames read `gdscript://<n>.gd`.
- **Errors are attributed by a sequence window**, so two calls in flight on one session at once may each report the other's errors, and an error a worker thread raises just after a reply is flushed goes out on the next frame and may land on the next call; `get_errors` has them all in order. Errors raised after the `shutdown` reply (in `_exit_tree` during quit) never reach the feed: a run still has them on stderr, an attached game does not.
- **Screenshots are saved under `<project>/.godot/godot-mcp/screenshots/`**, which both projects already ignore, as `<UTC stamp>-<process id>.png` (plus `_preview.png` when scaled), so two games on one folder never write the same file. A crop is in the screenshot's own pixels, which are viewport pixels when the project does not stretch. Baselines live beside them in `baselines/` (`<name>.png` and its `<name>.json` sidecar) and a compare's diff is saved beside its capture as `_diff.png`; `.godot/` is ignored, so baselines are not versioned.
- **Input points are viewport coordinates**, converted to window coordinates in one place (`_to_window` in the bridge) through `get_viewport().get_screen_transform()`. For the root window it equals `get_final_transform()`; measured in a 1000x900 window over 640x360 content: `[X: (1.5625, 0), Y: (0, 1.561111), O: (0, 169)]`, a 169 px bar above and below.
- **Every injected event is a new object followed by `Input.flush_buffered_events()`**, so accumulated input neither merges nor delays it (Godot merges consecutive motions with the same mask, `input_event.cpp` L1031-1075, and warns when one object is sent twice in a frame, `input.cpp` L1540).
- **Injected mouse events carry the mark `device = 0x6D6370`**, and while a gesture plays or injected input holds a button, the bridge swallows unmarked (real) mouse buttons and motions in `_input`. `_input` runs before the GUI (`viewport.cpp` L3527-3537), and Godot filters only on `DEVICE_ID_INTERNAL` (-2), so the mark changes nothing else. Its limits: hover, tooltips and `Input`'s own mouse state still follow the real cursor, because `push_input` updates them before `_input` (L3517-3520). A real button release still clears that button from the GUI's focus mask (L2462-2471). Real mouse events in 4.7.2 carry device 32, not 0.
- **With `emulate_touch_from_mouse` on, every left-button mouse event has a touch twin** (`InputEventScreenTouch`/`ScreenDrag`) with device `DEVICE_ID_EMULATION` (-1), injected events' twins included (`input.cpp` L850-861, L876-891). It is dispatched just before its mouse event, and Controls receive it in `gui_input` (`viewport.cpp` L2213-2287); a Button does not press from it. The mark cannot reach a twin, so the bridge tells its own twins apart by a flag set while `_dispatch` runs, and swallows every other twin while a gesture plays or an injected button is held. Real touchscreen events are left alone, as real keys are. The project setting is dropped on a machine with a touchscreen (`main.cpp` L3662-3668), so tests turn on `Input.emulate_touch_from_mouse` instead.
- **Injected keys cannot carry the mark.** A key event's device is 16 (`input_event.cpp` L669-671) and the built-in `ui_*` actions match only device 16 or -1 (`input_map.cpp` L147-153), so a marked key would stop driving Enter, focus moves and LineEdit's editing keys. Real keys are therefore never swallowed; a quiet run keeps them out by never having focus.
- **A quiet run cannot be muted by the game's buses or deafened by swallowing.** Swallowing in the bridge's `_input` misses scene `_input` handlers (they run first) and `Input` polling (updated before dispatch, `input.cpp` L1005-1041), and kills input the game synthesises itself; muting bus 0 hides the game's own mute and can leak into its saved settings. So quiet is made at launch: `window/size/no_focus` in the override (`project_settings.cpp` L1735, `main.cpp` L2723-2724: the window is shown with `SW_SHOWNA` and never focused, `display_server_windows.cpp` L1964-1966) and `--audio-driver Dummy`, whose thread still runs the mixer so playback advances (`audio_driver_dummy.cpp` L49-78). Windows clamps a new window's position onto the primary screen (`display_server_windows.cpp` L7180-7183, L7206-7211), so on Windows a quiet run starts on a hidden desktop (`HiddenDesktop`, `WinSta0\godot-mcp-<server pid>`, created at the first quiet launch and kept for the server's life) through `DesktopProcess` (`CreateProcessW` with `lpDesktop`, since `Process.Start` cannot choose a desktop); its windows never reach the user's desktop, and screenshots, input, recording and frame steps work there. Elsewhere the bridge moves the window off-screen in `_ready`, and it shows on the primary screen, unfocused, until then (measured on Windows before the hidden desktop: about 300 ms at (0,0)). Measured and rejected: `--position` (clamped), `--wid` (takes focus, and Godot treats itself as editor-embedded), minimized (nothing draws), `--headless` (never draws). Godot creates its main window without `WS_VISIBLE` and shows it in `Main::setup2` before any autoload runs (`main.cpp` L3459, `show_window` L1947-1978 in 4.7.2), about 0.9 s after `Godot.exe` starts, so no override or script can hide it. `STARTUPINFO.wShowWindow = SW_HIDE` does hide a window that still draws, but only when `Godot.exe` is started directly: `Godot_console.exe` builds a fresh `STARTUPINFOW` for the child (`console_wrapper_windows.cpp` L139-150) and drops it. Measured 2026-09-26 with a 5 ms window poller: gdtest, filtered itests and the `--import` prep put no window on the user's desktop; a not-quiet run started outside `run.ps1` (a plain `dotnet test`, or `quiet: false`) shows one, by design.
- **Injected pad events carry the pad's own device id** (0-15), not the mouse's injected mark.
- **By default a machine's real pads feed the same all-device actions and `ui_*` bindings as the injected pad.** This machine has four (`get_connected_joypads()` gave `[0,1,2,3]`), so `device=0` is a real pad's id too; they moved the fixture's menu focus within two frames of start.
  - `options.shutOutRealGamepads` (`run_project`) and `shutOutRealGamepads` (`attach_project`) keep them out. The override writes `joypads/ignore_joypad_on_unfocused_application=true`, and the bridge (`bridge/godot_mcp_gamepad.gd`) marks the application unfocused at startup and after every real focus change (`scene_tree.cpp` L934-942). Godot then drops the driver's pad input (`input.cpp` L1652, L1684) while injected events get through.
  - Its costs are why it is opt-in. Game nodes receive application focus-out notifications: delve mutes on them. Held injected keys release on a real focus change (`input.cpp` L1600-1623). Held injected pad buttons and axes are sent again after it, so their actions fire again.
- **An injected pad never shows as connected.** `get_connected_joypads`, `is_joy_known` and `get_joy_name` are filled only by the platform's pad driver; a game that waits for a connected pad needs an OS-level virtual pad.
- **Input calls to one session run one at a time** (a second waits; two sessions play input at once).
- **Godot converts a property's or argument's value silently**, so the `Inspect` module converts JSON by the declared type itself and reads the value back: a native setter given the wrong type fails with no log (`class_db.cpp` L1569-1610), a typed GDScript member that cannot construct the value is a silent false (`gdscript.cpp` L1536-1557), and C# turns a Dictionary into `Vector2()` (`variant.cpp` L1745-1761). A read-back that differs (a clamping setter, a read-only property) is put back and fails. The declared type has two forms: a method parameter or a variable not exported carries `PROPERTY_HINT_ARRAY_TYPE`/`PROPERTY_HINT_DICTIONARY_TYPE` with type names (`"int"`, `"String;int"`), an exported one `PROPERTY_HINT_TYPE_STRING` with numeric specs (`"2:"` for `Array[int]`, `"24/34:Node2D"`, `"4:;2:"` for `Dictionary[String, int]`; 4.7.2 `gdscript_parser.cpp` L4866-4985), so a converter that reads only the first silently passes an exported container untyped.
- **`call_method` reaches C# `internal` methods too**: Godot's C# source generator exposes every method with a Godot-compatible signature, with no accessibility filter (`ScriptMethodsGenerator.cs` L128-135), and calls one only when the argument count matches exactly, so optional parameters are passed. A refused call is recognised only when the error feed has placed Godot's `callv` error in the `Inspect` module's `call_method`, which needs script backtraces (debug builds, or `always_track_call_stacks`); without them the call returns null with the error in `errors`.
- **The `CsProbe` fixture is a C# project built by the tests**: `CsProbeProject` copies it to a temp folder and runs `dotnet build -c Debug -p:GodotTargetPlatform=windows` there (node reuse and the shared compiler off, the parent's MSBuild variables removed, stdin closed, two minutes), once per test class. Its own `Directory.Build.props` and `Directory.Packages.props` stop the repo's from applying.
- **Frame control shares the game's own pause.** `pause` sets `SceneTree.paused`, the one flag a game's pause menu uses, so a game can undo it; results report the state read afterwards. Nodes with `PROCESS_MODE_ALWAYS` or `WHEN_PAUSED` keep running while paused and during a step, and every step sends the game `NOTIFICATION_UNPAUSED` then `NOTIFICATION_PAUSED`. The bridge is `ALWAYS`, and `process_frame`/`physics_frame` fire regardless of pause (`scene_tree.cpp` L649, L713), which is what keeps it answering.
- **A step counts drawn frames.** It waits on `frame_post_draw`, which never fires while the window cannot draw (minimized) or, in low-processor mode, while nothing changed (`main.cpp` L5071-5087); both are refused up front, and a step whose frames stop mid-way ends at its deadline. Physics ticks per drawn frame vary with frame time (`main_timer_sync.cpp` L355-356) unless `--fixed-fps`, so a process step's `physicsFrames` varies while a physics step's is exact; a physics step's pause lands after the next tick has already flushed input and run the physics servers' `sync()`/`flush_queries()` callbacks (`main.cpp` L4972-4999). A quiet off-screen window is not held to 60 fps (about 170 measured).
- **`wait_for` expressions see only their inputs** (`node`, `root`, `tree`, `Input`, `Engine`), not autoloads or other singletons (`expression.cpp` L707-734): reach an autoload through `root.get_node`. An expression naming `node` without a `node` in the condition parses and then fails each check, counting as not met with one error in the feed.
- **The process the server starts is not the game.** On Windows it is the `Godot_console.exe` wrapper, so `run_project`'s `processId` and `GodotSession.ProcessId` are the wrapper's; the game (Godot.exe) reports its own pid in the hello (`GodotSession.GameProcessId`), and the hang watchdog samples that one.
- **A timed-out call fails up to 3 s later than its timeout**: the watchdog's 2 s ping, plus a 1 s CPU sample when the ping goes unanswered. It never uses `Process.Responding`, which asks the window through `SendMessageTimeout` and counts a thread as hung only after 5 s; `ProcessThread.WaitReason` throws unless the thread waits, so it is read only in the Wait state.
- **An attached session has no process and no captured output.** Its game must start after `attach_project` has written `override.cfg` and the one-use `.godot/godot-mcp/attach.json`: a game already starting when the call comes has read its settings without them.
- **An empty native Object property is not a GDScript null**: a native getter's null Ref is `TYPE_OBJECT`, equals `null` and fails `is_instance_valid` like a freed object; only `str()` tells them apart (`<Object#null>` against `<Freed Object>`). The JSON module reads it as null and the read-back comparison treats it as null.
- **Outside the editor, `ResourceLoader.get_resource_uid` reads only the uid cache** (`core/io/resource_loader.cpp` L1412-1416 in 4.7.2), so in a project never imported it is -1 for every file, even one whose header carries a uid; and a `--script` save writes no uid at all. `scene_edit.gd` therefore reads uids from the source file, the file's header, its `.uid` or its `.import`, and writes them back after each save. A binary `.scn` has no readable uid, so the edit tools refuse it.
- **An edit of a node inside an instanced scene, or a delete of a node an inherited scene gets from its base, is lost at save**: `pack` stores only nodes the root owns and the instance re-creates the rest (`packed_scene.cpp` L799, L1142). The headless edit tools refuse both, naming the scene to edit instead, as the editor does. A connection is lost only when its source is inside the instance; its target may be (it is saved by path: `packed_scene.cpp` L1142-1143).
- **A C# node whose class is missing from the assembly has no script**: while the build is red, `get_script()` returns null even though the scene stores `script = (res://X.cs)`, so the headless tools read the script from the scene state when they need to know a node is C#, and for an instance root follow its scene file's dependencies (and theirs) to a `.cs` script.
- **A tool method has at most five schema parameters**, plus a `CancellationToken`. The SDK builds a tool's flat schema from the method signature, so flags beyond five go into an `options` object: `run_project(projectPath, scene, userArgs, engineArgs, options {quiet, shutOutRealGamepads, session, prepare, preset})`, and `gamepad_axis` / `gamepad_stick` take `options {durationMs, release}` (`SweepOptions`) before `session`.
- **Prep's `dotnet build` runs without the server's MSBuild environment**: the parent's MSBuild variables are removed, `MSBUILDDISABLENODEREUSE=1` is set and `-p:UseSharedCompilation=false` passed, because a leftover MSBuild node or compiler server holds the redirected output pipes open. `ToolProcess` stops reading 5 s after the process exits if a grandchild still holds them, and logs that it did. Never `--build-solutions`: the editor dies on a cold cache. An import writes a `.uid` file beside every script, which is why prep imports only when an imported file is missing, never merely because `.godot/` is.
- **Several sessions can share one project folder** (delve's server and clients). They share its one `override.cfg`, which is removed only when the last live session on the folder ends, so they must agree on `shutOutRealGamepads`; and only one attach per folder can wait at a time, since the attach file is one per folder.

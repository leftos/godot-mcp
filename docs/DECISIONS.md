# Decisions

The user's decisions and the engine facts behind them, from the first version (2026-09-25 to 2026-09-26), promoted from its plan when it shipped. How the code works now is [ARCHITECTURE.md](./ARCHITECTURE.md); this page is why. A later decision that reverses one here edits it in place and says so.

## Why this server exists

The user's two Godot projects (opening-hand and delve-the-dungeon, both C#, Godot 4.7.2) were driven through the third-party `godot-mcp-runtime` 3.4.0 (npx, TypeScript, MIT), whose costs were recorded across both repos:
- **The bridge is written into `project.godot`**, and `stop_project` has left it there. There is a commit rule in both repos and in the user-level Godot conventions because of it.
- **Simulated input misses.** Motion events carry no `button_mask`, so a drag does nothing (2026-09-25). Clicks land in window pixels while `get_ui_elements` reports viewport pixels, so a letterboxed window misses small buttons. Typed text arrives in lower case.
- **`run_project` passes no arguments**, so delve uses a launch-then-attach workaround.
- **One command at a time**, no request ids, and JSON parsed out of stdout by finding the first bracket.

## Decided (user, 2026-09-25 and 2026-09-26)

1. **Fresh code.** `godot-mcp-runtime` (MIT) and Godot's source are read for reference only; nothing is forked.
2. **The bridge is injected and never committed.** A run loads it through `override.cfg` in the project folder, which is hidden from git through `.git/info/exclude`.
   - Verified 2026-09-25 on 4.7.2: an `override.cfg` autoload pointing outside the project loaded, and `project.godot` was untouched.
   - Godot's source: game runs read `override.cfg`; the editor, `--import` and `--export` never do (`main/main.cpp:2107`, `p_ignore_override`).
3. **C# / .NET 10 server, GDScript bridge.**
4. **Its own repo at `X:\dev\godot-mcp`.**
5. **First-version must-have: faithful input**, offered as gestures plus raw events. Gamepad input is part of it: buttons, sticks and triggers per device (user, 2026-09-25).
6. **The 16 headless scene and node tools are included.**
7. **`run_project` takes pass-through arguments.**
8. **Cutover at parity**, in every project at once; the old registration is removed.
9. **Sixteen friction features, all before the cutover** (user, 2026-09-25, choosing every option offered and "all before cutover" over building only the structural ones first):
   - Time: frame control, `wait_for`, `restart_project`, fresh-worktree prep.
   - Inspection: the running scene tree, `inspect_node`/`set_property`, `call_method`, an error feed on every result, screenshot baselines.
   - Scale: several sessions, a hang watchdog, quiet by default, in-engine recording.
   - Ergonomics: tool annotations, a batch drive tool, compact outputs, project profiles.

   This reversed decision 5's "several sessions" and "in-engine recording" as later work.
10. **Sessions, the error feed, screenshots and quiet runs** (user, 2026-09-25, each the recommended option of a ranked choice):
    - **Session names.** `run_project` and `attach_project` take an optional `session`; without one, the session is named after the project folder. A second session under a live name is refused and asked for a name; a name whose run has exited is replaced. Runs, attaches and process sessions share one name space.

      A stopped run is kept until then, for its crash output, a restart by name and a recording's outcome, but `list_sessions` and the session errors show only the live ones, with a count of the stopped (user, 2026-09-27, #11). `stop_project` says a run had ended before it (`alreadyExited`) and gives the game's own exit code beside the wrapper's (user, 2026-09-27, #12).

      A runtime tool without a name uses the only session, and with several it refuses, listing the names. The refusal and every `session` description tell the agent to pass the session `run_project` or `attach_project` returned on every call from the start, since another agent's game can start at any time; no default session is kept (user, 2026-09-28, #35).

      One server process serves one client, so the agents in it cannot be told apart, and a default one agent set would send another agent's calls, `stop_project` included, to its game. `list_sessions` (read-only) returns each session's name, project, kind (run, attached or process), liveness and process id.
    - **Several sessions on one project folder** (delve's server and two clients). The marked `override.cfg` is reference-counted and removed when the last session on that folder ends.

      Across servers too: its second line lists the server processes (pid and start time) with live sessions on it, a release takes one off and deletes the file only when none is left, and a file whose owners have all exited is stale, removed by a headless run on the folder and by every server's startup sweep of the folders it has written to (the user chose this over leaving the leftover for the bridge to make harmless).

      `stop_project {projectPath}` on a folder with no session also clears a stale marked `override.cfg` and `armed.json` on demand, so a folder can be freed without waiting for a server start (an orchestrator decision, open to the owner). Each file is judged and deleted through one handle, only when every owner it names has exited, an owner entry that does not parse counts as live, and the owners list is opened strictly: when it will not open nothing is touched. A file another process holds is reported in `warning`, never failing the stop; `attach.json`, the join, dormant and scratch status files and the `.git/info/exclude` line stay.

      A new session whose `shutOutRealGamepads` differs from the live ones' is refused, since the file holds one value. An attach is refused while another attach on the same folder is still waiting for its game.

      **Scratch sessions are exempt from the agreement** (GMCP-232; an orchestrator decision, not an owner ruling). A `run_scratches` session is headless, so its quiet and pad settings never reach a player: it always runs quiet with real pads live and unmuted, copies nothing from a live session or the arm, and is never refused against the folder's arm or its other sessions. `run_project`, `attach_project`, `restart_project` and `arm_project` are not refused because of a scratch session, and still are for a non-scratch session or the arm.

      A non-scratch run, attach, preview or arm beside scratch sessions only writes its own values into `override.cfg`, and every writer leaves the file untouched when it already lists this server with the same values. `preview_scene` takes its settings from non-scratch sessions, else the arm, else quiet with live pads, never from a scratch session. Agreement across servers through `override.cfg` is unchanged, and so are its refusal texts. After a windowed drive ends while scratch sessions still hold the folder, the file keeps the windowed values until they end, so another server's quiet session is refused meanwhile (accepted).
    - **The five-parameter limit holds.** `session` goes into `run_project`'s `options`; `gamepad_axis` and `gamepad_stick` move `durationMs` and `release` into an `options` object to make room for it.
    - **Error feed.** The bridge registers a `Logger` (`OS.add_logger`, confirmed in 4.7.2's source first) and sends errors with function, file, line and Godot's script backtrace over the wire, so attached games report too. Results carry errors only, in an `errors` array, and the call still succeeds; `get_errors(since)` returns errors and warnings keyed by a per-session sequence cursor.
    - **Screenshots** default to an inline preview at most 480 px wide, plus the full-size path.
    - **Quiet by default** (reshaped by the user on 2026-09-26 after review measured the first build): `run_project` starts quiet unless `options.quiet = false`.

      The window is created unfocused and off-screen by the quiet run's `override.cfg` (`[display]` `window/size/no_focus` and an off-screen initial position), because Godot creates the main window focused before any script runs (`platform/windows/display_server_windows.cpp` L1970-1973), and un-focusing it later does not release the focus it holds.

      It stays click-through. Audio is off through `--audio-driver Dummy`, placed before the user's engine arguments, never by touching the game's buses, so the game's own mute stays testable and no muted state leaks into its saved settings.

      Real input is kept out by the window never receiving it, not by swallowing: an always-on swallow also killed input the game synthesises itself (on-screen keyboards, virtual cursors) and never reached scene `_input` handlers or `Input` polling. The real mouse is still swallowed while a gesture plays, as before. Sessions on one folder must agree on quiet (the override holds one value).

      An attach is quiet only with `quiet: true` (user, 2026-09-27, #14): the override and the bridge's parking apply, but only a launcher can put a game on the hidden desktop or pass `--audio-driver Dummy`, so a debugger-launched game still shows for a moment at start and needs that argument in its own launch for silence.

      Real pads stay opt-in through `shutOutRealGamepads`. Ruled out: marking injected keys with the mouse's device mark (a key's device is 16 and the built-in `ui_*` actions match only 16 or -1: `core/input/input_event.cpp` L669-671, `core/input/input_map.cpp` L147-153).
    - **A quiet run caps its frame rate** (user, 2026-09-26, issue #6): the bridge sets `Engine.max_fps` to 60 when the project leaves it at 0. The window keeps VSync however hidden it is (`display_server_windows.cpp` `window_can_draw` L3123-3129 depends only on minimizing), so a quiet run drew at the monitor's 239 Hz.

      A project's own cap, or a `--max-fps` in `engineArgs`, wins; the bridge cannot tell an explicit 0 from the default. A recording run is unaffected: its fixed fps skips the frame delay (`main.cpp` L5170-5178).
11. **Time, inspection, prep, the watchdog, baselines, profiles and batches** (user, 2026-09-26, each the recommended option of a ranked choice; the rest settled from measurements and the explorers' 4.7.2 citations):
    - **Time.** One `frame_control(action, count, scale, options {unit, screenshot})` tool: pause is `SceneTree.paused` (the bridge is `PROCESS_MODE_ALWAYS`); `step` counts whole frames from one `frame_post_draw` to the next (or physics ticks with `unit: "physics"`), pausing first and leaving the game paused, and can capture on the Nth frame; `time_scale` sets `Engine.time_scale` in (0, 100].

      `wait_for(condition, timeoutMs)` takes exactly one of `{node, exists}`, `{node, property, equals}`, `{node, signal}` or `{expression}` (Godot's `Expression` with `node`, `root`, `tree`, `Input`, `Engine`); a timeout (default 10 s, cap 120 s) is a result `{met: false, last}`, not an error; while paused only a signal wait is allowed.
    - **Inspection.** `get_scene_tree` pages a flat depth-first list like `get_ui_elements`; `inspect_node` returns script variables plus editor-visible properties by default. `set_property` and `call_method` convert JSON by the declared type and read back, failing loudly, because Godot's own conversions fail silently (`gdscript.cpp` L1536-1557, `class_db.cpp` L1569-1610, `variant.cpp` L1745-1761). A C# fixture (`tests/fixtures/CsProbe`) proves `call_method` on C# methods.
    - **Restart and prep.** Prep (a missing import cache, a missing or stale C# assembly) runs automatically in `run_project` and `restart_project`, skipped by `options.prepare: "never"`. The build is `dotnet build <csproj> -c Debug -p:GodotTargetPlatform=windows`, not `--build-solutions` (the editor dies on a cold cache, delve's DEVELOPMENT.md L110).

      Sources count as changed when the newest source mtime under the git top level is later than the assembly's. A restart builds first, then stops, then launches, so a red build leaves the old game running; it keeps the same session, so error `seq` numbers continue. Step 11 reuses step 12's C# fixture.

      Settled 2026-09-26 (user, each the recommended option): an import runs when a versioned `*.import`'s `dest_files` target is missing, or `*.uid` files exist with no `.godot/uid_cache.bin`, never merely when `.godot/` is missing (the InputProbe copies run without one, and an import writes `.uid` files beside scripts); a red build refuses `run_project`'s launch with the parsed errors; an import is refused while another session's game runs on the folder.

      Settled from the explorer's map: `restart_project` relaunches with the stored arguments only (other arguments mean `stop_project` then `run_project`) and refuses an attached session.
    - **Watchdog.** Checked only when a request times out: a 2 s ping, and when that is silent too, the call fails as "main thread is stuck" with the game process's CPU, threads and last stderr lines. The bridge's hello carries the game's own pid (the server's process is the `Godot_console.exe` wrapper). Stop kills at once only when a ping is silent; otherwise it keeps the graceful order.
    - **Baselines.** Stored at `<project>/.godot/godot-mcp/baselines/<name>.png`, written only by an explicit `save_screenshot_baseline`; a compare against a missing one fails with a hint.

      The comparison runs in the bridge with Godot's `Image` (about 0.1 s at 720p, measured; no new dependency): pixels whose largest channel difference passes a tolerance (default 2/255) are counted, with a bounding box and a changed ratio; a size mismatch fails. The crop is stored with the baseline in a `<name>.json` sidecar and reused by the compare (user, 2026-09-26).
    - **Profiles and batch.** `godot-mcp.json` beside `project.godot`: `{scene, userArgs, engineArgs, resolution, quiet, presets: {name: {…, session}}, processes: {name: {command, cwd, env, ready, description}}}`; `run_project`'s `options.preset` merges one, explicit arguments win and user arguments append.

      Presets launch Godot only. A program that is not a Godot game (delve's `dotnet run` server) is declared in the profile's `processes` section and started by name with `run_process` as a process session (decision 36); the shell no longer keeps such companions.

      The batch tool runs existing tools by name plus assertions (`property`, `expression`, `no_errors`, `wait`) server-side in order, stops at the first failed assertion or tool error, and returns every step's result with screenshots as paths.

      Settled at build time (user, 2026-09-26): the batch calls tools through the SDK's tool collection; `property` and `expression` assertions check once (a new `wait_for` `timeoutMs: 0`, allowed while paused); `no_errors` looks back to the previous `no_errors` or the batch start; a `screenshot` assertion needs `compare_screenshot`'s `match`; at most 100 steps and 300 s. Profiles: the top level applies to every run, a preset replaces `scene`, `resolution` and `quiet` and appends arguments, explicit arguments win, and parsing is strict.
12. **The headless scene tools** (user, 2026-09-26, each the recommended option of a ranked choice; the rest settled from the explorer's probes). The remaining tools are 14: the reference's ninth node tool is `get_scene_tree`, shipped here as `get_scene_file_tree`.
    - **Values out.** A Node reads out as its path from the scene root (`.` for the root, null outside the scene). A Resource reads out, in the shared `bridge/godot_mcp_json.gd` so runtime `inspect_node` gains it too, as `{resource, uid?, class}` when external and `{class, subResource?, properties}` (its non-default stored properties) when built-in or unsaved.

      Values in: a Resource-typed property takes `"res://…"`, `"uid://…"`, `{resource}`, `{type, …properties}` or null; a Node-typed export takes a path from the scene root; enums take integers, as runtime `set_property` does.
    - **Edits.** A list edit (`delete_nodes`, `set_node_properties`) is all-or-nothing: one failing entry saves nothing and the result names it. An edit of a node inside an instance is refused, naming the instance's scene (the reference loses it silently: `packed_scene.cpp` L799, L1142).

      Scenes open with `GEN_EDIT_STATE_MAIN` and instanced children with `GEN_EDIT_STATE_INSTANCE` (the reference's DISABLED flattens inherited scenes and doubles inherited connections: `packed_scene.cpp` L233-236, L682).

      A save restores the header UID and every `ext_resource`'s `uid=` (a `--script` save writes neither: `resource_saver.cpp` L285-294). A new scene gets a fresh UID (`ResourceUID.create_id`). `duplicate_node` copies by packing the source under a bare holder and instantiating with MAIN (`Node.duplicate()` bakes instances: `node.cpp` L2789-2798); a name collision is refused. A second identical `connect_signal` is refused as already connected; an inherited connection cannot be disconnected.
    - **Imports.** An importable file a request names that has no `.import` sidecar is imported first through prep's import.
    - **Shapes.** `add_node(projectPath, scenePath, nodeType, nodeName, options {parent, properties})`, the reference's top-level position/rotation/scale/visible/modulate moving into `properties`. Write tools always prepare; read tools keep `options.prepare`. `create_scene`'s root is named after the file in PascalCase unless `rootName` is given.

      Only `.` and relative node paths are taken; `root/…` is refused with a hint. `get_node_properties` returns what `inspect_node` does, and `changedOnly` means the values the scene file stores. `load_sprite` takes any node with a `Texture2D`-typed `texture` property.

      `export_mesh_library` follows the editor's rule (each `MeshInstance3D` with a mesh under the root, not looking inside one, shapes from `StaticBody3D` children, no previews: `mesh_library_editor_plugin.cpp` L458-618); items and shapes use the node's local transform as the editor does, but the navigation mesh is composed with the item transform, where the editor places it by its region alone and misplaces it under an offset mesh (user, 2026-09-26).

      `batch_scene_operations` takes every write op and stops at the first failure, saving nothing, as `batch_drive` does. Read-only: `get_node_properties`, `get_node_signals`; destructive: `delete_nodes`, `disconnect_signal`, `export_mesh_library`, `batch_scene_operations`.
13. **Input capture** (user, 2026-09-26, each the recommended option but the last). The bridge records both sources on its one clock, real events from the root Window and injected ones at its dispatch, so a gesture comes back as its raw events and the order between a person's input and an agent's is exact; the alternative, the server logging gestures and merging them with the bridge's real events, put two clocks a round trip apart.

    A quiet run captures the server's gestures only and says so in a warning, rather than refusing.

    The bridge streams what it captures to the server in batches, so a capture survives a crash, stop or restart and the next stop returns it; the recommended option, dropping it with the game as snapshots are, would lose the recording of what led to a crash. Orchestrator defaults: the tool is `capture_input` ("recording" already names the Movie Maker video), motions with no button held are dropped unless asked so a drag still replays, and at 2000 events capture stops with `truncated`.
14. **Games listen only to the gamepads players choose** (user, 2026-09-26). None of the user's Godot games treats every connected pad as input. A seat is claimed by a button press on a pad, never by an axis. At connection (and on reconnect, or from settings) each pad's axes are sampled while idle, so a resting value becomes that axis's centre and a pad that jitters at rest is flagged as noisy (the user's idea: this machine's Winwing MCDU rests its stick at -0.98 and jitters).

    A device `Input.is_joy_known` does not map as a gamepad is listed in settings but never offered at the claim prompt. The rule lives in the shared Godot conventions, and each game builds it from its own plan.

    This server's gamepad tools inject, when no `device` is given, on the lowest id 0-15 no real pad holds and report it, so an agent claims that pad in a game's selection step as a player would.

    How (user, 2026-09-26, each the recommended option): the chosen id is kept for the game's life and re-picked only once a real pad has connected on it; the rule is the same in shut-out mode, where real pads are still listed as connected; an explicit `device` a real pad holds is injected as asked with a `warning` naming that pad; `simulate_input`'s raw `joypad_*` events without a `device` follow the same rule.

    The shared test sessions all launch shut out of real pads, and a test that needs real pads live launches its own game (user, 2026-09-26), rather than a reset that tries to tell which actions a real pad holds.
15. **Scene-file splices, timed captures and stopping timed-out scripts** (user, 2026-09-28, each the recommended option of a ranked choice).
    - **A headless edit keeps what it did not touch** (#24).

      Godot's saver has no flag that keeps a file's layout (`ResourceSaver.SaverFlags`), so an edit saves as today, then splices: every section the edit left alone keeps its original text byte for byte, and an added or changed node or resource takes Godot 4.7's form, except that a changed node keeps its own header's `unique_id` state (none when it had none, its original value when it had one); only an added node takes Godot's drawn `unique_id`.

      Changed sections are found by comparing sections, ignoring `unique_id` and the saver's id renumbering, rather than by each op reporting what it touched, so an op cannot drop an edit by forgetting to report it. `save_scene` stays a full re-save, the explicit way to bring a file to 4.7's form. A section the splice cannot map falls back to the full save with a `warning`.

      Keeping a changed node's id state reverses an earlier ruling that let it take the drawn id because the editor's next save adds one anyway: a property edit in a scene with no ids then showed a stray header change that agents reverted by hand (GMCP-88). Ruled out: a splicing `save_scene` (no tool would upgrade a file).
    - **`capture_frames`** (#25). A new tool takes `at` (a list of seconds) or `{every, for}`, counted in game time from the call's start (the sum of scaled frame delta, so it follows timers under `Engine.time_scale`); the bridge grabs in-process with no round trips; a late frame is taken and its lateness reported; at most 1000 frames and 120 s; stamped files in the screenshots folder, `path_only` by default; a paused game is refused as `monitor_property` refuses it.

      Ruled out: an option on `frame_control` (stepped games only) and a real-time clock (it drifts from the game's timers, the drift #25 reports).
    - **One capture helper, compositing non-embedded windows**, built with `capture_frames` rather than later: every grab (`take_screenshot`, baselines, frame steps, `wait_for`, `preview_scene`, `capture_frames`) goes through one helper that pastes each visible non-embedded `Window` at its offset from the root, the offset checked on a visible desktop.

      A quiet run launched on the hidden desktop is no longer parked off-screen, since Windows clamps a native popup of a parked root to (0,0) and its offset is lost; attaches and runs off the hidden desktop stay parked (user, 2026-09-28, over landing the helper for visible runs only).
    - **A timed-out `run_script` or `call_method` is stopped** (#26). The server cancels on timeout as it does for `wait_for`; the bridge drops its reference to the script instance, which in 4.7.2 disconnects the suspended coroutine so it never resumes.

      The bridge restores `Engine.time_scale` and `SceneTree.paused` to their values at the call's start only when it stops a call, and the timeout says what it stopped and restored, and that a coroutine the script awaited on another object keeps running.

      A script that finishes keeps its changes. Ruled out: a `ctx.cancelled` flag (it changes `execute`'s contract) and a report-only timeout with a `stop_script` tool (the next run is still corrupted when the message is skipped). `run_csharp` keeps its "still running" answer; a snippet stops itself through a token (decision 18).
16. **Moving nodes in a scene file** (#27; user, 2026-09-28). A new `move_node` tool, batchable like every other edit, moves a node among its siblings or to another parent; `add_node` takes the same `options.position`. A position is one object with exactly one of `index`, `before` (a sibling's name) or `after`. A negative `index` counts from the end as Godot's `move_child` does (-1 is last), chosen over refusing negatives.

    Reparenting is in (chosen over a later item): the subtree keeps its owner, a node cannot move under itself or its own descendant, a name clash under the new parent is refused. A node of an instance or of a base scene is refused, as the editor refuses it, since the saved file cannot record its move (`packed_scene.cpp` L491, L766-776). The splice keeps the saved order of node sections and its self-check compares that order, since a reorder alone changes no section.
17. **No editor bridge** (user, 2026-09-28). `preview_scene` covers seeing a scene an agent edits headless, so no `EditorPlugin` bridge is built. Should the need return, the open questions were enabling a plugin through `override.cfg` rather than the tracked `project.godot` and headless saves racing an open editor's copy of the scene; hybridindie/godot-mcp routes edits through `EditorInterface.get_editor_undo_redo()` and refuses a move while `get_unsaved_scenes()` lists the scene.
18. **A `run_csharp` snippet sees its timeout as a token** (user, 2026-09-28). `SnippetGlobals` gains a protected `CancellationToken Cancellation` that the call's timeout cancels; a snippet passes it to its awaits or checks it in its loops, and one that ignores it keeps running as before.

    No `Checkpoint()` helper: it would do no more than `Cancellation.ThrowIfCancellationRequested()`. The timeout's reply is unchanged and sent at the timeout; what the snippet does after it (a stop, an exception) is dropped silently, as a reply to a timed-out request id is.

    Only the helper's `forget` cancels it (the server's cancel, the bridge's backstop and a lost connection all end there), and it reaches the snippet through the bridge's per-frame poll, so a snippet stuck in a main-thread loop that never yields cannot see it; the tool's docs say so.

    Ruled out: a real-time `CancelAfter` in the helper (it runs on wall time while the server's timeout is load-adjusted, so under load the snippet could cancel first and one call answer two ways), waiting only through helpers that stop on cancel (a snippet's own CPU loop could not be stopped) and a debug-output line on a late stop (noise in the game log).
19. **A C# field named like an engine property does not reach the saved scene** (#32; user, 2026-09-28). Headless, a C# script is a real instance, and `Object::get` asks the script instance before the engine class (`object.cpp` L319-326), so a field such as `private float scale` answers for `Node2D.scale` and `PackedScene::pack` stores it (`packed_scene.cpp` L883, L981-984); the editor writes the file cleanly because it gives a non-tool C# script a placeholder instance.

    A headless save stores the engine's value for such a name, as the editor does, by rewriting the packed state after `pack`, and its result warns with the field's name; `get_node_properties` and `set_node_properties` read and set engine properties through `ClassDB`, so they agree with the file. Ruled out: refusing the save until the field is renamed (it blocks every headless edit of the scene).
    - **An instanced or inherited node too** (user, 2026-09-28, each the recommended option). Godot builds an instance whole, script included, before it applies the instancing record's overrides with `Object::set`, which the script instance answers first (`packed_scene.cpp` L266, L233, L494; `object.cpp` L239-245), so an override lands on the field. Every instantiation for editing restores the hidden engine values from the SceneState stack, inner scenes first.

      A non-plain record's pair is dropped when the engine value equals what its instanced or base scenes give the node, found by walking the SceneState stack as the engine's `PropertyUtils` does, never by instantiating the base scene again (that would rerun the user's `_init`). Object values are not restored: a `local_to_scene` resource set raw would be shared by every instance.
20. **Scene-edit frictions from delve-the-dungeon** (#33; user, 2026-09-28, each the recommended option of a ranked choice).
    - **`attach_script` keeps the values the new script still declares**, by the editor's rule (`InspectorDock::store_script_properties` / `apply_script_properties`, `inspector_dock.cpp` L631-683): every storage script property of the old script is stored before `set_script`, and set after it when the new script declares the name and the value's Variant type matches, or an Object value fits the new property's hint.

      The result lists the kept and dropped names. Ruled out: a stricter same-type-and-hint rule (a swap the editor keeps would lose values here).
    - **A save keeps the source's stored set.** Godot's `pack` compares against the ClassDB default, which is 3 for `layout_mode` on every Control subclass (built parentless) and 0 on `Control`, so a subclass in position mode gains `layout_mode = 0` (`class_db.cpp` L2184-2196, `control.cpp` L978-982, L4911-4912); the editor writes the same line and the loaded scene is identical.

      Every save with a source drops a pair the source did not store when its value equals what the source node loads as, with a self-check that falls back to the full pack and a `warning`.

      Ruled out: `save_scene` only, and documenting it as a footgun. The other half (#64): `pack` also leaves out a line the source stored when its value is the default, the class's (`Label`'s constructor sets `SIZE_SHRINK_CENTER`, `label.cpp` L1531) or the instanced scene's, and the splice then took Godot's text for an untouched node.

      A save that keeps the layout (every edit, a save-as) puts each such pair back when the packed scene still reads that value, with the same self-check and `warning`; an in-place `save_scene` does not, as it brings a file to Godot's form.
    - **A full-rect Control's stored `layout_mode = 3` becomes 1 at every headless save** (GMCP-25). Under a Control parent the node reads 1 (Anchors) from its anchors, and `pack` stores that (4.7.2 `control.cpp` L944-947). The put-back above cannot keep the 3 without changing the load, since the loaded node reads 1.
    - **`save_scene` save-as splices against the source's text**, so the sections it leaves alone keep their `ext_resource` ids and tag lines; an in-place `save_scene` stays the full re-save of decision 15.
    - **A script with no `.uid` gets one**, computed as the editor's scan does (`ResourceUID.create_id_for_path`, `resource_uid.cpp` L134-154; measured identical to an import's) and written beside it, for scripts and shaders (`should_create_uid_file`, `resource_loader.cpp` L1428-1440); the result names the written file so the agent commits it.

      Loads outside the editor log "invalid UID" until the cache knows a uid (`resource_format_text.cpp` L491-506), so each uid a headless edit creates is appended to `.godot/uid_cache.bin` when the cache exists (never creating one), and prep imports when the cache's contents lack a scanned `.uid` or scene header uid, which covers an editor save that drops the appended entries (user, #34).

      Ruled out: importing before every such edit (3-6 s each, and refused while a game runs on the folder), appending without the prep check, and a warning only.
21. **The live tools reach a C# field Godot does not list** (#36; user, 2026-09-28, each the recommended option). The editor binary the server runs lists only a C# script's `[Export]` members, while `get` reads every field (`csharp_script.cpp` L1500-1527, L2725-2750), so `inspect_node`, `set_property`, `wait_for` and `monitor_property` accept a name `in` the node that is not a method, signal or class constant, and `set_property` converts by the held value's type.

22. **A pause and a capture in game time, started from a call** (#41; user, 2026-09-29, each the recommended option). `wait_for` gains `{gameMs: N}` (1-120000; met once N ms of scaled process delta have passed) and `{frames: N}` (1-7200 unpaused process frames), each a condition alone; their clock sums delta on the bridge's `process_frame` as `capture_frames` does, starting at the first frame after the request, and a paused frame adds nothing.

    Left out, their `timeoutMs` is derived as `capture_frames`' and `step`'s allowances are (N + 10 s; 10 s + 100 ms a frame), up to 600000; an explicit one wins; check-once (`timeoutMs: 0`) and a start while paused are refused.

    `capture_frames` and the two waits take `options.call {node, method, args}`: the bridge runs it with `callv` in the frame their clock starts and does not await a coroutine, so `at` and `gameMs` count from the method's entry; a refused call, or a new error in the bridge's error feed across the `callv` (a GDScript runtime error or C# exception cannot be caught), answers that error and no frames.

    `batch_drive`'s wait assertion takes the new conditions but no `call`: a `call_method` step goes before it. Ruled out: keeping the 10 s default (a long game-time wait reads `met: false` as the effect not happening), keeping the frames and listing the error (frames of a broken effect read as the real one), and awaiting a coroutine before the clock starts (a method that awaits its whole effect starts the clock after it ended, the miss #41 reports).

    `capture_frames` also takes `options.start {node, property, equals | exists | expression, edge?, timeoutMs?, then?}`, a condition laid out as `wait_for`'s (kinds `exists`, `property`, `expression`; another is refused), and its points count from the frame the start is met.

    `start.then` runs in the met frame (call, then `timeScale`, as `wait_for`'s `then`), the capture's own `options.call` runs after it, and the clock starts in that frame; a start already met at the request starts the clock at the next process frame, as a plain capture does.

    `start.timeoutMs` defaults to 10 s (0 checks once) and is added to the capture's allowance, at most 600000 ms; a start that times out is a success with `stopped: true`, no frames and `start: {met: false, last}`. Chosen over a capture started from `wait_for`'s `then` because `capture_frames` already owns the points, crop, result shape and busy guard, and it removes the round trip that put the capture's points 40 to 270 frames after the met frame.
    - **`capture_frames`' `options.start` takes a `call`, and an `every` series always has a point at 0** (GMCP-123, GMCP-125). The start's call runs after the start's baseline check (for an `edge` start, its first false check), so the start sees the rise its own call makes: a change made by an earlier tool call can rise and fall before the next call's first check, since that call reaches the game 0.2 s to seconds later.

      `start.timeoutMs` counts from after the call, the clock starts in the met frame (the call's own frame at the earliest), `start.call` is allowed without `edge`, and its value is reported as `start.call: {value}` whether the start is met or times out. A point at 0 is always taken, in the clock's first frame after `options.call`, and counts against the 1000-point cap.
    - **Acting in the met frame is a separate `options.then {call?, timeScale?}`** (GMCP-7; the design and its rulings are archived in [plans/archive/step-until-render.md](./plans/archive/step-until-render.md) sections 3.1 and 7), run once in the frame a `wait_for` condition is first found true, and taken by every condition kind. `options.call` keeps its meaning, the start of the checks, since a wait takes both: a call at its start and a `then` in its met frame.
    - **`options.then` also takes `pause: true`** (GMCP-100; the owner ruled [plans/archive/step-until-render.md](./plans/archive/step-until-render.md) question 2 (b)), pausing the game in the met frame as `frame_control pause` does, beside `frame_control` step's `options.until`. Why: a wait on a running game can be longer than a step's 1000 frames (about 17 s at 60 fps), and a game repo needed the met frame held for later reads and crops.

      The cost is two ways to pause on a condition, checked at points half a frame apart: a plain wait pauses at the met frame's `process_frame`, before its `_process`, a screenshot wait and a step after the frame is drawn. A wait met while a step or `capture_frames` runs does not pause and fails, naming the running one; `capture_frames`' `start.then` refuses `pause`.
    - **`options.call` is taken by `exists`, `property` and `expression` waits as well as `gameMs` and `frames`** (GMCP-98), so a step and the condition on its effect run on one clock: a `call_method` then an expression wait left a round trip between them, and the condition could already be past its threshold when the wait began, so the screenshot and `then.call` caught a later moment. `signal` and `uiChanged` waits still refuse it.

      The call runs in the frame the checks start (the next process frame); `frames` and `elapsedMs` count from the first check, which follows the call in that frame, so a wait met there reports `frames: 0`. With `options.edge` the baseline check runs in that frame before the call, so an effect the call makes at once is met as a rise. A check-once wait with a call waits for the next frame, calls, then checks once.
    - **`options.edge: true` meets an `exists`, `property` or `expression` wait only on a rise** (GMCP-97): a check that finds the condition true after a check that found it false. A first check that already finds it true is not met, so a condition true for the whole wait times out with `met: false`; any other kind, and `timeoutMs: 0`, are refused.

      Without it a condition already true was met at frame 0 and started a `then` on the wrong event, and a `visibility_changed` signal wait is no substitute since it fires on hide too. The edge lives in the shared probe (`edge_probe`), so every check, including a draw's, counts toward it; `batch_drive`'s wait assertion takes no `edge`.

      A check whose expression fails to run is no fall, so an expression that errors for one frame mid scene swap does not make a rise the game never made; a missing node is a fall, since a node not there is not true. A screenshot wait checks an edge probe once at the request, so a rise before its first draw is seen.

    - `then` carries `timeScale` beside `call`, since with a call alone delve's slow motion needs a game method that sets `Engine.time_scale`, a game change for a drive. A `then.call` that fails fails the wait, naming the met frame, and leaves the time scale unset, as a failed `options.call` answers no frames.

      In the met frame `call` runs first, then `timeScale`, which scales the next frame on, since `Engine.time_scale` is read once at an iteration's start (4.7.2 `main/main.cpp` L4936). A timeout runs nothing; a check-once wait (`timeoutMs: 0`) runs `then` at once when met, paused or not. The result adds `then: {frame, call?: {value}, timeScale?}`, `frame` being `Engine.get_process_frames()` when it ran.

      `batch_drive`'s `wait` assertion takes no `then`, as it takes no `call`: a `wait_for` tool step carries it. Ruled out: a `then` on the assertion (assertions would run game code), a `then.set {node, property, value}` (a second way to set a property, with `set_property`'s conversion and read-back to carry into the met frame), and a failed `then.call` answering `met: true` with the time scale still set (an agent that skims `met` captures an effect that never started).
23. **Joining a game that is already running** (#48; user, 2026-09-29, each the recommended option). The bridge is an autoload that `override.cfg` names, read only when a game starts (decision 2), so a game started with no override has no bridge and nothing can join it. What can be joined is a game started while the override was there, so a folder is **armed** ahead of time.
    - **`arm_project` and `disarm_project` tools** arm a folder: the override and `armed.json` stay until the disarm or the server's exit. Ruled out: an option on `attach_project` that keeps the override after its wait (arming as a side effect of a call that may have timed out), a `godot-mcp.json` setting (the override present whenever the server runs, wanted or not), and a clearer refusal only.
    - **A game started on an armed folder is dormant**: its bridge dials nothing and registers no logger. It writes `dormant/<pid>.json` and checks twice a second for its own `join-<pid>.json`. So the error feed starts at the join. Ruled out: buffering errors from start (a logger in every armed game, joined or not).
    - **Which game:** `attach_project` joins the one dormant game when there is one, takes `options.pid` to choose among several, and refuses with the list when several wait and no pid is given. `list_sessions` lists the dormant games under `armed`. Ruled out: the first bridge to see a shared file (delve's server and clients share a folder, so the agent could not choose), and refusing whenever more than one waits.
    - **Arguments:** `attach_project` became `(projectPath, waitSeconds, options {quiet, shutOutRealGamepads, session, pid})`, `run_project`'s shape, since the five-parameter limit left no room for `pid`. The old top-level arguments were removed. Ruled out: moving only `session`, and a separate `join_project` tool.
    - **After a detach**, a joined game on a still-armed folder goes dormant again and can be joined again; a window a quiet join parked comes back on screen. Ruled out: leaving it idle for good.

27. **State digest** (GMCP-17; each the recommended option but the last; the design and the spike are archived in [plans/archive/state-digest.md](./plans/archive/state-digest.md)).
    - **A node opts in by joining the `mcp_state` group** and defining `_mcp_state()` (GDScript) or `_McpState()` (C#: any accessibility, no parameters, any return type, found by reflection in the helper and written by `ValueWriter`).

      Ruled out: an attribute on fields and members (marks scattered over many classes and a second attribute file) and a Godot-visible `_McpState` returning a Godot Dictionary (no records, the state delve would return), and finding nodes by the method alone (every read walks the tree and loads the helper even when nothing is marked).
    - **Godot sees a C# method by its signature, not its accessibility**: a `public`, `internal` or `private` method whose return and parameters marshal to Variant passes `has_method` and `call`, and one returning a record passes neither (measured on 4.7.2; `ScriptMethodsGenerator.cs` L128-135, `ExtensionMethods.cs` L302-334). The game repos' notes that only a public method is seen do not hold for a method Godot can marshal.
    - **No fallback**: a group member without a state method reads as an `error` entry, and a game with no marked node gets an empty list and a hint naming `snapshot_subtree` and `get_ui_elements`. Ruled out: falling back to script variables and `[Export]` members (layout knobs, not state) and a visibility tier (it duplicates `get_ui_elements` and `snapshot_subtree`).
    - **A new tool, `get_game_state`**. Ruled out: an option on `snapshot_subtree` (seeing the state takes a snapshot and a diff) or on `inspect_node` (one node a call, and a read-only tool running game code).
    - **`keep` stores the read in the session's snapshot store**, flattened to one value per leaf keyed by its dotted path, so `diff_snapshots` reports a changed hit point as one entry. Ruled out: comparing top-level keys whole, and no diffing (two full results in context).
    - **`get_game_state` and `diff_snapshots` are destructive with a `read` class override**, since state methods are game code and a live re-read runs them. Ruled out: `ReadOnly` (a client that auto-approves reads runs game code unasked) and no override (the read-only agents never get the tool).
    - **One frame**: the bridge's `state` handler reads the GDScript nodes and calls the helper inline for the C# ones. Ruled out: two requests merged by the server (halves read frames apart, so a kept read diffs noise) and the helper reading every node (two walks and two value writers kept alike).

      Measured in the spike (4.7.2): the handler called the helper's Callable synchronously with `Engine.get_process_frames()` unchanged, a state method calling Godot from inside it with no re-entrancy failure. The helper's reply passes through the bridge as a string, since GDScript's JSON parser reads every number as a float (`core/io/json.cpp` L390-396).
    - **Size bounds.** `maxNodes` (1 to 500, default 50) counts marked nodes in tree order before anything is read, and `maxDepth` (1 to 8, default 4) cuts nested values; each node's value walk stops at 5000 values, in GDScript and C# alike. A node's state over 4000 characters of JSON comes back as `{valuePreview, valueLength}`, and past 40000 characters of `nodes` the later nodes move to `omitted {count, paths}` (the first 20 paths).

      Why: a returned record writes its whole graph (delve's `GameState` holds the floor's rooms beside the party), so the skill tells games to return the few values an agent checks and the context to judge them, not a model object whole.
    - **A node's own failure is its entry's `error`, and the read goes on**: a method that raises (a GDScript error from the feed, a C# exception's type and message) or returns a coroutine or a `Task`, which is never awaited, since a digest is one frame's read. The bridge's own nodes are never read, even in the group.
    - **The C# half's fallbacks.** Every marked C# node goes to the helper; one whose type has no `_McpState` answers `missing` and is read through a Godot-visible `_mcp_state` in the same frame. A project with C# the helper cannot serve sends `csharpError`, which each C# node without a Godot-visible `_mcp_state` reads as its error, while the GDScript nodes still read. A C# node with both names is read by `_McpState`, with a `warning` that its `_mcp_state` was not read.
    - **Values differ by language**: a GDScript Node value reads as its path string (the JSON module's rule), a C# one as `{"$node": path}` (the helper's `GodotFormatter`), as `inspect_node` and `cs_get` differ.
    - **Kept reads share the snapshot store** with `snapshot_subtree`: its 16 entries and its id sequence. A state that is not a non-empty Dictionary or Array is the one leaf `$`, an errored node the one leaf `error`, and lists flatten by index, so a game that wants stable diffs keys its state by id. A kept read stores a cut state's preview, so its diff compares previews. Diffing a state read against a subtree snapshot is refused, naming both kinds.
    - **Waiting on a state key is in the first version**: a `wait_for {node, state, equals}` condition and the matching `batch_drive` assertion, chosen over leaving C# games to poll with repeated reads.
    - **The state wait's rules (GMCP-143)**: `state` is a key path in exactly `get_game_state keys`' grammar (`a.b[0].c`; a key holding a dot or bracket is unsupported, as for `keys`), and `$` names the whole state, checked before the path is parsed, so a state member literally named `$` cannot be reached.

      The value is compared as the `property` kind compares (numbers within 1e-6; `equals: null` refused). The node must be in the `mcp_state` group: a node outside it, or one whose state cannot be read (no method, a raising method, a coroutine, a C# helper that cannot run), ends the wait with an error, while a missing node is not met as for `property`.
    - **A key path the state lacks is not met, with `last` null**, since a state changes shape as the game moves. Ruled out: failing the wait on a missing key.
    - **The state is written with the read's own writer, then the key is picked**, so a wait sees what `get_game_state keys` returns: maxDepth 4 and 5000 values, and a key deeper than the cut reads the cut marker and compares unequal. A key path index of more than 10 digits is not found. C# ints above 2^53 lose precision through `JSON.parse_string` and are not fixed. The state method runs at every check, as it does at every read.
    - **`options.edge`, `options.call` and `timeoutMs: 0` (even while paused) are allowed**, as for `property`; `capture_frames`' `options.start` refuses the kind. The C# helper's cold load is covered by the default timeout, with no special case.
    - **`batch_drive` gets a `state` assertion** `{assert: "state", node, state, equals, timeoutMs?}` with `timeoutMs` defaulting to 0 like `property`, and the generic `wait` assertion takes the state fields too; a failure reads as any wait assertion's, with `last` the value at the key.

    - **A scene's object pace may carry a `steps` map of single steps' paces**, keyed by a step's index or its name, so one slow step does not make every step wait for it (a 22.7 s step made all nine steps of a delve scene wait 30 s each). A call's `options.pace` overrides step paces too, and a key that names no single step makes the scene red before it plays. Ruled out: one pace per scene (every step waits for the slowest).
    - **A step is also red on an output line in its window matching `scratch.patterns`**, by default Godot's own error lines and the leak line. Ruled out: the error feed and exit code only (a `GD.PrintErr` failure from a timer passes) and porting each game's text rule (the games disagree on case and skips).
    - **A fresh headless game per scene.** Ruled out: one game per folder reused with `change_scene_to_file` (autoloads, statics and the command line stay the first scene's, and leaks are one total).
    - **The boot is judged by the error feed alone**: an error logged between the launch and the first step (an engine error, `push_error`, a C# exception in `_Ready`) makes the scene red at `failedAt` index -1 named `boot`, with no step played and no `details`; `known` does not excuse it and it is never replayed alone.

      Warnings at the boot pass, and the lines printed before the first step stay unjudged, `scratch.patterns` included. Ruled out: ignoring the boot (a scene whose `_Ready` threw passed) and matching its lines against the patterns (an error-looking line a scene prints while it starts is not a failure).
    - **A folder run starts its slowest-paced scenes first** (by the largest pace a scene holds, its own or a step's), equal paces in name order; a listed run starts in its own order, and the result keeps the order given either way. Ruled out: name order for a folder run (a slow scene started last ends the run alone).
    - **`options.keepGoing` (default false, no profile key) plays on after a step red on a pushed error or a matching line**, so independent failures all show; a step whose own call failed (the game gone or stuck) still stops the scene, and the wait after the last step and the exit are then judged.

      Without it a scene stops at its first failed step, since scratch steps are usually stateful and sequential. The result lists every failed step in `failures`. Ruled out: always continuing (a step after a failed one runs on broken state) and a profile key (the choice is per call).
    - **The wait after the last played step lasts the longer of its pace in game time and in wall time**, so a scaled-up run's exit leak check gets the wall time a 1x run gives it and no time scale waits less than before; the scene's ceiling and the status file's remaining time count it the same way. No fixed floor and no option: a scene that needs longer sets its last step's pace.
    - **A scene's ceiling can be given, and replaces the derived one** (`options.ceilings`, the profile's `scratch.ceilings`, each `{<scene>: seconds}` above 0 and at most 3600, counted from the scene's first step on the same load-adjusted clock as the derived one, and not scaled by `timeScale`): lower or higher than the paces' sum, with no cap by it, and the call's value wins over the profile's for the same scene.

      A key naming a scene outside the run is refused in the options and ignored in the profile; the kill reason names the source. Ruled out: a ceiling that can only raise the derived one or is capped by it (a scene that is known to hang wants a tight one) and a profile that wins (the call is the nearer, narrower choice).
    - **`details` lists every played step by its status line, and only a failing step carries its detail** (`error`, `errors`, `lines`), with `[scratch]` notes kept only for it; `options.details` adds the green steps' detail.

      A step's errors fold by message, file and line with a `count`, as `get_errors` does, and each step's detail is cut to a character budget (1500 without `options.details`, 4000 with), dropping lines, then errors from the end, and ending with a `cut` note; messages and copies of the error are cut at fixed lengths, and nothing caps the whole result. Ruled out: a cap on the whole result.
    - **`options.steps` plays only the steps it names, once each in ascending order**, so one step of a long scene can be rerun without the rest. A token is a number (an index) or a string read as a plain index, then an exact step name, then an inclusive ASCII-digit range `"2-5"` (`03` and `+3` are names, a name wins over a range).

      Malformed input (an empty array, a bad type, a negative or non-integer number, a reversed range, a duplicate) is refused before launch; a token matching no step, a range past the end or a shared name makes that scene red at index -1, since names are known only after launch, and the other scenes still play.

      A scene played in part reports `selected`, and a `known` scene whose played steps are all green stays `known` and passes: `known-now-green` needs every step played, since a partial run cannot show that the whole scene is fixed. Ruled out: running the unnamed steps anyway and skipping a step's dependents for the caller (whether a step needs an earlier one is the caller's call).
    - **A scene's setup is declared in the profile (`scratch.setup {<Scene>: [step, ...]}`), not inferred and not a protocol method**: a partial run plays those steps beside the selected ones, ascending, and reports the unselected ones as `setup`, leaving `selected` the call's own choice (a `known` scene's "played in part" rule reads `selected` alone).

      This amends the ruling above: a later step that depends on a skipped one is still the caller's choice for steps not declared as setup. A setup step is judged like any other (`keepGoing` applies), a key naming no step or a shared name makes the scene red before a step plays, and a malformed value is refused at load. Ruled out: inferring dependencies and a scratch protocol method that names a step's prerequisites.
    - **`run_scratches` reports its `prep` as `run_project` does**, the same block, `build` and `import` `skipped` with `prepare: never`.
    - **A step ends on a per-step `until` when its scene gives one** (GMCP-181; the design is [plans/scratch-runs.md](./plans/archive/scratch-runs.md) part A). An optional public `GetStepUntil(i)` on the root returns a `wait_for` condition (an empty dictionary or null for a paced step), and the runner plays that step inside one `wait_for` on it with `PlayStep(i)` as the wait's `options.call`, so the wait's clock and `PlayStep` share a frame.

      The pace is the most game time the step may take: the bridge ends the wait unmet at that game time (`limitGameMs`, sent by the runner alone), and a real-time backstop of the pace + 10 s ends it if the game's clock stands still. A step not met in time, or whose until is refused, is red and stops the scene even under `keepGoing`, since the next `PlayStep` would start on a step still running.

      Ruled out: a boolean `IsStepRunning()` polled every 50 ms (a second clock a frame apart from the step, and no condition on the game's state), a step-end log line (it would share the runner's marker form and judge a step by its log, which this decision rules out above), and a real-time limit alone (it counts load, not the game's time, as a pace does).
    - **A scratch run can play in the background** (GMCP-200; the design and the rulings of its invariant pass are [plans/scratch-runs.md](./plans/archive/scratch-runs.md) part B). `run_scratches` with `options.background` returns `{runId, statusFile, logFile, scenes}` at once and the run plays on in the server under its own token, never the call's; `scratch_status` reads it or, with `stop`, ends it.

      One background run is live per project per server, and while it is, every `run_scratches` on the project is refused, background or not.

      The first end reason recorded wins (`stopped`, `interrupted`, `done` or `failed`), and the final write puts the status file first, then the log's completion line, then marks the run finished, so a reader sees the line after the file, unless every status write in its one-second budget failed, when the line is still written.

      The files are `<project>/.godot/godot-mcp/scratch-<runId>.json` (rewritten whole as a temp file moved into place) and `.log`, which a harness waits on with `^godot-mcp scratch run \S+ finished:`; an event write a reader blocks is skipped and reported, and no write fails a scene.

      A tool called without `session` never resolves to a session a live background run holds, so a drive aimed at the default game never lands on a scratch scene; an explicit name still finds it. The server's exit interrupts the runs before its games stop, waited for only within the existing shutdown cap; a server killed outright leaves `running` in the file with its `serverPid`, and another server's run can be read but not stopped.

      Ruled out: holding the call open (a client's tool timeout ends a run of many minutes), a second concurrent run per project (the scene sessions' names and the files would collide), a fresh shutdown deadline for the runs, and a run that survives the server (its games would be orphaned).

    - **One `watch` tool with `start`, `stop` and `run`**, one watch per session, `stop` taking no id; `run` replaces `monitor_property`, which is removed once `run` lands. Ruled out: a blocking call only (nothing can drive the game during the window, delve's case), separate start and stop tools beside `monitor_property`, and keeping `monitor_property` or a forwarding form (two tools for one job).
    - **Every other tool runs beside a watch**, `frame_control`'s steps included; only a second watch is refused. Ruled out: `monitor_property`'s guard (a stepped sequence could not be watched).
    - **Tracks are properties, expressions, signals, monitors and audio** (voices and buses, GMCP-46, below).     - **Audio is two track kinds of the watch** (GMCP-46; each the recommended option, the first and third ruled by the owner; the design and its spike are archived in [plans/archive/audio-observation.md](./plans/archive/audio-observation.md)): `tracks.audio {players?: {under?}, buses?: [names] | ["*"], thresholdDb?}`, at least one of `players` and `buses`.

      Why: "did the hit sound fire when I clicked" is an event in a window, which a read between calls misses for any sound shorter than the gap between them.

      Ruled out: a `get_audio` read tool, alone or beside the tracks (it misses a sound that starts and ends between calls, delve's blow, heal and downing, and cannot line a sound up with its cause), and recipes with property and expression tracks (`playing` reads a pause as a stop and a polyphonic restart as nothing, a fire-and-forget player cannot be named ahead, and no voice says its stream).

    - **Voices are read in paused frames, levels are not**, as a signal emitted in a paused frame is recorded and property tracks are not sampled; so `frame_control pause` shows as `pause` and `resume` events, never an `end`. Ruled out: both read (a `heard` range would span frames listed as paused) and neither (a pause menu's click on a `PROCESS_MODE_ALWAYS` player is never seen).
    - **The watch never changes the mute, a bus or a player.** The bridge's own Master mute is reported as `bridgeMuted`, and a watch reading Master (by name or `"*"`) warns when it was on at a sampled frame, naming the child buses, whose peaks survive it. Ruled out: lifting the mute for the watch (a run the user asked to keep silent plays out loud) and refusing Master. A warning also says when a sampled frame ran at a `time_scale` other than 1, since audio does not follow it.
    - **Budgets**: at most 200 players (the rest counted in `playersSkipped`) and 300 voice events shared fairly across players, `voiceCounts` counting all; at most 50 `heard` ranges a bus (the first 25 and the last 25, the cut counted in `heardCut`).

      A peak is the last 512-frame mix step's (`audio_server.cpp` L614-660), so in a quiet run a sound shorter than about 81 ms never reaches a peak read: voices, not peaks, say whether a sound fired.

      A recording mixes `mix_rate / fps` frames each iteration (`movie_writer.cpp` L244), so its audio is locked to frames. A bus's peak is taken with its own volume and mute before its send adds it to Master (`audio_server.cpp` L598-670).

34. **A game the server launched ends with the server** (GMCP-86). At the server's exit each launched game is pinged and sent `shutdown`, all sharing one load-adjusted grace (3 s, 30 s while recording), so its exit work runs; the games' part of the exit is capped at 10 s of wall time, and a game still running then is killed at once with its process tree, the kill waiting up to 5 s for each killed game's run process and own process to be gone.

A pass spends its one 10 s cap first waiting until no launch or restart is in flight, so one under way finishes or is refused before its game is asked to quit, and then on the games' grace.

      A session still starting when the cap runs out is handed back to a later pass (process exit or `Dispose`, which leaves it undisposed) and its game is killed if it has one; the kill acts only on sessions the pass took or that are still starting, so a restart's healthy old game that settled in time is not killed.
    - The cap does not cover the whole exit: the kill step adds up to 5 s, headless hosts stop all at once after the games (about 3 s plus up to 5 s waiting on a kill) and their release takes up to `ReleaseLimit` (about 20 s), so one `Shutdown` is about 43 s at worst and a few seconds typically; these figures are derived from the constants, not measured. One session's failed stop is written to stderr and the others go on.
    - A game the server launched (`SOURCE_ENV`) quits one frame after its connection to the server drops, through its own `get_tree().quit()`, which covers a server killed outright or crashed, but only if the server welcomed it: after the handshake of every launch, restart, preview and scratch run the server sends the bridge `welcome`, which marks the connection accepted. An attached or joined game never quits on a lost connection, since it is the user's.
    - A child Godot that inherited `GODOT_MCP_PORT` and `GODOT_MCP_TOKEN` (`OS.create_instance`, a self-restart) is refused at its hello, is never welcomed and runs on; without the welcome it would have quit with a connection it never had. Accepted cost: a server that dies before the welcome round trip completes leaves its game running. The welcome is sent once the game's process id is known.

      A welcome that times out after 2 s is logged ("did not answer welcome within 2 s; it will mark the connection when it reads it": the frame was delivered, so the game still quits on loss once it reads it); one that fails with the frame not delivered is logged as "the game will not quit by itself if this server dies". Either way the launch goes on.
    - `install` keeps `Stop-Process -Force` on the running servers, because a server's stdin belongs to the MCP client and install cannot ask it to exit; the games those servers launched quit by themselves.
    - Ruled out: relying on the `OwnWork` job to end the games (it sets no limits and kills nothing when it closes, `OwnWork.cs` L8-13).
    - Engine fact (4.7.2): `get_tree().quit()` runs every node's `_exit_tree` and sends `NOTIFICATION_EXIT_TREE`, and sends no close request.

      `SceneTree::quit` only sets `_quit` (`scene/main/scene_tree.cpp` L886-891); `OS_Windows::run` leaves its loop when `Main::iteration()` returns true (`platform/windows/os_windows.cpp` L2353) and calls `main_loop->finalize()` (L2358); `SceneTree::finalize` calls `root->_set_tree(nullptr)` (`scene_tree.cpp` L855-862); `Node::_set_tree` calls `_propagate_exit_tree` (`scene/main/node.cpp` L3354-3361), which calls `_exit_tree` (L427) and sends `NOTIFICATION_EXIT_TREE` (L431).

36. **Drives across several processes** (GMCP-47; each the recommended option; the design and its spike are archived in [plans/archive/multi-process-drives.md](./plans/archive/multi-process-drives.md)). A networked game is driven as several sessions of one server: a host and a headless guest are two `run_project` sessions on one folder, beside a server that is not a Godot game.
    - **A second client is a session.** `run_project` with `engineArgs: ["--headless", "--resolution", "<the viewport size>"]` and its own `options.session` starts it, with its output captured and every runtime tool reaching it. Both sessions on the folder agree on `quiet` and `shutOutRealGamepads` (decision 10); a headless `run_project` stays bound by it, only `run_scratches` sessions are exempt.
    - **A headless client needs `--resolution`.** Its root window is 64 x 64 (the root's minimum size, `scene_tree.cpp` L2069), so under `expand` stretch the viewport lays out at 640 x 640 and with no stretch input is refused (measured). Under `canvas_items` or `keep` stretch, `click`, `drag`, `hover` and `get_ui_elements` match a windowed run. A guest that needs pictures is a quiet windowed run, since a headless one draws none (decision 33).
    - **Process sessions.** A program a project needs beside its games is declared in `godot-mcp.json`'s `processes` and started by name with `run_process(projectPath, process, args?, options {session, ready})`, a third session kind with no bridge (amending decision 11).

      Ruled out: a free-form command (a client that auto-allows the godot tools would run any program without the shell's prompt; the tracked profile is the allow-list) and the shell keeping companions (delve's four-second sleep, the port lock on `Delve.Server.dll`, output read from files by hand, and no way to wait on it or order it inside a batch).
    - **A process is ended with its job.** It starts in a job of its own with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so every descendant ends when the session stops or the server dies.

      Measured: a nested kill-on-close job ended `dotnet run`, its app and the app's child within 1.5 s, which also ends delve's leftover `Delve.Server` child. A start whose job cannot be created or joined is refused rather than falling back to a tree kill. The server's `OwnWork` job kills nothing, so it cannot do this.
    - **A process stops by termination, never gracefully**, and by name: `stop_project {projectPath}` never stops one, since a process holds no folder bookkeeping and no `override.cfg`. A server that saves on shutdown loses what it had not saved. A stopped process stays listed as a stopped run does.
    - **`ready` is a stdout or stderr line.** `ready.output` is a regex and `timeoutMs` runs 1 to 600000 (default 60000, load-adjusted); `options.ready` replaces the profile's whole. An exit before the line, and a timeout, refuse the start with the last output lines and stop the process. `restart_project` stops a process and starts its stored command (`args` included) and `ready` again; its `prepare` means nothing, since `dotnet run` builds itself and no prep runs.
    - **A run session writes its whole output to `run-<session>.log`** beside a process session's `process-<session>.log`, in `.godot/godot-mcp/`, reported as `log` by `run_project`, `restart_project` and `get_debug_output`.
        - GMCP-220, an orchestrator decision, not an owner ruling: the file is named `run-<session>.log`, truncated at a fresh launch and appended to on a restart, and every run session writes one, a `run_scratches` scene's included.
        - GMCP-220, an orchestrator decision, not an owner ruling: it closes when the run's output ends (and on cancel, by the time `stop_project` returns, and at dispose), so a stopped session never pins its project folder.
    - **A process session is reached by few tools.** `list_sessions`, `get_debug_output`, `stop_project`, `restart_project` and `wait_for {output}` reach it, a `batch_drive` tool step on it is refused at validation, and any other runtime tool is refused naming those.

      Its answers are its own shapes (`ProcessStopResult`, `ProcessRestartResult`), not widened run results. Stopping a process is not a batch step (a batch that kills its own server leaves later steps failing on the clients), so a swap to a lost server is four sequential calls around a watch.
    - **Output waits.** `wait_for {output: "<regex>", stream?, after?}` on a run or process session is answered by the server from the session's ring buffers, with no bridge request, so it works on a paused game. It sees lines that arrive after the call starts; `after`

      (a line number, a previous match's `lineNumber` included) looks back within the buffer. Ruled out: every held line (a wait for `joined` is met by the previous run's line) and lines since the session's last output wait (hidden state).
    - **An output wait's rules.** Scanning starts at `after + 1`; the buffers carry their numbering over a restart; a match gives `value: {line, stream, lineNumber, groups, at}` with `groups` the captures only; `stream: "any"` scans stdout first. A line is matched raw with a 1 s regex timeout that fails the wait naming the pattern.

      An attached session (no captured output), `options.call`, `options.then`, `options.edge`, `options.screenshot`, `timeoutMs: 0` without `after`, and `frame_control`'s `until` and `capture_frames`' `options.start` are refused.
    - **Parallel groups.** A `batch_drive` step may be `{parallel: [...]}`, 2 to 8 tool or assertion steps, each on its own session (one session twice is refused, statically and again on the resolved sessions), no nesting.

      Why: every step of a batch starts after the last answered, so an effect one game's input causes in another passes before a wait begins (measured: a guest wait sent after the host's click missed a one-frame label 30 of 30 times, one armed before it caught 40 of 40). Ruled out: a `background`/`join` pair (a forgotten join leaves a wait running into the next batch) and a multi-session `wait_for` (a group also films, reads and presses at once).
    - **A group starts its members in listed order**, a member only once the previous member's request is written to its socket (`PendingRequest.MarkWritten`), so arming a wait before acting is guaranteed rather than left to the thread pool. A setup request (the C# helper's first `ping`) releases nobody, a failure before sending or a server-side output wait releases the next, and a group's time counts once toward the batch's 300 s and its members toward the 100 steps.
    - **A failed member cancels the rest** through the bridge's `cancel` (ruled out: letting them run, which leaves a wait up to 120 s). A cancelled member is `{index, tool|assert, session, ok: false, cancelled: true, sent, startMs, endMs}`; `sent` says whether its request reached the game, since a gesture once sent plays to its end.

      A member that finished before the failure keeps its outcome, the first failure by completion order is `failedAt.member`, and a cancelled `frame_control` leaves its game paused. `fired` and `no_errors` are refused in a group.
    - **`{uiChanged: "now"}`** takes the UI baseline when the wait's probe is built, replacing a gesture's pending one, so a wait member in a group sees a change another session's input causes. `{uiChanged: true}` keeps its meaning and refusal, whose text points at the new form. Ruled out: an `options.uiBaselineIn` on every input tool (a press in one session reaching into another).
    - **Errors elsewhere.** A batch marks the feeds of every session it names, and each step's entry gains `errorsElsewhere: {"<session>": [errors]}` for the other sessions' errors while it ran (collapsed and capped at 20 a session as `ErrorReport` does, the rest counted in `errorsElsewhereOmitted`).

      `no_errors` takes `sessions: "all"` or a list of distinct names (refused beside `session`, and on any other step). A tool called outside a batch is unchanged, since the batch says which sessions belong together.
    - **The error cursor.** "While that step ran" is a contiguous cursor per session, kept apart from the `no_errors` marks, so an error shows on at most one entry. A group's entry carries the errors of sessions no member addresses and, for each member's session, those outside that member's own call; its members carry none.

      One gap remains: an error in the next step's own session landing between one step's cursor read and the next step's call mark is shown nowhere (GMCP-211). Process sessions have no feed, so they are never in `errorsElsewhere`, `"all"` skips them and naming one is refused.
    - **The drive clock** is the server's process-wide `Stopwatch` in milliseconds to 0.1 ms. `batch_drive` entries carry `startMs` and `endMs` and the result `startedAt`, exact; a met `wait_for` carries `metAt`, the drive time of the frame whose check met, with `clockErrorMs`; an output wait's `value.at` is the server's receipt time of the line.

      So the gap between a host click and the guest's reaction is `metAt - startMs`, two numbers of one result. Ruled out: the system clock (millisecond fields through `GetSystemTime`, adjustable mid-drive) and batch stamps only (a game's moment bracketed by its wait step's end).
    - **A clock offset is a constant for a game's life on Windows.** `get_ticks_usec` is QPC minus the value at the OS object's construction (`os_windows.cpp` L292-293, L986-1012), the server's `Stopwatch` reads the same counter, and QPC is consistent across processes.

      So a session's offset is estimated, not tracked: the bridge's hello and every pong carry `ticksUsec`, each ping gives bounds `[S - t, R - t]` from the send and receipt times, and the session keeps the tightest, the offset being their midpoint and `clockErrorMs` their half-width. Measured: no drift over a minute in 9 runs (within 8 us). On Linux the monotonic clock .NET reads is slewed and the bridge's is not, so a long drive drifts there (unmeasured).
    - **The bounds come from unevenly spaced pings.** The bridge answers a ping in `_process`, adding up to a frame to its round trip (under 0.5 ms otherwise), and pings that each wait for the last reply, or follow a multiple of the frame time, lock to the frame and bound the offset only to 6-9 ms.

      After the handshake the server sends five pings 7 ms apart, each written without awaiting the last, and `run_project` and `attach_project` await all five (about 40 ms): measured 1.4-1.9 ms (median), enough to order a network hop (3-15 ms on loopback) but not two events in one frame. A failed ping does not fail the launch.
    - **A wider clock gets one extra ping.** Before converting a watch result or a met wait, a session whose bounds are wider than 2 ms (or missing) sends one more ping on the raw path and awaits it; a timeout, a closed connection or a cancellation leaves the bounds, and a cancellation never turns a met wait into a cancelled one. It adds a sample and no promise of a width, since one ping can lock to the frame. A late ping is valid for earlier stamps because the offset is constant.
    - **Random-gap pings are GMCP-213.** Random gaps over a minute narrowed the bounds to 0.2-0.3 ms in the spike, but they need a loop with a lifetime of its own and are their own item. A disagreeing pong (a reordered reply, a clock that jumped) replaces the bounds, a hello can only tighten the upper bound (it carries no send time) and is ignored if it cannot sit above a pong's lower bound, and a bridge too old to send `ticksUsec` leaves the bounds to its pongs.
    - **A stamp that cannot be converted** (no pong yet) is reported without `metAt`, or with `at` null in the watch, never guessed. `clockErrorMs` sits on a result whose stamp was converted, never beside an output wait's `at` and never on a timed-out or cancelled wait. The bridge's `ticksUsec` is stripped from every reply the server forwards, so a raw tick never reaches the client. A clock ping is the connection's raw send, so it never releases the next parallel member early.
    - **The watch's `at`.** Decision 29's items end with `at`, last so no index moves. A point or voice carries the frame-start tick that `advance` already reads, shared by every track in the frame; a signal event fires mid-frame and reads its own tick when kept. `at` is rounded to 0.1 ms and converted before `WatchTimeline.Shape`, so the 40000-character budget counts the real length. `clockErrorMs` is read from one set of bounds before the walk.
    - **Pause and recording.** The watch samples unpaused frames only, so a gap in `at` includes paused wall time that `gameMs` does not. A recorded session's `at` and `metAt` are drive time with its `clipMs` still clip time, and a group may mix a recorded and a plain session.
    - **No lockstep pause across sessions**: a tree held paused across calls drops a networked game's socket (delve's DEVELOPMENT.md L79), and a .NET server cannot be paused; a paused host still answers a group's members on other sessions. Ruled out: lockstep frame control and a network conditioner (survey idea 18: delve's client speaks WebSocket to a .NET server outside Godot's multiplayer API).

A world node's `input_event` comes from physics picking in the next physics tick (`scene/main/scene_tree.cpp` L652, `viewport.cpp` L780), which fell after the two settle frames 5 of 5 times at 20 Hz physics and 6 of 6 uncapped at 60 Hz (measured).

38. **Step until a condition, with input riding the stepped frames** (GMCP-20 and GMCP-44; each the recommended option; the design is archived in [plans/archive/step-until-render.md](./plans/archive/step-until-render.md)). `frame_control` step takes `options.until` and `options.input`, beside `wait_for`'s `options.then` (decision 22); no new tool.

    Ruled out: a `step_until` tool (three tools on one clock with overlapping options and refusals, and one more name in every agent file), documentation of `batch_drive` recipes (a batch stops at its first failed assertion and takes at most 100 steps, so "step until" is not expressible), and a loop in `batch_drive` (each step is a request at least a frame after the last, so it cannot stop on the met frame).

      The check runs after each stepped frame, never before the first, so a step runs at least one frame: with the process unit at each counted frame's `frame_post_draw`, so it sees what that frame drew and `options.screenshot` captures the met frame; with the physics unit at the `physics_frame` after each counted tick.

      Never met, the step runs `count` frames, stays paused and answers `met: false` with `last`, a result rather than an error. Ruled out: pausing where `wait_for` checks (`process_frame`), which leaves a frame whose physics ran and whose process did not.
    - **Pausing on a condition lives in both tools** (the owner ruled (b)): the step's `until` and `wait_for`'s `then.pause` (decision 22), checked half a frame apart. `wait_for` refuses a paused game, so the paused case needs the step, and a wait on a running game can run past a step's 1000 frames.
    - **Riding input is sent at the stepped frame's `process_frame`.** `options.input` holds up to 100 of `simulate_input`'s raw events, each with `frame`, the 0-based stepped frame it arrives in (default 0), sent through the input module's `dispatch` before that frame's nodes process, with the process unit only. The tree is unpaused there, so `_input`, `_unhandled_input` and `gui_input` reach pausable nodes at once and `is_action_just_pressed` holds in that frame's `_process`.

      Engine facts (4.7.2): a pausable node gets no input callback while paused (`scene/main/scene_tree.cpp` L1430, L1471; `viewport.cpp` L2002, L2179), and a press stamps `pressed_process_frame` with the current process frame and `pressed_physics_frame` with the next tick (`core/input/input.cpp` L1033-1037, L438-442). So input sent while paused, then stepped, is never just-pressed; the step's itest keeps that as its control case.

      Ruled out: sending at the previous frame's `frame_post_draw`, where the step unpauses (the process edge is stamped with the frame just drawn and lost, and `_input` runs a frame early); no riding input (a game that reacts to a just-pressed edge or an input callback cannot be driven frame by frame); gestures inside a step (a gesture plays over frames of its own); and `options.call` on a step (`call_method` while paused, then the step, gives the same frames).
    - **What riding input does.** An event with `pressed` left out is a press at `frame` and a release at `frame + 1`, which must fall inside the step. It plays under the session's input gate, marks a gesture playing so a watched run's real mouse is swallowed, goes into a running `capture_input`, and takes the `uiChanged` baseline when none is pending, so `until: {uiChanged: true}` with a riding key steps until that key's effect shows.

      An early `until` leaves later events unsent: the result adds `inputNotSent` (a press and release counting two) and `held {keys, mouseButtons, padButtons, actions}`, and a failed step that leaves something held ends its error with `; held: <JSON>`. A wait entry and a `click_element` are refused, as is the physics unit.
    - **No report on the met frame**: the game left paused serves every read tool, `then.call` returns what a game method gives, and a watch around the step records the stepped frames up to the met one. Ruled out: a `report` list of expressions (a second list beside the watch's tracks, with its own budget and errors) and `report: "state"` (every C# game pays the helper's load on the first report).
    - **Annotations unchanged**: `frame_control` and `wait_for` already run game code through expressions and `options.call`, so `until` and riding input need no agent sweep.
39. **A drive turns the per-frame hover re-pick off; the bridge does not re-pick only when the game asks** (GMCP-65; an orchestrator decision, not an owner ruling). `run_project` takes `options.repickHover` (default true); false stops the bridge re-picking the hover at the injected pointer each frame.

    Why: 4.7.2 gives a script no hook for the game's own re-pick. `Window::update_mouse_cursor_state` (`scene/main/window.cpp` L935-950) emits no signal and calls no script virtual, `Viewport::update_mouse_cursor_state` is bound as a plain method (`viewport.cpp` L5223), and `window_input` filters internal events (`window.cpp` L2019-2026), so the bridge cannot tell when to re-pick. The agent who needs the game's own re-picks to decide the hover says so with `repickHover: false`.

    With it false the bridge still re-picks once at the injected pointer after a scene change (`SceneTree.scene_changed`, emitted after the engine's own re-pick, `scene_tree.cpp` L1691-1695) and once at the end of a GUI drag (`NOTIFICATION_DRAG_END`, which `Viewport::gui_perform_drop_at` sends to every node before its re-pick, `viewport.cpp` L2457-2459), while it owns the pointer: those engine re-picks also read the OS cursor, and no game call decides them.

    Ruled out: a `warp_mouse` route, whose effect on a quiet run's hidden desktop is unmeasured.

40. **What the server parses comes from files MSBuild writes itself, never from a prep wrapper's captured output, except as a fallback** (GMCP-276; an orchestrator decision, not an owner ruling). The Compile-items listing reads the item list from MSBuild's `-getResultOutputFile` JSON, and the build's diagnostics come from MSBuild's quiet file logger (`build.diagnostics.log`), so a prepWrapper may prefix or rewrite its log freely.
    - **The switches use MSBuild's slash form on the command line** (`/flp:`, `/getItem:`, `/getResultOutputFile:`): a PowerShell prepWrapper (`pwsh -File`) splits a `-name:value` argument at the colon but keeps `/name:value` whole, and a gate that routes the build to another machine sees and rewrites the path after the colon, which it cannot do inside an `@` response file (it also does not send git-ignored files).
    - **Fallback to the captured log**: when MSBuild's file is missing (a routed build's diagnostics file stays on the builder) or a failed build's file logger holds no error (early errors such as MSB1009 reach only the console log), the server reads the captured `build.log` (for the listing, its log), keeping a prefixing wrapper's prefix. `build.log` and `build.diagnostics.log` are deleted before each build.
    - **The import is not covered**: its `ERROR:` check reads the wrapped import output, so an import error a prefixing wrapper rewrites is not detected.

41. **A game that acknowledged the quit and closed its bridge gets 7 s more before a kill** (GMCP-268; an orchestrator decision, not an owner ruling). Such a game is in the engine's own teardown, whose measured tail reached about 3 s, so a stop, a restart or a scratch scene's quit waits 7 s past the 3 s exit grace (10 s in all, load-adjusted) before killing it; a game whose connection is still open at 3 s is still killed at 3 s.
    - A recording run keeps its 30 s grace with no teardown phase, and the silent path and an attached stop without a process handle are unchanged.
    - The server's exit shares the same wait inside its 10 s cap, so its bound does not move.

## Wire

- **The server listens and the bridge dials in.** The server binds `127.0.0.1:0` and keeps the listener open, then passes the port and a session token to Godot through environment variables (`GODOT_MCP_PORT`, `GODOT_MCP_TOKEN`). This removes the reference server's free-port race and its regex-editing of the port into GDScript.
- **Frames** are a 4-byte length plus UTF-8 JSON.
- **Every request carries an id** and every reply echoes it. A reply for a timed-out id is dropped, not matched to the next request.
- **Handshake:** the bridge's hello carries the token and the project path; a mismatch is refused, which catches a stale bridge.

## Coexisting with a debugger (user, 2026-09-26 and 2026-09-27)

An agent debugs a game godot-mcp holds with DebugMCP and netcoredbg; the two servers stay separate, and godot-mcp wraps no debugger.

- `list_sessions` keeps `processId` (the wrapper `stop_project` kills) and adds `gameProcessId`, the hello's pid, the one a debugger attaches to.
- While a debugger is attached to the game (`CheckRemoteDebuggerPresent`), each runtime call pings first for 500 ms and fails at once when the game does not answer: it is most likely paused at a breakpoint. A game with no debugger attached is untouched.
- `stop_project` and `restart_project` go ahead while a debugger is attached, and warn that its debug session ended with the game.
- No hold-until-attached launch option (decided 2026-09-27, after the trial recorded in the `debug-live` skill): a run stops Godot at its 15 s handshake timeout, and netcoredbg cannot attach before the runtime starts. Startup code is debugged by launching Godot under netcoredbg while `attach_project` waits; the listener holds a hello read open for as long as any session waits for a bridge, since the bridge dials in `_ready`, says hello in its first `_process` and never redials.

## Gamepad input, from Godot 4.7.2's source

- **What works.** A parsed `InputEventJoypadButton` updates `is_joy_button_pressed` (`input.cpp:977-987`). A parsed `InputEventJoypadMotion` updates `get_joy_axis`, raw with no deadzone (`input.cpp:989-993`, `601-614`).

  Actions match through `InputMap::event_get_index`: pressed means `|value| >= deadzone` (default 0.2, `input_map.h:55`), and strength is `inverse_lerp(deadzone, 1, |v|)` (`input_event.cpp:1133-1171`). Joypad events are never merged by accumulated input, and `is_echo()` is always false.
- **Focus navigation.** The default `ui_left/right/up/down` have d-pad buttons plus the left stick at ±1.0 (`input_map.cpp:490-512`) and all devices (-1), so they react to injected events. A stick push moves focus only on the released-to-pressed change, so the next move needs a 0.0 release first (`viewport.cpp:2340-2380`, `input.cpp:1033-1034`). `ui_accept`, `ui_cancel` and `ui_focus_next` have no joypad binding by default; `ui_select` is Y.
- **Devices.** The first pad is device 0; ids 0-15 are joypads (`input_event.h:64-67`).
- **Not settable from script.** `get_connected_joypads`, `is_joy_known`, `get_joy_name`/guid/info and vibration are script-callable but filled only by the platform driver's `joy_connection_changed`, and only its signal is bound (`input.cpp:153`, `239`, `711`, `747`, `2291-2301`).

  An injected pad never shows as connected; the real pads do, in shut-out mode too, which is how the pad tools find a free id. Neither project calls those queries (checked 2026-09-25). A game that does would need an OS-level virtual pad.
- **Losing focus can clear pad state.** The setting is `input_devices/joypads/ignore_joypad_on_unfocused_application`, default false (`ProjectSettings.xml` L1671; defined at `input.cpp` L2374).
  - Pad state is cleared only in a project that sets it true, on `NOTIFICATION_APPLICATION_FOCUS_OUT` (`scene_tree.cpp` L934-947, `input.cpp` L1600-1623).
  - While it is true and the application is unfocused, the driver's real pad input is ignored (`input.cpp` L1652, L1684), but events injected through `parse_input_event` still get through.
  - Enum values were checked against `input_enums.h` L68-102.
- **Shutting real pads out is opt-in** (user, 2026-09-25). This machine has four pads connected, and in the gamepad tests they moved menu focus and pushed an action's strength mid-test.
  - The only script-reachable shut-out is to set the setting true and mark the game unfocused: pad state updates in `Input` before any script sees the event. A real focus-in turns the pads back on (`scene_tree.cpp` L934-947), so the bridge answers every application focus change with a focus-out and restores held injected pad state.

    The root Window's focus signals get no focus-out: an embedded popup taking focus fires them too (`viewport.cpp` L465-470), and a focus-out then would close the popup as it opens (`popup.cpp` L114-121). They only re-send held pad state when the OS takes focus from the window, since Windows clears pressed input then, after the focus-out was answered (`display_server_windows.cpp` L6948-6962).
  - The costs: the game sees application focus-out notifications, and delve mutes on them (`Main.cs:340-352`, when its mute-in-background option is on). Held injected keys release on a real focus change, and held pad buttons fire "just pressed" again.
  - So the default leaves real pads live (the setting written false). `shutOutRealGamepads: true` on `run_project`/`attach_project` turns the shut-out on, and the gamepad tests use it.
  - This reverses a same-day first decision of "shut out by default", made before these costs were measured.
  - **A game embedded in the editor's Game view keeps its real pads** (GMCP-61). Real pad input is dropped only while `Input`'s `application_focused` and `embedder_focused` are both false (`core/input/input.cpp` L383, `_should_ignore_joypad_events`), and the editor sets `embedder_focused` through the scene debugger (`scene/debugger/scene_debugger.cpp` L576). The bridge's re-sent application focus-out never clears it, so `shutOutRealGamepads: true` there leaves the real pads live.
  - **A window drag drops held injected pad input** (GMCP-61). `WM_ENTERSIZEMOVE` clears injected pad state with no focus event after it (`platform/windows/display_server_windows.cpp` L6750), so a window drag in a visible run drops held injected pad input.
- **Releases are sent explicitly** (`pressed=false`, or `axis_value=0.0`), and every event is a new object.

## The error feed, from Godot 4.7.2's source

- `Logger` extends `RefCounted` with `_log_error(function, file, line, code, rationale, editor_notify, error_type, script_backtraces)` and `_log_message(message, error)` (`core/core_bind.h` L125-138); `ErrorType` is ERROR 0, WARNING 1, SCRIPT 2, SHADER 3.

  `OS.add_logger` catches only what is logged after it; the logging tutorial registers in an autoload's `_init()`. Script loggers are removed at shutdown (`core/object/script_language.cpp` L335-339); the list has no lock, so `remove_logger` while threads log is unsafe and the bridge never calls it.
- `_log_error` runs on the thread that raised the error with no engine lock (`core/error/error_macros.cpp` L125-133, `core/os/os.cpp` L98-151); a per-thread guard sends an error raised inside it to stderr only (`error_macros.cpp` L49, L116-121). So it only appends under a `Mutex`, and the main thread sends.
- Engine `_MSG` errors put the condition in `code` and the message in `rationale`; `push_error`, `push_warning` and GDScript runtime errors put the text in `code` (`core/error/error_macros.h` L426-428, `core/io/logger.cpp` L67-72). `push_error`'s function/file/line are its C++ site (`core/variant/variant_utility.cpp` L1023, L1033; Godot issue #119628), so the script's location is backtrace frame 0.
- GDScript runtime errors reach loggers in debug builds only (`modules/gdscript/gdscript_vm.cpp` L3963-3993); backtraces are filled in debug and editor builds or with `debug/settings/gdscript/always_track_call_stacks` (default false, `gdscript.cpp` L2871-2875).

  Runtime `load()` parse errors arrive as `function="GDScript::reload"` (`gdscript.cpp` L824-853). Nothing arrives with `application/run/disable_stderr` on, or outside startup-to-shutdown (`main.cpp` L2363-2376, PR #117790). Loggers are additive: the console logger stays (`os.cpp` L829-835).

# Architecture

How the server and the bridge fit together today, for anyone about to change them. Symbols are named by file and member, not by line. Toolchain, tests and footguns are in [DEVELOPMENT.md](./DEVELOPMENT.md); terms are in the [glossary](./README.md#glossary).

## A request's path

1. A tool method checks its arguments (failures become `McpException`, whose message is all the client sees).
2. It resolves its session: the named one, else the only live session, else the only session there is; with none it throws "No Godot session is running…", and with several and no name it refuses and lists them. Then it calls `GodotSession.SendAsync(command, params, timeout, ct)` on that session.
3. `BridgeConnection` sends a frame (4-byte big-endian length, UTF-8 JSON) carrying a request id and waits for the reply with that id; a reply for a timed-out id is dropped. A timeout goes to the hang watchdog (`HangProbe`): a ping with 2 s to answer tells a busy game (the ping answers: the main thread is running) from a stuck one, and for a stuck one the tool's error adds the game process's CPU use over a 1 s sample, its thread count, its main (earliest-started) thread's state and wait reason, and a run's last 20 stderr lines. The process sampled is the game's own, from the hello's `pid`, not the `Godot_console.exe` wrapper the server started. A game a debugger holds at a breakpoint has every thread frozen, the bridge's too: when `DebuggerPresence` (`CheckRemoteDebuggerPresent` on the game's pid; never true off Windows) finds a debugger attached, `GodotSession.SendAsync` sends a 500 ms ping before each command and fails at once when it goes unanswered, and the watchdog reports such a game as paused under a debugger rather than stuck; with no debugger attached no extra ping is sent.
4. The bridge's `_handle_frame` looks `command` up in its handler table (`_command_handlers`, command → `Callable` taking `(id, params)`, built in `_ready`) and replies `{id, ok: true, …}` or `{id, ok: false, error}` (`_reply_error`).
5. The tool shapes the reply into its result: JSON text (`JsonSerializerDefaults.Web`), and for `take_screenshot` an image block read from the PNG file the bridge saved. Lists and logs are held to a budget (compact output): `get_ui_elements` pages by `offset`/`limit`, `get_debug_output` by `limit`/`before` with long lines cut, a `run_script` value over 20000 characters becomes `{valuePreview, valueLength}`.

**The error feed.** The bridge's `Logger` (`bridge/godot_mcp_logger.gd`, registered with `OS.add_logger` in the bridge's `_init`) receives every engine and script error and warning on whatever thread raised it, and only appends it, under a `Mutex`, to a queue capped at 200 (overflow is counted as `dropped`). On the main thread the bridge flushes the queue as an id-less errors frame, `{type: "errors", entries, dropped}`, every frame and before every reply, so an error raised while a command ran is on the wire before its reply. `BridgeConnection` hands errors frames to the session's `ErrorFeed` (the last 500 entries, each with a per-session `seq`). A runtime tool marks the feed before sending and attaches the errors (not warnings) after the mark to its result as `errors: [{seq, message, file, line, function, engine?, stack, count?}]`, shaped by `ErrorReport` (repeats collapsed with a count, at most 20 then `errorsOmitted`, messages cut at 2000 characters); the call still succeeds, except `run_script`, which fails when its script does not compile, or returns null with an error located in its own source (`gdscript://…`). An error whose location is not a script (`push_error`'s own C++ site, an engine `ERR_FAIL` such as `get_node` on a missing path, C# errors) is moved to the most recent backtrace frame, and the C++ site is kept as `engine: "<file>:<line>"`. A handler failure on an errors frame is logged and the frame dropped; the read loop carries on. Backtraces are filled in debug builds, or when the project sets `debug/settings/gdscript/always_track_call_stacks`. Launched and attached games report alike; stderr is kept only for `get_debug_output`.

## Session lifecycle

- **Names**: `run_project` (`options.session`, else its preset's `session`) and `attach_project` (`session`) name the new session, by default after the project folder. A name is 1-64 of letters, digits, `.`, `_`, `-`: a given name outside that is refused, and a folder name is fitted to it, each other character becoming `_` and the result cut to 64 (`My Game` → `My_Game`), so two folders that fit alike share a name and the second needs its own. Runs and attaches share one name space. A live name (running, attached, or still launching or waiting to attach) is refused; a stopped one is replaced. A stopped run stays listed so `get_debug_output` can read it; a detached session is forgotten.
- **One folder, several sessions**: the marked `override.cfg` is written by the first live session on a folder and removed when the last one ends (stop, detach, the game exiting, a failed start, server exit). A new session whose `shutOutRealGamepads` or `quiet` differs from the live ones' is refused (an attach counts as not quiet), and so is a second attach on a folder while one is still waiting.
- **Prep** (every launch, under the folder's prep lock from `SessionRegistry`, held through starting Godot, so launches on one folder never build or import at once): unless `options.prepare` is `"never"`, `ProjectPrep` builds the C# assembly when it is missing or older than its build inputs (the csproj is `[dotnet] project/assembly_name`'s, else the one `*.csproj` beside `project.godot`; inputs are `git ls-files -co --exclude-standard` from the git top level, filtered to C# build files; a `.godot/godot-mcp/build.stamp` touched after each green build keeps a non-compile change from rebuilding every run) with `dotnet build <csproj> -c Debug -p:GodotTargetPlatform=windows`, then runs `godot --headless --path <p> --import` when a versioned `*.import`'s `dest_files` target is missing or `*.uid` files exist with no `.godot/uid_cache.bin`, or a `.gd` declaring `class_name` is newer than `.godot/global_script_class_cache.cfg` (or that cache is missing while one exists: a game and a `--script` run read class names only from it, and the import's first scan rewrites it) (a second pass when the first logged `ERROR:`). A red build or a failed import refuses the launch with the parsed compiler errors or the log path; an import is refused while another session's game runs on the folder. A build is not: a running game reads its assembly and pdb into memory and holds no file open (`PluginLoadContext.cs` L59-69 in 4.7.2; measured 2026-09-26 with two games on one CsProbe copy, four rebuilds, each exit 0), and it keeps the code it loaded. Logs go to `.godot/godot-mcp/build.log` and `import.log`; each has a 300 s ceiling.
- **Profile** (`run_project`, before the launch): `ProjectProfile.Load` reads `godot-mcp.json` beside `project.godot` (absent: an empty profile), strictly: invalid JSON, an unknown or repeated key, a wrong-typed value, a `resolution` other than `WIDTHxHEIGHT`, a bad preset `session`, and an `options.preset` the file lacks are each refused with the path and the fix. `Merge` layers the top level, then `options.preset`'s preset, then `run_project`'s own arguments: `scene`, `resolution` and `quiet` are replaced by the later layer, `userArgs` and `engineArgs` append in that order, `resolution` becomes `--resolution WxH` before every engine argument, and the session is `options.session`, else the preset's `session`, else the folder's name. `quiet` stays true when nothing sets it. The merged request is what `LastLaunch` stores, so `restart_project` never re-reads the file.
- **Run** (`run_project` → `GodotSession.LaunchAsync`): after prep, `OverrideFile.Write` writes the marked `override.cfg` naming the bridge as an autoload (refusing a user's unmarked one), `GitExclude` hides it, and `StartRunAsync` creates a random token, starts Godot with `GODOT_MCP_PORT` and `GODOT_MCP_TOKEN` in its environment (plus `GODOT_MCP_QUIET` unless `options.quiet` is false, and `GODOT_MCP_SHUT_OUT_REAL_GAMEPADS` when asked). A quiet run also gets `--audio-driver Dummy` before the user's engine arguments (a later `--audio-driver` of theirs wins), and its override adds `[display]` `window/size/no_focus=true` with an off-screen initial position, so the window is created unfocused; on Windows a quiet run's Godot is started by `DesktopProcess` on the server's hidden desktop (`HiddenDesktop`), created suspended, watched through `Process.GetProcessById`, then resumed, with its output read from its own pipes (`IRunProcess` in `GodotRun.cs`; `StartInfoProcess` is the `Process.Start` path every other run takes). It then waits for the handshake.
- **Attach** (`attach_project` → `AttachAsync`): `AttachFile` writes the one-use `.godot/godot-mcp/attach.json` ({port, token, shutOutRealGamepads}), then the override under the folder's prep lock (so it never lands during a launch's prep or a headless run), and waits for a game launched after it to dial in; the attach file is deleted once the wait ends.
- **Handshake**: each session registers its expectation with `BridgeListener.AcceptBridgeAsync`. The listener's one accept loop reads each hello `{type: "hello", token, projectPath, pid}` (`pid` is the game's own process id, kept as `GodotSession.GameProcessId` and checked by nothing; a hello without it still connects) (sockets handled concurrently; a hello not arrived within 5 s refuses its socket, unless a session is still waiting for a bridge, when the read lasts until the last waiter ends, so a game paused at a startup breakpoint before its first frame keeps its connection), finds the waiter by a dictionary lookup on its token and checks the hello with `HandshakeExpectation` (the token, then the path). The lookup is not constant-time; the token is 32 random bytes on loopback only. An unknown token or a mismatch is logged and its socket closed; the waiter keeps waiting.
- **Recording** (`run_project` `options.record`): Godot's Movie Maker from launch. `GodotCommandLine.BuildArguments` adds `--write-movie <project>/.godot/godot-mcp/recordings/<UTC yyyyMMdd-HHmmss-fff>-<session>.avi --fixed-fps 60 --quit-after 36000` (a 10 minute cap) before the engine arguments, a new file each start; `--headless`, `--display-driver headless`, and a user's own `--fixed-fps`, `--write-movie` or `--quit-after` are refused. Movie Maker forces the Dummy audio driver and still records audio, and fixed fps makes game time advance 1/60 s a frame whatever the wall clock does (main.cpp L2829-2832, L5170-5172 in 4.7.2). `record_mark` asks the bridge's `movie_frame` for `Engine.get_process_frames()`, which equals the number of frames the writer has written (the counter rises once an iteration, just before `add_frame`); marks alternate start and stop. When the run ends (stop, the game quitting, a restart replacing it), `RecordingCut` waits up to 10 s for the game's own process, then cuts one clip per start-stop pair with ffmpeg (`FFMPEG_PATH`, else `PATH`; output-side `-ss`/`-to` half a frame early, `-c copy`, exact for MJPEG and PCM), 120 s a cut, log `recordings/ffmpeg.log`, and deletes the full file once every clip is cut. A killed game's movie has no duration and is kept uncut with an error; a missing ffmpeg or a failed cut keeps the full file and reports an error, never throws. The outcome is `stop_project`'s `recording`, `restart_project`'s `previousRecording`, and the stopped session's `recording` in `list_sessions`. If the server itself exits, a recording game is killed and its movie is not finalised.
- **Stop** (`stop_project`): a ping first; a game silent for 2 s is stuck and is killed at once with no `shutdown` command. One that answers (or whose connection is gone) gets a `shutdown` command and a kill after 3 s (30 s for a recording run, whose clean quit finalises its movie). Either way the override is removed if no other live session uses the folder.
- **Restart** (`restart_project` → `GodotSession.RestartAsync`, in `GodotSession.Restart.cs`): under the session's gate and with the session pending throughout (its name never frees), prep runs while the old game still runs, counting only other sessions' games for the import refusal; then the old run stops as a stop does but keeps the folder reserved and the override in place, and the stored `LaunchRequest` starts again under the prep lock. The new `GodotRun` takes over the old one's output buffers and gets a marker line; the error feed is the session's, so `seq` continues. An exit of a run the session has already replaced does nothing but log, so the old run's `Exited` handler cannot remove the new run's override. A failure after the stop releases the folder and leaves the session listed with its output. A cancelled call never stops the old game once prep is done. A `stop_project` that lands while a restart is waiting for the session's gate is followed by the restart's relaunch, since a stopped session can be restarted.
- **Detach** (`detach_project`): the connection closed, the override removed as for stop, the game left running. The attach file is not touched: each attach removes its own when its wait ends, so a detach never deletes another attach's file on the same folder.
- **Game exits on its own**: `OnRunExitedAsync` releases the override as for stop.
- **Snapshots**: `GodotSession.Snapshots` (`SnapshotStore`) holds `snapshot_subtree`'s captures, the 16 most recently used, ids never repeating in the session; it is emptied when the run stops, when a restart has ended the old run, when the current run exits, and when an attached game's connection ends (a watcher started at attach awaits `BridgeConnection.Closed`). A detach drops the session, and the store with it.
- **Captures**: `SessionRegistry.Captures` (`CaptureStore`) holds `capture_input`'s events by session name, not on the `GodotSession`, so a capture outlives its game: a stop, a restart, the game exiting or a detach marks a running capture `ended` (`stop`, `restart`, `exit`; a detach counts as `stop`) and keeps what reached the server, until the next `capture_input stop` naming that session takes it or a new start replaces it. It holds at most 2000 events.
- **Server exits**: `SessionRegistry.Shutdown` kills every run and removes every folder's files.

## The bridge

- **Start**: in `_init`, `_find_endpoint` reads the port and token from the environment, else from `res://.godot/godot-mcp/attach.json`; with one, the error-feed logger is registered there (and never removed: Godot drops script loggers at shutdown); with neither it warns and frees itself. With `GODOT_MCP_QUIET`, `_park_window` makes the window click-through and moves it off-screen: Windows clamps the override's off-screen initial position onto the primary screen at creation, so the window shows there, unfocused, until the bridge's `_ready`. The same branch sets `Engine.max_fps` to 60 when it reads 0 (the project set none): a quiet window keeps VSync, so it would otherwise draw at the monitor's refresh (239 fps measured) for frames nobody sees.
- **Commands** (`_command_handlers`): `ping`, `preview` (the `Preview` child, `godot_mcp_preview.gd`: when the viewport has a 3D world, no current `Camera3D` and visible `GeometryInstance3D` nodes under the current scene, adds a `PreviewCamera` framing their merged AABB from `(1, 0.8, 1).normalized()` at `radius / sin(fov / 2)`, waits two drawn frames, then saves the screenshot as `screenshot` does and adds `scene` and `cameraAdded`), `screenshot` (saves `.godot/godot-mcp/screenshots/<stamp>-<pid>.png` and a Lanczos preview when wider than asked; replies with paths, never bytes), `ui_elements`, `run_script` (compiles a script with `execute`, returns its value), `input` (gestures and raw events, under `_handle_input`), `shutdown`; `scene_tree`, `inspect_node`, `set_property`, `call_method` and `snapshot` (every node of a subtree with its shown or named properties and sorted groups, for `snapshot_subtree`; the diff is the server's `SnapshotDiff`) are forwarded to the `Inspect` module, which refuses the bridge's own nodes; `frame` and `wait_for` to the `Time` module; `compare_screenshot` to the `Baseline` module. The screenshot's capture and save are split (`_save_screenshot`, `_crop`) so a step can capture inside its own `frame_post_draw` handler; in low-processor mode a screenshot forces a draw rather than waiting for one.
- **Real input**: injected mouse events carry the injected mark, and `_input` swallows unmarked (real) mouse events while a gesture plays or an injected button is held, and with them the touch twins of real mouse events (those not raised while `_dispatch` runs). Keys are never swallowed, and injected keys carry no mark (their device stays 16, which the built-in `ui_*` actions require). A quiet run keeps real input out by never receiving it: unfocused from creation, click-through and off-screen. `godot_mcp_gamepad.gd`'s `shut_out_real_pads` keeps real pads out when asked.

## Tool annotations

Every tool declares `openWorldHint: false`. `readOnlyHint: true`: `get_debug_output`, `list_sessions`, `take_screenshot`, `compare_screenshot` and `preview_scene` (their PNGs go under the ignored `.godot/`), `get_ui_elements`, `get_errors`, `get_scene_tree`, `inspect_node`, `snapshot_subtree` and `diff_snapshots` (their store is server memory), `cs_members` (reflection runs no game code), and the headless `validate`, `get_scene_file_tree`, `get_node_properties` and `get_node_signals` (their prep writes only under `.godot/` and the build output). `destructiveHint: true`: `stop_project` (kills a process), `run_script`, `call_method`, `cs_get`, `cs_set`, `cs_call` and `run_csharp` (run arbitrary game code: a getter, setter or method runs), `batch_drive` (its steps may call them), `delete_nodes` (removes nodes from a scene file), `disconnect_signal`, `export_mesh_library` (can replace a file) and `batch_scene_operations` (its steps may do both). Every tool sets all three hints explicitly: a read-only tool is also `destructiveHint: false`, every tool not listed as read-only is `readOnlyHint: false`, and every tool not listed as destructive is `destructiveHint: false`. `McpServerSmokeTests` checks all three for every tool.

## Adding a runtime tool

1. A method in the right `RuntimeTools` partial with a last `session` parameter (five schema parameters at most): validate, resolve the session, then `SendAsync` on it.
2. A handler in the bridge, registered by its command name in `_command_handlers` (or a gesture under `_handle_input`).
3. A unit test for the server-side checks (`tests/GodotMcp.Tests/Tools/`).
4. An integration test against the InputProbe fixture (`tests/GodotMcp.IntegrationTests`), and the name in `McpServerSmokeTests`' list. A new test class goes into one group of `run.ps1`'s `$itestGroups`, keeping each group well under its 300 s ceiling (a full `itest` refuses to run while a class is in no group).
5. Its annotations (`ReadOnly`, `Destructive`, `OpenWorld = false`) and `McpServerSmokeTests`' annotation check.
6. This file's tool table and, for a new term, the glossary.

## Adding a headless scene edit tool

1. A method in a `HeadlessTools` partial (`HeadlessTools.Scene.cs`, `HeadlessTools.Properties.cs`, `HeadlessTools.Signals.cs`, `HeadlessTools.Mesh.cs`; five schema parameters at most): check the scene path (`CheckEditableScenePath`), build the op's parameters in an `internal static <Op>Parameters(…)` beside it (taking `projectDir` only when a check needs it, as a path check does) that checks every other argument (`CheckNodePath`, the new-file check, …) and that `batch_scene_operations` calls too, then `RunAsync` with the op name and its ceiling.
2. An `apply_<op>(root, params, context)` in the module that owns its kind of op, returning `{result}` or `{error}` without saving and reading the scene and build state from `context`, and its entry in `scene_ops.gd`'s `EDIT_MODULES` (and `READ_OPS` for a read); refuse before changing anything, so a list edit stays all-or-nothing.
3. Unit tests for the server-side checks (`HeadlessSceneValidationTests`), integration tests in `HeadlessSceneTests` on a copy of the probe project, and pure GDScript helpers in `tests/bridge/test_operations.gd`.
4. Its annotations and `McpServerSmokeTests`' list, then this file's tool table.

An op that never saves the open scene is listed in `READ_OPS`: the reads (`get_node_properties`, `get_node_signals`) and `export_mesh_library`, which writes a file of its own; given `context.pending_writes` (an Array), it appends the write there instead of saving, and `SceneMesh.write_pending` saves them later.

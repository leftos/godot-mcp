## Components

| Part | Where | Job |
|---|---|---|
| Host | `src/GodotMcp.Server/Program.cs` | The MCP SDK over stdio (stdout is the protocol; every log goes to stderr). Registers three singletons, `BridgeListener`, `SessionRegistry` and `CSharpBridge`, and calls `SessionRegistry.Shutdown` on application stop and process exit |
| Tools | `src/GodotMcp.Server/Tools/` | `[McpServerTool]` methods: `ProjectTools` (lifecycle, output, `list_sessions`) and the `RuntimeTools` partials (`RuntimeTools.cs` reads and scripts, `.Input.cs` mouse and keyboard, `.Gamepad.cs` pads, `.Inspect.cs` the running game's nodes, `.Time.cs` frame control and waits, `.Baseline.cs` screenshot baselines, with the baseline names, folder and sidecar in `ScreenshotBaseline.cs`; `save_screenshot` is in `RuntimeTools.cs`, its path rules and copy in `ScreenshotTarget.cs`), `PreviewTools` (`RuntimeTools.Preview.cs`, `preview_scene`) and `StressTools` (`RuntimeTools.Stress.cs`, `stress_input`); the headless tools are in the Headless row. They validate arguments, resolve their `session` through the registry, then call that `GodotSession` |
| Agent sweep | `src/GodotMcp.Server/Agents/` | the exe's commands besides the MCP server (`ServerCommands`, run when `args[0]` is `--list-tools` or `--sweep-agents`): `ToolClasses` gives each `[McpServerTool]` a class (`read` when `ReadOnly`, `edit-scene` for a `HeadlessTools` edit, `edit-live` when `Destructive`, `drive` otherwise, with eight overrides); `AgentSweep` rewrites the `tools:` line of each agent file marked `<!-- godot-mcp tool classes: … -->` (`AgentFile`) and commits the changed tracked files once per repository, keyed by git's top folder, through `GitRunner` |
| Session | `src/GodotMcp.Server/Session/` | `SessionRegistry` holds the named sessions and the rules between them (names, one folder shared by several sessions, the override's lifetime). A `GodotSession` is one of them: a run (`GodotRun`: process, stdout and stderr ring buffers of `GodotRun.OutputCapacity` lines, connection) or an attached game (`GodotSession.Attach.cs`), with its own input gate. `OverrideFile`, `AttachFile` and `GitExclude` own the files a session writes into a project; `GodotCommandLine` builds the launch. `ProjectPrep` (with `PrepScan` finding the csproj, the assembly, the build inputs and the missing imports, and `CompilerErrors` parsing a red build) makes a project runnable before a launch; `ToolProcess` runs one tool process (stdin closed, output to a log, the tree killed at its ceiling, its backstop or a stall; see [Load-adjusted time](#load-adjusted-time)); `GitRunner` runs git (stopped with its tree after 30 s of load-adjusted time, which counts as a git failure); `LoadClock` (with `SystemLoadSource`, `OwnWork` and `StallWatch`) measures every ceiling the server enforces |
| Headless | `src/GodotMcp.Server/Tools/HeadlessTools.cs`, `HeadlessTools.Scene.cs`, `HeadlessTools.Properties.cs`, `HeadlessTools.Signals.cs`, `HeadlessTools.Mesh.cs`, `HeadlessTools.Batch.cs`, `HeadlessTools.Describe.cs`, `src/GodotMcp.Server/Session/HeadlessRunner.cs`, `HeadlessHosts.cs`, `HeadlessHost.cs`, `ProjectFingerprint.cs`, `headless/operations.gd`, `headless/host.gd`, `headless/scene_edit.gd`, `headless/scene_ops.gd`, `headless/scene_nodes.gd`, `headless/scene_props.gd`, `headless/scene_values.gd`, `headless/scene_signals.gd`, `headless/scene_paths.gd`, `headless/scene_files.gd`, `headless/scene_mesh.gd` | Tools that read or edit a project's files without running the game. Every request carries its own ceiling and the prep's C# build state (`params.build`), the configuration it builds (`params.buildConfiguration`, `ProjectPrep.Configuration`) and, when the build failed, its errors quoted by `CompilerErrorList.Quote` (`params.buildErrors`), which `SceneEdit.csharp_refusal` quotes. Under a failed build `HeadlessTools.AddBuildAndErrors` adds the `csharp` block to every scene tool's result and drops the missing-assembly symptoms from `errors`. A request can name assets it loads (`HeadlessRequest.ImportAssets`); one with no `.import` sidecar, or whose imported file is missing (`PrepScan.AssetNeedsImport`; `.tres`, `.res`, `.dds` and `.ktx` load without one), makes prep run the import first. Script, texture and scene paths must match the case on disk. `operations.gd` runs `validate` and `get_scene_file_tree` itself and hands every other op to `scene_ops.gd` (`delete_nodes`, `attach_script`, `duplicate_node` and `load_sprite` are in `scene_nodes.gd`; the signal ops in `scene_signals.gd`; `export_mesh_library` in `scene_mesh.gd`; the property ops in `scene_props.gd`, which uses the JSON module's public `property_info`, `is_shown`, `same` and `type_name` as the `Inspect` module does, and `scene_values.gd` converts values with the JSON module's `node_root` set to the scene root; `scene_paths.gd` holds the node-path helpers and `scene_files.gd` the uid family and `save_resource`, which writes a resource and restores its uids, the ext uids for `.tscn` and `.tres` only): `create_scene` and `save_scene`, and every node op through `apply(op, root, params, context {scene, build, buildConfiguration, buildErrors})`, a lookup in the `EDIT_MODULES` table; an op in `READ_OPS` runs through `read_scene` (open, apply, free, never save), any other through `edit_scene` (open, apply, save). `scene_edit.gd` opens a scene with `GEN_EDIT_STATE_MAIN` (DISABLED flattens an inherited scene and doubles its inherited connections: `packed_scene.cpp` L233-236, L682), finds nodes by paths relative to the root, refuses a node inside an instance (its owner is not the root) and, for a delete, a node an inherited scene gets from its base, refuses a save that depends on a C# script while the build is red (a node's own `.cs` script, or a scene it instances or inherits, or references as a `PackedScene`, that uses one, followed through `.tscn`/`.scn` dependencies however deep: a C# script that cannot load leaves its node with no script, and saving then drops it and the instance's exported values), and saves with `pack` and `ResourceSaver.save`, then writes back the header uid (`ResourceSaver.set_uid`; a new file gets `ResourceUID.create_id()`) and each `ext_resource`'s `uid=` (the source file's own first, else read from the file, its `.uid` or its `.import`), since a `--script` save writes neither. The edit tools write `.tscn` only: a binary `.scn`'s uid cannot be read back outside the editor. `HeadlessRunner` takes the folder's prep lock and holds it through prep and the Godot run; runs beside live sessions on the folder: a `--script` run reads `override.cfg` and loads the bridge, which `GODOT_MCP_OFF=1` (`GodotCommandLine.OffVariable`, set on every headless run) switches off before it reads its env vars or an attach file, so it frees itself silently; `ClearFolder` deletes a marked file no live server owns (`OverrideFolders.RemoveStaleOverride`), and leaves one a live server owns, this server's own for a session or an arm included; runs prep (a red build is reported, not thrown); then, for a GDScript-only project (`PrepScan.FindCsproj` finds none), sends `headless {op, params}` to the folder's **warm host** (`HeadlessHosts` on the registry, one `HeadlessHost` per `ProjectPaths.Normalise`d folder): `godot --headless --path <p> --script <abs host.gd>`, started through `ToolProcess.Start` (a process kept running, stdin closed, its tree in `OwnWork`) with `GODOT_MCP_OFF=1`, `GODOT_MCP_HOST_PORT` and `GODOT_MCP_HOST_TOKEN`, dialling `BridgeListener` with a hello `{host: "headless"}` within `GodotSession.HandshakeTimeout`, and answering `{id, ok, result: {ok, result?, error?, engineErrors}}`, the object a result file holds, through `headless/operations.gd`'s static `run_request` with the **start slice** of errors it logged while starting; ## A request's path

1. The SDK binds the call's arguments with `ToolJson.Options` (an unmapped key is refused); the call-tool filter `ArgumentErrors.Filter` refuses an unknown top-level argument first and turns a binding failure into an `McpException` naming the argument path, the kind it takes and the value given. The tool method then checks its arguments (failures become `McpException`, whose message is all the client sees).
2. It resolves its session: the named one, else the only live session, else the only session there is; with none it throws "No Godot session is running…", and with several and no name it refuses and lists them. Then it calls `GodotSession.SendAsync(command, params, timeout, ct)` on that session.
3. `BridgeConnection` sends a frame (4-byte big-endian length, UTF-8 JSON) carrying a request id and waits for the reply with that id for the tool's timeout of load-adjusted time, bounded by its backstop; a reply for a timed-out id is dropped. A timeout at the ceiling keeps the tool's usual text; one at the backstop adds `; that is 5 x its <n> s ceiling in wall time, the backstop (load-adjusted <a> s, machine free <f>% on average)`. A timeout goes to the hang watchdog (`HangProbe`): a ping with 2 s to answer tells a busy game (the ping answers: the main thread is running) from a stuck one, and for a stuck one the tool's error adds the game process's CPU use over a 1 s sample, its thread count, its main (earliest-started) thread's state and wait reason, and a run's last 20 stderr lines. The process sampled is the game's own, from the hello's `pid`, not the `Godot_console.exe` wrapper the server started. A game a debugger holds at a breakpoint has every thread frozen, the bridge's too: when `DebuggerPresence` (`CheckRemoteDebuggerPresent` on the game's pid; never true off Windows) finds a debugger attached, `GodotSession.SendAsync` sends a 500 ms ping before each command and fails at once when it goes unanswered, and the watchdog reports such a game as paused under a debugger rather than stuck; with no debugger attached no extra ping is sent.
4. The bridge's `_handle_frame` looks `command` up in its handler table (`_command_handlers`, command → `Callable` taking `(id, params)`, built in `_ready`) and replies `{id, ok: true, …}` or `{id, ok: false, error}` (`_reply_error`). A cancellable request (`frame`, `wait_for`, `monitor`, `frames`, `dotnet`, `run_script`, `call_method`, `watch`: the bridge's `CANCELLABLE`) is kept in `_running_requests`, id → the params its handler holds, from the frame that read it until its reply; when the connection ends, each is cancelled, so it stops at its next frame rather than at its `backstopMs`, and the list is emptied. The server sends one `cancel` at most for a request, and only for one it wrote.
5. The tool shapes the reply into its result: JSON text (`JsonSerializerDefaults.Web`), and for `take_screenshot` an image block read from the PNG file the bridge saved. Lists and logs are held to a budget (compact output): `get_ui_elements` pages by `offset`/`limit`, `get_debug_output` by `limit`/`before` with long lines cut, a `run_script` value over 20000 characters becomes `{valuePreview, valueLength}`.

**The error feed.** The bridge's `Logger` (`bridge/godot_mcp_logger.gd`, registered with `OS.add_logger` in the bridge's `_init`) receives every engine and script error and warning on whatever thread raised it, and only appends it, under a `Mutex`, to a queue capped at 200 (overflow is counted as `dropped`), numbering every entry so `first_error_since` can find an error logged across one call (`options.call`) while the entry is still queued. On the main thread the bridge flushes the queue as an id-less errors frame, `{type: "errors", entries, dropped}`, every frame and before every reply, so an error raised while a command ran is on the wire before its reply. `BridgeConnection` hands errors frames to the session's `ErrorFeed` (the last 500 entries, each with a per-session `seq`). A runtime tool marks the feed before sending and attaches the errors (not warnings) after the mark to its result as `errors: [{seq, message, file, line, function, engine?, stack, count?}]`, shaped by `ErrorReport` (repeats collapsed with a count, at most 20 then `errorsOmitted`, messages cut at 2000 characters); the call still succeeds, except `run_script`, which fails when its script does not compile, or returns null with an error located in its own source (`gdscript://…`). An error whose location is not a script (`push_error`'s own C++ site, an engine `ERR_FAIL` such as `get_node` on a missing path, C# errors) is moved to the most recent backtrace frame, and the C++ site is kept as `engine: "<file>:<line>"`. A handler failure on an errors frame is logged and the frame dropped; the read loop carries on. Backtraces are filled in debug builds, or when the project sets `debug/settings/gdscript/always_track_call_stacks`. Launched and attached games report alike; stderr is kept only for `get_debug_output`.

**Cancel and `backstopMs`.** A request the bridge can end early is sent with a release (`BridgeCall.Release`): a `frame_control` step gets its allowance (10 s + 100 ms a frame), a `capture_frames` its `options.timeoutMs` or the last point plus 10 s + 100 ms a point (plus `options.start`'s `timeoutMs`), a `watch` `run` its window's allowance (10 s + 100 ms a frame, or `gameMs` + 10 s, at most 600 s), a `wait_for` with `timeoutMs` above 0 its `timeoutMs` (in a recording, `timeoutFrames`, `ceil(timeoutMs x 60 / 1000)` movie frames the bridge counts, released at 10 s + 100 ms a frame), and every `dotnet` request its `timeoutMs` (10000 when the tool gives none). The request then carries `backstopMs`, 5 x the release in milliseconds: the bridge's own real-time limit, used in place of the step's `deadlineMs` or the wait's or C# call's `timeoutMs`. The server waits for the reply 5 s past the release for a step, capture, wait or watch run, and `timeoutMs` plus 30 s for a C# call. When the release passes in load-adjusted time, or the caller abandons the call while it runs (its own timeout or a cancelled token), the server sends `{"command": "cancel", "params": {"request": <id>}}` through `SendRawAsync` (2 s to answer) and keeps waiting for the request's own answer. The bridge answers `{cancelled: true}` and marks the request's params `_cancelled`: a step ends as at its deadline (`STEP_STALLED`, the game left paused), a `watch` `run` with its timeline so far and `stopped: "deadline"`, a `wait_for` answers `{met: false, elapsedMs, frames, last}` at its next frame, and a C# call is forgotten with the usual timed-out error. It answers `{cancelled: false}` for a request already answered, not cancellable or unknown. A bridge that predates the command answers `unknown command 'cancel'` and ignores `backstopMs`; an unanswered or refused cancel is logged at Debug, and the request ends at its `backstopMs`, or at its `deadlineMs` or `timeoutMs` on an older bridge.

## Load-adjusted time

Every ceiling the server enforces counts load-adjusted time: a clock that keeps wall time on an idle machine and slows while other work loads it, so a busy machine does not turn a slow build or a slow frame into a timeout. `LoadClock.Shared` samples the machine once a second (`GetSystemTimes` through `SystemLoadSource`; off Windows, or while a read fails, the clock runs at wall time). Between two samples the busy share of all processors, times the processor count, less the cores the server's own work used, is the other work's load; the free share is what that leaves of the processors, never below 5%, and each second of wall time adds the free share of a second. The server's own work is its own CPU plus that of a job object (`OwnWork`) that every process it starts joins, used only for accounting: no limits, no kill on close. An attached game joins no job, so it counts as other work.

- **Ceilings**: the prep's C# build, its `dotnet msbuild -getItem:Compile` listing and its Godot import (300 s each), a headless run (60 s; `batch_scene_operations` 120 s), a recording's ffmpeg cut, the launch handshake (15 s), `attach_project`'s `waitSeconds`, `preview_scene`'s 60 s, `batch_drive`'s 300 s, git (30 s; after git exits its output gets 5 s, and a sweep's `git commit` has no ceiling, since killing it mid-hook can strand the user's unstaged work in a hook's stash), and every bridge reply wait, caller-set ones included: `run_script`, `call_method`, `cs_call` and `run_csharp` `timeoutMs`, and `wait_for` `timeoutMs`. Durations of an action are not ceilings: `drag` `durationMs`, a gamepad sweep, `stress_input`'s gap, `hover`'s tooltip wait.
- **Backstop**: every ceiling also ends at 5 x its value in wall time, however loaded the machine (`LoadDeadline`, `DeadlineReason.Backstop`).
- **Stall kill**: `ToolProcess` checks its process once a second, and kills the tree when neither a line reaches the log nor its tree uses CPU for 120 s (`StallWatch`, `ToolProcessRequest.StallLimit`). The tree's CPU comes from a job of its own (`OwnWork.TreeCpu`); when the process cannot join one, the stall guard is off for that run (logged at Debug) and the ceiling and backstop still apply.
- **Kill text**: a prep, headless or ffmpeg process killed by any of the three says `did not finish within 300 s of load-adjusted time (wall 812 s, machine free 37% on average)` at the ceiling, and `did not finish (<detail>)` for the other two: `stalled: no output and no CPU for 120 s`, or `ran 1500 s of wall time, 5 x its 300 s ceiling (load-adjusted 118 s, machine free 8% on average)`. A bridge or tool timeout keeps its usual text at the ceiling and adds the backstop clause (see [A request's path](#a-requests-path)) at the backstop.
- **Wall time**: the pings (the hang probe's 2 s, the debugger check's 500 ms), the `shutdown` reply, the `cancel` itself, the listener's 5 s hello read, and the kill and exit graces (a killed tree's and git's 5 s, the output drain, a recording's 10 s wait for the game to exit).

The integration tests' `SessionHarness` runs its requests' and tools' ceilings on a wall-time clock, so another build loading the machine cannot move a short ceiling into its backstop and change the text a test asserts, and sets the registry's `LaunchClock` to the load-adjusted clock, so a launch's handshake and an attach's wait for its game wait out the load as they do in the server (`LaunchClock` is `Clock` unless set); the unit tests cover the load with `FakeTimeProvider` and `FakeLoadSource`.

## Session lifecycle

- **Names**: `run_project` (`options.session`, else its preset's `session`) and `attach_project` (`session`) name the new session, by default after the project folder. A name is 1-64 of letters, digits, `.`, `_`, `-`: a given name outside that is refused, and a folder name is fitted to it, each other character becoming `_` and the result cut to 64 (`My Game` → `My_Game`), and when a live session on another folder holds the default name, the first `<name>-<n>` (n from 2) no live session holds is taken, the folder part cut so the suffix fits, chosen under the registry lock. Runs and attaches share one name space. A given live name, or a default one whose live holder is on the same folder (running, attached, or still launching or waiting to attach), is refused; a stopped one is replaced. A stopped run stays listed so `get_debug_output` can read it; a detached or stopped attached session is forgotten.
- **One folder, several sessions**: the marked `override.cfg` is written by the first live session on a folder and removed when the last one ends (stop, detach, the game exiting, a failed start, server exit). Its second line lists its owners, the server processes (`pid@start ticks`, `OverrideOwner`) with live sessions on it: `WriteOverride` records the folder in `%LOCALAPPDATA%\godot-mcp-cache\override-folders.txt` (`OverrideFolders`, held open alone) and writes the file with this server added to the live owners already listed; a release (`OverrideFile.Release`) takes this server off and deletes the file only when no live owner is left, so one server never deletes a file another server's session uses. Every release, and every write or release of `armed.json`, runs while that list is held alone (`OverrideFolders.Hold`, retrying up to 2 s), file lock outside the registry's `_lock`, so two servers never interleave their read-modify-writes. A write whose bridge path, `quiet` or `shutOutRealGamepads` differs from a live other owner's (parsed from its body, so a file another version wrote with the same values is shared) is refused naming that server's pid, and so is an `armed.json` write whose `quiet`, `shutOutRealGamepads` or `mute` differ. A server killed before its shutdown leaves its file; `Program.cs` runs `OverrideFolders.Sweep` before the host starts, deleting each listed folder's marked file whose owners have all exited (or that lists none) and dropping folders that hold none. A game started by hand from such a leftover finds no server: the bridge warns, restores a window the quiet `[display]` keys parked (focusable, centred, in front) and frees itself. A new session whose `shutOutRealGamepads` or `quiet` differs from the live ones' is refused (an attach is quiet only with `quiet: true`), and so is a second plain attach on a folder while one is still waiting for a launch (`attach.json` is one per folder); joins wait beside it and beside each other, each for its own pid.
- **Prep** (every launch, under the folder's prep lock from `SessionRegistry`, held through starting Godot, so launches on one folder never build or import at once): unless `options.prepare` is `"never"`, `ProjectPrep` builds the C# assembly when it is missing or older than its build inputs (the csproj is `[dotnet] project/assembly_name`'s, else the one `*.csproj` beside `project.godot`; inputs are `git ls-files -co --exclude-standard` from the git top level, filtered to C# build files; a `.godot/godot-mcp/build.stamp` touched after each green build keeps a non-compile change from rebuilding every run) with `dotnet build <csproj> -c Debug -p:GodotTargetPlatform=windows`, then runs `godot --headless --path <p> --import` when a versioned `*.import`'s `dest_files` target is missing or `.godot/uid_cache.bin` lacks a uid a `*.uid` file or a `.tscn`/`.tres` header records, in a folder Godot's scan reaches (`PrepScan.IsUidCacheStale`, comparing contents: the headless tools append each uid they create to the cache, `SceneFiles.cache_uid`, and an editor open on the project rewrites it from its own list on its next save; with no cache, any scanned `*.uid` file), or a `.gd` declaring `class_name` is newer than `.godot/global_script_class_cache.cfg` (or that cache is missing while one exists: a game and a `--script` run read class names only from it, and the import's first scan rewrites it) (a second pass when the first logged `ERROR:`). A red build or a failed import refuses the launch with the parsed compiler errors or the log path; an import is refused while another session's game runs on the folder. A build is not: a running game reads its assembly and pdb into memory and holds no file open (`PluginLoadContext.cs` L59-69 in 4.7.2; measured with two games on one CsProbe copy, four rebuilds, each exit 0), and it keeps the code it loaded. Logs go to `.godot/godot-mcp/build.log` and `import.log`; each process (the build, the Compile listing, the import) has a 300 s ceiling of load-adjusted time, its backstop and the stall kill, and a killed one refuses the launch saying it `did not finish (<detail>)` with its log.
- **Profile** (`run_project`, before the launch; and for every prep about to run a process, `PrepWrapper.Read` loads the same file for its `prepWrapper`, and `PrepWrapper.Wrap` runs the build, the Compile-items listing and the import through it from the project folder, `{log}` and `{ceiling}` substituted, the wrapper's own output in `<step>.wrapper.log` when it owns `{log}`, no stall kill, exit 124 a stop): `ProjectProfile.Load` reads `godot-mcp.json` beside `project.godot` (absent: an empty profile), strictly: invalid JSON, an unknown or repeated key, a wrong-typed value, a `resolution` other than `WIDTHxHEIGHT`, a bad preset `session`, and an `options.preset` the file lacks are each refused with the path and the fix. `Merge` layers the top level, then `options.preset`'s preset, then `run_project`'s own arguments: `scene`, `resolution` and `quiet` are replaced by the later layer, `userArgs` and `engineArgs` append in that order, `resolution` becomes `--resolution WxH` before every engine argument, and the session is `options.session`, else the preset's `session`, else the folder's name. `quiet` stays true when nothing sets it. The merged request is what `LastLaunch` stores, so `restart_project` never re-reads the file.
- **Run** (`run_project` → `GodotSession.LaunchAsync`): after prep, `OverrideFile.Write` writes the marked `override.cfg` naming the bridge as an autoload (refusing a user's unmarked one), `GitExclude` hides it, and `StartRunAsync` creates a random token, starts Godot with `GODOT_MCP_PORT` and `GODOT_MCP_TOKEN` in its environment (plus `GODOT_MCP_QUIET` unless `options.quiet` is false, `GODOT_MCP_SHUT_OUT_REAL_GAMEPADS` when asked, and `GODOT_MCP_MUTE` for a watched run with `options.mute`). A quiet run also gets `--audio-driver Dummy` before the user's engine arguments (a later `--audio-driver` of theirs wins), and its override adds `[display]` `window/size/no_focus=true` with an off-screen initial position, so the window is created unfocused; on Windows a quiet run's Godot is started by `DesktopProcess` on the server's hidden desktop (`HiddenDesktop`), created suspended, watched through `Process.GetProcessById`, then resumed, with its output read from its own pipes (`IRunProcess` in `GodotRun.cs`; `StartInfoProcess` is the `Process.Start` path every other run takes). Every run joins the server's `OwnWork` job, the hidden-desktop one while still suspended. It then waits for the handshake: 15 s of load-adjusted time (`GodotSession.HandshakeTimeout`), after which Godot is stopped and the launch fails with its stderr.
- **Attach** (`attach_project` → `AttachAsync`): `AttachFile` writes the one-use `.godot/godot-mcp/attach.json` ({port, token, shutOutRealGamepads, quiet, mute}, `mute` the effective `mute || quiet`), then the override under the folder's prep lock (so it never lands during a launch's prep or a headless run), and waits `waitSeconds` of load-adjusted time for a game launched after it to dial in; the attach file is deleted once the wait ends, only while it still carries this attach's token and under `OverrideFolders.Hold`, which its write (temp file then move) and the join file's write and removal take too.
- **Handshake**: each session registers its expectation with `BridgeListener.AcceptBridgeAsync`. The listener's one accept loop reads each hello `{type: "hello", token, projectPath, pid, window: {width, height}}` (`window` the game window's size after the bridge's resize, carried to the launch and attach results) (`pid` is the game's own process id, kept as `GodotSession.GameProcessId` and checked by nothing; a hello without it still connects) (sockets handled concurrently; a hello not arrived within 5 s refuses its socket, unless a session is still waiting for a bridge, when the read lasts until the last waiter ends, so a game paused at a startup breakpoint before its first frame keeps its connection), finds the waiter by a dictionary lookup on its token and checks the hello with `HandshakeExpectation` (the token, then the path). The lookup is not constant-time; the token is 32 random bytes on loopback only. An unknown token or a mismatch is logged and its socket closed; the waiter keeps waiting.
- **Recording** (`run_project` `options.record`): Godot's Movie Maker from launch. `GodotCommandLine.BuildArguments` adds `--write-movie <project>/.godot/godot-mcp/recordings/<UTC yyyyMMdd-HHmmss-fff>-<session>.avi --fixed-fps 60 --quit-after 36000` (a 10 minute cap) before the engine arguments, a new file each start; `--headless`, `--display-driver headless`, and a user's own `--fixed-fps`, `--write-movie` or `--quit-after` are refused. Movie Maker forces the Dummy audio driver and still records audio, and fixed fps makes game time advance 1/60 s a frame whatever the wall clock does (main.cpp L2829-2832, L5170-5172 in 4.7.2). `record_mark` asks the bridge's `movie_frame` for `Engine.get_process_frames()`, which equals the number of frames the writer has written (the counter rises once an iteration, just before `add_frame`); marks alternate start and stop. When the run ends (stop, the game quitting, a restart replacing it), `RecordingCut` waits up to 10 s for the game's own process, then encodes one clip per start-stop pair with ffmpeg (`FFMPEG_PATH`, else `PATH`) to `<stem>-clipN.mp4`: input-side `-ss`/`-to` half a frame early, so the filters see only the clip's frames; libx264 `-preset veryfast -crf 18`, `yuv420p` scaled to an even size, AAC, `+faststart`. With `options.dropIdle` the filters start with `mpdecimate,setpts=N/60/TB` and the audio is dropped: Movie Maker writes a frame every main-loop iteration whatever was drawn (`add_frame` is unconditional, and a custom `MovieWriter` must be registered before any autoload), so idle frames can only go at the cut. A clip whose encode fails is cut the old way instead, by output-side `-ss`/`-to` and `-c copy` to `<stem>-clipN.avi` (exact for MJPEG and PCM), and the failure joins the result's `error`. Each cut may take `max(120 s, 3 s per clip second)` of load-adjusted time (an open clip counts to the frame cap), with the backstop and the stall kill; a killed cut's error says `ffmpeg did not finish <step> <clip> (<detail>)`; log `recordings/ffmpeg.log`; the full file is deleted once every clip is cut. A killed game's movie has no duration and is kept uncut with an error; a missing ffmpeg or a failed copy keeps the full file and reports an error, never throws. The outcome is `stop_project`'s `recording`, `restart_project`'s `previousRecording`, and the stopped session's `recording` in `list_sessions`. If the server itself exits, a recording game is killed and its movie is not finalised.
- **Stop** (`stop_project`): a ping first; a game silent for 2 s is stuck and is killed at once with no `shutdown` command. One that answers (or whose connection is gone) gets a `shutdown` command and a kill after 3 s of load-adjusted time (30 s for a recording run, whose clean quit finalises its movie), with the backstop at 5 x the grace in wall time (`ProcessExit.WaitUntilGoneAsync` with a `LoadDeadline` on `registry.Clock`). Before a kill after the grace the server samples the game's process for 1 s and reads whether the bridge's connection had closed, and the `killReason` says both (`GameKillReason.AfterGrace` with a `GraceKill`): a connection still open means the scene tree was never freed, a closed one means the time went into the engine's or .NET's teardown. The grace waits on the game's own process (`GodotRun.Game`, kept from the hello) when there is one, not the wrapper: on Windows `Godot_console.exe` puts the game in a job object and waits for every process in it, so a game that quit leaving a child running would read as a kill. Once the game is gone the wrapper gets 1 s to follow; one still running is ended (`TerminateAsync`, not a kill), which ends the job, and the processes the game started are listed first (`LeftBehind`, a Toolhelp snapshot by parent pid and start time) as `leftRunning`. A real kill records `killReason` (`GameKillReason`) and makes `gameExitCode` null. The ping, the shutdown and these graces are wall time, not load-adjusted. Either way the override is removed if no other live session uses the folder. An attached session is stopped by the same `StopGameAsync`, watching and killing the game's own process: `AttachAsync` opens a handle on the hello's `pid` (`KeepAttachedGameHandle`) so its exit code stays readable; with no handle (no `pid`, or it could not be opened) the game is only asked to quit, the stop waits the grace for its connection to close, and a `warning` says it may still be running. The session then ends as a detach does (`EndAttachmentAsync`), forgotten rather than kept as stopped, with `exitCode` null.
- **Restart** (`restart_project` → `GodotSession.RestartAsync`, in `GodotSession.Restart.cs`): under the session's gate and with the session pending throughout (its name never frees), prep runs while the old game still runs, counting only other sessions' games for the import refusal; then the old run stops as a stop does but keeps the folder reserved and the override in place, and the stored `LaunchRequest` starts again under the prep lock. The new `GodotRun` takes over the old one's output buffers and gets a marker line; the error feed is the session's, so `seq` continues. An exit of a run the session has already replaced does nothing but log, so the old run's `Exited` handler cannot remove the new run's override. A failure after the stop releases the folder and leaves the session listed with its output. A cancelled call never stops the old game once prep is done. A `stop_project` that lands while a restart is waiting for the session's gate is followed by the restart's relaunch, since a stopped session can be restarted.
- **Arm** (`arm_project` → `SessionRegistry.ArmAsync`): under the folder's prep lock, the override is written as for a session, `GitExclude` hides it and `ArmFile` writes `.godot/godot-mcp/armed.json` ({quiet, shutOutRealGamepads, mute, owners}, the owners as in the override). The registry keeps the folder's arm settings. A folder is held while a live session uses it or it is armed, so a stop or detach there leaves the override, and every new session is checked against the arm's `quiet` and `shutOutRealGamepads`. `disarm_project` releases `armed.json` (deleted once no live owner is left) and then the override, as a stop does. `Shutdown` disarms every folder, and the startup sweep deletes an `armed.json` whose owners have all exited.
- **Dormant bridge**: a game with a window started with the override but with no environment endpoint and no `attach.json`, on a folder whose `armed.json` exists, keeps its bridge dormant; a headless one never goes dormant, at start or after a detach. It writes `dormant/<pid>.json` ({pid, startedUnixMs}), parks its window when the arm is quiet, and checks every 500 ms (`PROCESS_MODE_ALWAYS`, so also while paused) for `join-<pid>.json` and for `armed.json`. With `armed.json` gone it deletes its file and goes idle. `DormantGames.List` reads the files and deletes each one whose pid is no longer a live process, or whose process started more than 2 s after `startedUnixMs` (a reused pid).
- **Join** (`attach_project` on a folder with dormant games): the choice is made under the registry's lock, before any file is written, and carried on the spec as `JoinPid`; a join of a pid another join already waits for is refused naming that session, and so is a pid-less join whose only dormant game is taken. `options.pid` must name a dormant game; with no pid, a single dormant game is joined, several are refused with the list, and none falls back to the attach above. A join writes `join-<pid>.json` ({port, token, shutOutRealGamepads, quiet, mute}) in place of `attach.json` and waits for the hello as an attach does. The bridge deletes the file on reading it, and the server deletes it when the wait ends or at shutdown, only while it still carries this join's token. The result carries `joinedPid`. The bridge registers its logger at the join, so the error feed starts there.
- **Detach** (`detach_project`): the connection closed, the override removed as for stop (kept while the folder is armed), the game left running. A bridge whose endpoint came from `attach.json` or a join file goes dormant again when its connection ends and `armed.json` still exists: the injected input it still holds released (keys, input actions, mouse buttons, pad buttons and axes), its connection state reset, a running or held watch dropped (as it is when the bridge goes idle instead), a window a quiet join parked restored, its dormant file rewritten. The attach file is not touched: each attach removes its own when its wait ends, so a detach never deletes another attach's file on the same folder.
- **Game exits on its own**: `OnRunExitedAsync` releases the override as for stop.
- **Snapshots**: `GodotSession.Snapshots` (`SnapshotStore`) holds `snapshot_subtree`'s captures and `get_game_state`'s kept reads, each a `Snapshot` of its `SnapshotKind` (`Subtree` or `State`) carrying the options that take it again, the 16 most recently used, ids never repeating in the session; it is emptied when the run stops, when a restart has ended the old run, when the current run exits, and when an attached game's connection ends (a watcher started at attach awaits `BridgeConnection.Closed`). A detach drops the session, and the store with it.
- **Captures**: `SessionRegistry.Captures` (`CaptureStore`) holds `capture_input`'s events by session name, not on the `GodotSession`, so a capture outlives its game: a stop, a restart, the game exiting or a detach marks a running capture `ended` (`stop`, `restart`, `exit`; a detach counts as `stop`) and keeps what reached the server, until the next `capture_input stop` naming that session takes it or a new start replaces it. It holds at most 2000 events.
- **Server exits**: `SessionRegistry.Shutdown` kills every run and removes every folder's files.

## Distribution

Two routes put the same files in `%LOCALAPPDATA%\godot-mcp` (the published server: `godot-mcp.exe` framework-dependent on .NET 10, `bridge/`, `headless/`, `dotnet/`, the skills as `skill/` and `agent-sweep-skill/`, and `VERSION`). Both stop every `godot-mcp.exe` running from the install folder first, through `tools/InstalledServers.psm1` (inlined into the release's `install.ps1` by `tools/package.ps1`), and print a line for each naming the Claude session (the parent `claude.exe`'s `--session-id`) and its project (the `cwd` in that session's transcript under `~/.claude/projects`), so the user can reconnect it with `/mcp`. From source, `run.ps1 install` publishes and runs `tools/install.ps1`, which mirrors `bin/publish` (the publish copies `skills/godot-mcp` and `skills/godot-agent-sweep` in as `skill/` and `agent-sweep-skill/`) and links `~/.claude/skills/godot-mcp` and `godot-agent-sweep` to the install folder's copies as junctions, so the skill an agent reads always matches the installed server. From a release, `install.ps1` (`tools/install-release.ps1`) downloads `godot-mcp-win-x64.zip` (the latest, or `-Version`; `-ZipPath` for a local one), checks for the .NET 10 runtime where the apphost looks (`DOTNET_ROOT_X64`, `DOTNET_ROOT`, the registered install location, then `%ProgramFiles%\dotnet`) and installs `Microsoft.DotNet.Runtime.10` through winget when asked (`-InstallDotNet`) or allowed at a prompt, replaces the folder's contents (refusing a non-empty folder that holds neither `godot-mcp.exe` nor `VERSION`), and copies the zip's `skill/` into `~/.claude/skills/godot-mcp`, removing a junction there without following it. The zip is `run.ps1 package`'s, built by the release workflow on a `vX.Y.Z` tag (see DEVELOPMENT.md, CI and releases).

## The bridge

- **Start**: in `_init`, `choose` (`bridge/godot_mcp_dormant.gd`) picks the mode: a run's port and token from the environment, else `res://.godot/godot-mcp/attach.json`, else dormant when `armed.json` exists and the game has a window (`is_headless`: `DisplayServer.get_name() == "headless"`; see Dormant bridge in the session lifecycle), else off. With an endpoint, the error-feed logger is registered there (and never removed: Godot drops script loggers at shutdown); off, it warns and frees itself, silently when `frees_silently` (the server switched it off, or a headless game on an armed folder). `_build_once` makes the children and `_join` serves the endpoint, at `_ready` or at a later join. When the endpoint is quiet (`GODOT_MCP_QUIET` is 1, or the attach or join file says `quiet`), `park_window` (`bridge/godot_mcp_window.gd`) makes the window click-through and moves it off-screen: Windows clamps the override's off-screen initial position onto the primary screen at creation, so the window shows there, unfocused, until the bridge's `_ready`. A run the server started on its hidden desktop (`GODOT_MCP_HIDDEN_DESKTOP` is 1, set by `GodotCommandLine.CreateStartInfo` for a quiet Windows run and removed for every other launch) is moved to (0, 0) instead, out of sight already: a parked root would make Windows clamp a non-embedded popup to (0, 0) and lose its offset from the root, which `grab_frame` needs. The same branch sets `Engine.max_fps` to 60 when it reads 0 (the project set none): a quiet window keeps VSync, so it would otherwise draw at the monitor's refresh (239 fps measured) for frames nobody sees.
- **Commands** (`_command_handlers`): `ping`, `preview` (the `Preview` child, `godot_mcp_preview.gd`: when the viewport has a 3D world, no current `Camera3D` and visible `GeometryInstance3D` nodes under the current scene, adds a `PreviewCamera` framing their merged AABB from `(1, 0.8, 1).normalized()` at `radius / sin(fov / 2)`, waits two drawn frames, then saves the screenshot as `screenshot` does and adds `scene` and `cameraAdded`), `screenshot` (saves `.godot/godot-mcp/screenshots/<stamp>-<pid>.png` and a Lanczos preview when wider than asked; replies with paths, never bytes), `ui_elements`, `run_script` (compiles a script with `execute` and calls it with `Object.call`, never awaiting it: a suspended `execute` is kept in `_running_scripts` with its instance and a snapshot of `Engine.time_scale` and `SceneTree.paused`, and answered from its `completed` signal; a cancel drops the instance, whose destructor clears the pending coroutine so it never resumes, restores the snapshot and answers the request as stopped; a `call_method` still awaited is kept in `_running_calls`, and a cancel restores its snapshot, answers it and leaves the method running), `input` (gestures and raw events, under `_handle_input`), `shutdown`, `cancel` (`{request}` → `{cancelled}`: marks a running cancellable request's params `_cancelled` and calls the `Time` and `Watch` modules' `cancel`, each of which ends a running step, capture or watch as its deadline would only when the params are the very Dictionary it runs on; see [A request's path](#a-requests-path)); `scene_tree`, `inspect_node`, `set_property`, `call_method` and `snapshot` (every node of a subtree with its shown or named properties and sorted groups, for `snapshot_subtree`; the diff is the server's `SnapshotDiff`) are forwarded to the `Inspect` module, which refuses the bridge's own nodes; `frame` and `wait_for` to the `Time` module; `watch` to the `Watch` child (`_handle_watch`, which awaits its `handle`: a `start` answers after the watch's first frame, a `run` at its window's end); `state` to the `State` child (`godot_mcp_state.gd`: the `mcp_state` group's nodes in tree order, bridge nodes left out, each one's `_mcp_state()` read in one handler with no `await` and `call_now`'s error window, cut at `maxDepth` with leaves through `to_json`, sliced by `maxNodes`); `compare_screenshot` to the `Baseline` module. Every capture of the root viewport goes through the `Frame` child's `grab_frame` (`godot_mcp_frame.gd`) (the texture, with each visible non-embedded `Window` found through `DisplayServer.get_window_list` pasted by the static `paste_windows` at its offset from the root, mapped through the inverse screen transform); the screenshot's capture and save are split (`save_screenshot`, `crop`) so a step can capture inside its own `frame_post_draw` handler; in low-processor mode a screenshot forces a draw rather than waiting for one.
- **Real input**: injected mouse events carry the injected mark, and `_input` swallows unmarked (real) mouse events while a gesture plays or an injected button is held, and with them the touch twins of real mouse events (those not raised while the input module's `dispatch` runs). Keys are never swallowed, and injected keys carry no mark (their device stays 16, which the built-in `ui_*` actions require). A quiet run keeps real input out by never receiving it: unfocused from creation, click-through and off-screen. `godot_mcp_gamepad.gd`'s `shut_out_real_pads` keeps real pads out when asked.

## Tool annotations

Every tool declares `openWorldHint: false`. `readOnlyHint: true`: `get_debug_output`, `list_sessions`, `take_screenshot`, `compare_screenshot` and `preview_scene` (their PNGs go under the ignored `.godot/`; `save_screenshot`, which writes a project file, is `readOnlyHint: false`, `destructiveHint: false`), `get_ui_elements`, `get_errors`, `get_scene_tree`, `inspect_node`, `snapshot_subtree` (its store is server memory), `cs_members` (reflection runs no game code), and the headless `validate`, `get_scene_file_tree`, `get_node_properties` and `get_node_signals` (their prep writes only under `.godot/` and the build output). `destructiveHint: true`: `stop_project` (kills a process), `run_script`, `call_method`, `cs_get`, `cs_set`, `cs_call`, `run_csharp` and `call_game_tool` (run arbitrary game code: a getter, setter or method runs), `get_game_state` (runs the game's state methods; the `read` class through a `ToolClasses` override, as `cs_get` has), `diff_snapshots` (a live re-read of a kept state read runs them; the `read` class the same way), `watch` (its expressions and `options.call` run game code; the `read` class the same way), `batch_drive` (its steps may call them), `delete_nodes` (removes nodes from a scene file), `disconnect_signal`, `export_mesh_library` (can replace a file) and `batch_scene_operations` (its steps may do both). Every tool sets all three hints explicitly: a read-only tool is also `destructiveHint: false`, every tool not listed as read-only is `readOnlyHint: false`, and every tool not listed as destructive is `destructiveHint: false`. `McpServerSmokeTests` checks all three for every tool.

## Adding a runtime tool

1. A method in the right `RuntimeTools` partial with a last `session` parameter (five schema parameters at most): validate, resolve the session, then `SendAsync` on it.
2. A handler in the bridge, registered by its command name in `_command_handlers` (or a gesture under `_handle_input`).
3. A unit test for the server-side checks (`tests/GodotMcp.Tests/Tools/`).
4. An integration test against the InputProbe fixture (`tests/GodotMcp.IntegrationTests`), and the name in `McpServerSmokeTests`' list. A new test class goes into one group of `run.ps1`'s `$itestGroups`, keeping each group well under its 300 s ceiling (a full `itest` refuses to run while a class is in no group).
5. Its annotations (`ReadOnly`, `Destructive`, `OpenWorld = false`) and `McpServerSmokeTests`' annotation check; a destructive tool that only reads (it runs game code to read) gets a `read` entry in `Agents/ToolClasses.cs` `Overrides` and in `ToolClassesTests`, and the batchable count in `BatchValidationTests` moves with every tool.
6. This file's tool table and, for a new term, the glossary.

## Adding a headless scene edit tool

1. A method in a `HeadlessTools` partial (`HeadlessTools.Scene.cs`, `HeadlessTools.Properties.cs`, `HeadlessTools.Signals.cs`, `HeadlessTools.Mesh.cs`; five schema parameters at most): check the scene path (`CheckEditableScenePath`), build the op's parameters in an `internal static <Op>Parameters(…)` beside it (taking `projectDir` only when a check needs it, as a path check does) that checks every other argument (`CheckNodePath`, the new-file check, …) and that `batch_scene_operations` calls too, then `RunAsync` with the op name and its ceiling.
2. An `apply_<op>(root, params, context)` in the module that owns its kind of op, returning `{result}` or `{error}` without saving and reading the scene and build state from `context`, and its entry in `scene_ops.gd`'s `EDIT_MODULES` (and `READ_OPS` for a read); refuse before changing anything, so a list edit stays all-or-nothing.
3. Unit tests for the server-side checks (`HeadlessSceneValidationTests`), integration tests in `HeadlessSceneTests` on a copy of the probe project, and pure GDScript helpers in `tests/bridge/test_operations.gd`.
4. Its annotations and `McpServerSmokeTests`' list, then this file's tool table.

An op that never saves the open scene is listed in `READ_OPS`: the reads (`get_node_properties`, `get_node_signals`) and `export_mesh_library`, which writes a file of its own; given `context.pending_writes` (an Array), it appends the write there instead of saving, and `SceneMesh.write_pending` saves them later.
